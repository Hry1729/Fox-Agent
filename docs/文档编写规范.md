# 文档编写规范

> 状态：生效<br>
> 适用范围：`docs` 下所有维护中文档<br>
> 最后更新：2026-07-29

## 目标

让不同角色编写的文档具有一致结构，并帮助工程师快速区分当前事实、设计约束、未来计划和历史记录。

## 文件命名

- 除文档入口 `README.md` 外，文件名使用中文。
- 文件名直接表达主题，不添加日期和 `final`、`new`、`v2` 等临时后缀。
- 行业通用名称可以保留，例如 `Agent Runtime架构.md`、`Runtime协议.md`。
- 带日期的内容只用于审计报告、发布记录和归档快照。

## 文档元信息

每篇维护中的文档在标题后提供：

```markdown
> 状态：草案｜维护中｜生效｜已归档
> 适用版本：Fox 0.1.x
> 维护范围：相关目录或模块
> 最后更新：YYYY-MM-DD
```

“草案”不能作为实现依据；“生效”表示已经与当前代码和测试核对；“已归档”表示仅供追溯。

## 推荐结构

核心技术文档优先使用以下结构：

1. 目标与读者。
2. 范围与非目标。
3. 核心设计或职责边界。
4. 组件关系、数据流或状态机。
5. 接口和数据契约。
6. 异常、恢复与兼容策略。
7. 安全与性能考虑。
8. 测试和验收方式。
9. 相关代码与关联文档。
10. 已知限制和待决事项。

不要求为凑齐结构而增加空章节，小型参考文档可以缩减。

## 表达规则

- 先写结论和边界，再写实现细节。
- 使用“必须”“应当”“可以”区分硬约束、推荐做法和可选能力。
- 当前事实使用现在时；尚未实现的内容必须标注“计划”“候选”或关联 Issue。
- 不使用“后端”笼统指代所有非前端代码，应明确是 Tauri 后端、Agent Runtime 还是知识库服务。
- 对外统一称“知识库服务”；代码中的 `yuxi` 模块名作为兼容实现名称保留。
- Mermaid 图中的节点名称应与正文术语一致。

## 代码与路径

- 路径从仓库根目录开始，例如 `apps/desktop/src/features/conversations`。
- 只引用稳定模块入口，避免为每个私有函数建立易失效链接。
- 接口和状态枚举应引用其事实源文件，并说明是否由测试覆盖。
- 命令默认使用 Windows PowerShell 可执行形式，如 `pnpm.cmd build`。

## 旧文档迁移

旧文档迁移必须经过以下检查：

1. 提取仍然有效的架构、契约、风险和验收内容。
2. 将内容合并到对应常青文档或路线图。
3. 核对新文档中的代码路径、接口名和当前实现。
4. 更新所有指向旧文档的链接。
5. 确认旧文档没有独有且仍有效的信息。
6. 再决定移动到 `归档` 或删除。

阶段状态、调研过程和已经退役的方案通常进入归档；仍被开发流程依赖的规格与契约不能仅因文件较旧而删除。

## 审查清单

- 文档描述的是当前实现还是未来计划，是否明确？
- 术语、状态名和字段名是否与代码一致？
- 是否包含真实凭据、个人目录或仅适用于作者机器的信息？
- Mermaid、表格和相对链接是否有效？
- 是否与另一篇文档重复维护同一事实？
- 公共行为是否有测试或人工验收方法？
