# 0 v0.3.1 变更说明（开工备注）

1. **实验开关不豁免安全底线**（第 8 节）：实验后端可暂不满足完整功能和稳定性要求，但权限隔离、审批不重放、凭据保护必须满足，手动开启也一样。
2. **冻结会话配置不等于永久保留权限**（6.5）：权限撤销、企业禁用、安全策略收紧对已有会话立即生效，继续执行或恢复前重新检查。
3. **不伪造原生确认**（6.3）：响应发送途中断线、无法确认是否送达，记为“结果未知”；原生协议没有确认机制时，状态停在“答复已写出”，不标“原生已确认”。
4. **复用优先**（新增 6.7）：公共端口直接采用 ACP v1，Host 用官方 Rust 库；三个外部后端都走现成 ACP 入口，不逐家自研协议对接。

可以开始开发，不代表已经通过发布验收：公共基础能否冻结、各后端能否发布，按实测结果验收。

# 1 方案摘要

**目标**：保留现有 Kernel 作为 FoxBackend，新增原生 pi、Codex CLI app-server、DeepSeek Harness 三个后端；每个会话创建时绑定一个后端。Fox 继续负责会话、授权资源、业务工具、事件、审计和界面，尽快把团队精力转回 UI 与业务流程。

**基线**：Fox-Agent `main` 提交 `06076646be761afd90cba95e8a87565249789a11`，pi 0.84.2。

**推进主线**：先 Fox + 公共 Host，后三分支并行，分批验收、分批发布。

**相对 v0.2 的修改**

1. 恢复三分支并行：公共基础冻结后，pi、Codex、DeepSeek 三个分支同时开发，谁先通过验收谁先合并；DeepSeek 保持实验状态。
2. 补回执行拓扑、并发上限、Agent 反向请求、配置优先级、旧会话映射（第 6 节），作为公共基础冻结内容。
3. 取消与回执丢失允许“结果未知”；晚到响应保留用于核对与审计，不翻转已确认终态。
4. 不改名、不重定义旧字段：新增外层 backend 身份，`engine_id` 保持历史语义。
5. 时间写成评估窗口而非完成保证；授权能力按“审批覆盖 / 沙箱范围 / 取消能力 / 可观测性”分别声明，不排安全等级。

**阶段一览**

| 阶段 | 名称 | 时间 | 并行关系 | 核心产出 |
|---|---|---|---|---|
| 0 | 协议原型与证据 | 约 2 周评估窗口 | 与 1 并行 | 原型、能力声明草表、安全条目补证 |
| 1 | 共享 Host 加固 | 视补证结果定 | 与 0 并行 | 分级清单“冻结前”条目关闭 |
| 2 | Fox + 公共基础 | 视阶段 0 结果定 | 依赖 0、1 | 冻结的端口、拓扑、并发、反向请求、配置、迁移规则 |
| 3 | 三分支并行接入 | 各分支独立 | 依赖 2 | 先过门槛先合并，分批发布 |
| 4 | 收敛 | 持续 | 依赖 3 首批发布 | FoxBackend 定位、旧路径清理 |

阶段 0 的两周是评估窗口：到期时按已得证据做取舍（收窄范围、标实验、推迟），不代表届时一定实测完成。其余阶段不预设固定工期，按退出条件推进。

# 2 不变的边界（全阶段适用）

- 每个会话创建时绑定一个后端；运行中不换后端，不跨后端迁移，不做多 Agent 协作。
- 改造期间只增不删：旧会话、旧数据、旧路径保持可用；每个新后端可单独关闭。
- 未支持的能力明确显示“不支持”，不伪装成功（尤其是原生会话恢复、逐次审批）。
- skip / ignore 的测试不算通过。
- 授权能力按四个维度如实声明，UI 按声明展示；“统一审批体验”不等于“统一阻断能力”：

| 维度 | 回答的问题 | 示例取值 |
|---|---|---|
| 审批覆盖 | 哪些工具类别在执行前经 Host 审批，粒度到哪 | 文件写：逐次；shell：逐条命令；MCP 业务工具：逐次；网络：不经审批 |
| 沙箱范围 | 由 OS 或原生沙箱强制的文件、网络、进程边界 | 工作目录可写、其余只读；网络关闭；Windows 下待验证 |
| 取消能力 | 能停到哪一层，是否可确认 | 停止 turn：原生确认；终止进程树：Job Object；不可确认时标“状态未知” |
| 可观测性 | Host 能看到什么 | 工具开始/结束事件；命令内部子进程不可见 |

注意：一次审批只批准“发起这个调用”，不约束命令内部行为（例如批准一条 `npm test` 后，测试脚本里做什么由沙箱范围决定）。四个维度不合并成一个高低等级。

# 3 阶段 0：协议原型与证据（约 2 周评估窗口）

**目标**：用真实协议样例回答“外部后端能做到什么”，为阶段 2 端口设计和阶段 1 安全条目提供证据。

## 3.1 工作项

**A. 现状基线**：记录调用链（UI → Host → Kernel → 展示）中 engine、mode、授权 manifest、run、session、checkpoint 的来源与写入时机；保留脱敏 Fox 基准场景（普通问答、文件处理、授权请求、拒绝、知识库或业务工具、恢复、取消、异常退出、产物呈现）。

**B. Codex app-server 原型**：锁定 CLI 版本并生成协议 schema；跑通启动 → thread → turn → 工具 → 审批（允许、拒绝）→ interrupt → 正常退出 / 强杀；记录一个 app-server 进程能否承载多个 thread、各平台沙箱差异。

**C. pi RPC 原型**：pi 0.84.2 RPC 模式；跑通 prompt → 工具 → steer → follow_up → abort，以 `agent_settled` 判定完成；验证扩展 `tool_call` 钩子能否阻断并等待 Host 审批；验证环境白名单启动与进程树终止。

**D. DeepSeek Harness 冒烟**：锁定 `@deepseek-ai/dsh` 版本，`dsh --profile acp`；验证 session new / prompt / cancel、`request_permission` 覆盖范围、Node 版本兼容。

**E. 端口形状评估**：对照两份原型事件流，评估以 ACP 为端口基础；列出需 Fox 补充的部分（steer、产物候选、能力声明、连接代次等）。

**F. 安全条目补证**：对第 4 节“影响待验证”的条目做最小复现或不可达证明。

**G. 文档修正**：评审稿附录 A 重新导出（链接丢失）；`docs/02-架构/Agent运行时架构.md` 中“Kernel 非 authoritative”与代码不符，同步更新。

## 3.2 交付物与退出条件

- 交付：现状调用链记录；三后端能力声明草表（按第 2 节四个维度，每项注明版本、平台、步骤、预期、实际、证据位置）；原型代码与协议录制；安全补证表；端口草案。
- 退出：能解释现有行为、知道各后端缺什么、能提出有依据的公共端口。不要求三个外部后端都稳定；某项未验证就记为“待验证”，不阻塞其他后端。

# 4 阶段 1：共享 Host 加固（与阶段 0 并行）

**目标**：在向外部后端开放 Host 业务工具之前，关闭共享 Host 的权限与进程问题。FoxBackend 内部问题归 FoxBackend 回归，不扩写成外部后端必须遵循的 Kernel 机制。

## 4.1 分级登记表

| # | 问题 | 机制 | 影响 | 归属 | 优先级 |
|---|---|---|---|---|---|
| 1 | `git_read` 经 Git 配置（`core.fsmonitor`、`textconv`）执行外部程序 | 已确认：GitRead 不需审批、不受只读阻断；`git diff` 只有 `--no-ext-diff` | 待复现：恶意配置如何进入授权项目、能否经已有工具写入 | 共享 Host | 冻结前 |
| 2 | 测试授权只绑参数，脚本与依赖可变 | 已确认：权限哈希只含工具输入，可会话级复用 | 取决于授权语义：是否让用户误以为只批准了固定代码 | 共享 Host + 产品 | 冻结前（先定语义） |
| 3 | `run_process` 继承全部环境变量 | 已确认：未 `env_clear`、无白名单 | 条件性：取决于环境中是否有凭证、子进程是否可信、有无外发通道 | 共享 Host | 外部后端开放前 |
| 4 | 子进程收尾无界 | 已确认：读到 EOF 才 join，无截止时间；子孙持管道时可挂起 | Windows 已有 `taskkill /T /F`（非 Job Object，失败被忽略）；非 Windows 只杀直接子进程 | 共享 Host | 冻结前 |
| 5 | Windows UNC 路径先访问后判越界 | 已确认：`canonicalize` / `exists` 在越界判断之前 | 待 Windows 验证：NTLM 是否实际发出取决于 SMB 与认证策略 | 共享 Host | 外部后端开放前 |
| 6 | 运行中补充消息只影响注入当轮 | 已确认：pi 0.84.2 continuation 用 `state.messages.slice()` 快照，Fox 改的是外层状态 | 同一次 continue 内后续工具轮可能丢失补充要求 | FoxBackend | FoxBackend 回归 |
| 7 | Host 工具失败在 pi 投影中变成 `isError:false` | 已确认：pi 对正常返回一律标 `isError:false` | 模型侧错误标记丢失；Host 持久状态不受影响 | FoxBackend | FoxBackend 回归 |
| 8 | 取消时未结算 pending Host 请求 | 已确认：`cancel` 只 abort，未 reject / clear | 局部 Promise 可挂起；整机永久卡死未证实 | FoxBackend + 公共语义 | FoxBackend 回归；公共语义见 6.4 |
| 9 | 续做权限可能比原任务宽 | 已确认：用会话当前 mode / root / grants 覆盖原 binding | 是否缺陷取决于产品契约 | 共享 Host + 产品 | 冻结前（先定契约） |
| 10 | Cancelling 不结束 / 终态未结算工具 | 复核不成立：`settle_cancellation` 与 `terminate` 均结算未终态工具，驱动循环见 `cancelling` 即结算 | — | — | 撤回；有新轨迹再重开 |

## 4.2 修复方向

1. **Git**：最小化 Git 配置与环境（如 `GIT_CONFIG_NOSYSTEM`、`-c core.fsmonitor=`、`--no-textconv`），不可信仓库考虑无钩子读取实现；回归覆盖只读模式和免审批路径。
2. **测试授权**：明确“这是项目代码执行授权”；默认一次性或绑定工作区修订，敏感入口变更时重新确认；配合真实沙箱。不以“只哈希 `package.json`”宣布完成。
3. **环境变量**：区分模型凭证、业务连接器凭证、普通工具环境，只传白名单；日志与输出脱敏。白名单不替代文件凭证保护和网络隔离。
4. **进程收尾**：Windows 用 Job Object，Unix 用进程组；管道读取设截止时间；覆盖“父进程正常退出、子孙仍持有管道”。取消超时只表示“已请求停止”。
5. **路径**：任何 `exists` / `metadata` / `canonicalize` 之前先判路径类别；默认拒绝 UNC、设备路径，仅放行明确授权的网络根目录；考虑重解析点。
6. **续做权限**：契约二选一，“原范围与当前授权取交集”或“经确认的新授权用于新的续做任务”；禁止静默扩大，权限缩小立即生效，旧凭证不继承。

## 4.3 回归用例（立即加入）

Git 配置辅助执行；参数相同但项目代码已变；环境隔离；后代进程持管道；UNC 前置判定；连续多轮 steering（检查注入后第 2、3 次模型请求）；工具错误投影（模型消息、事件、Host 持久状态三者一致）；取消时 pending Host 请求被结算或标“结果未知”。

## 4.4 退出条件

“冻结前”条目关闭，或有可验证的隔离措施并写明残余限制；“外部后端开放前”条目在对应后端合并前关闭。尚未证实的条目只补证据，不作为扩大重写的前置工程。

# 5 阶段 2：Fox + 公共基础

**目标**：建立三个分支共同的起点。FoxBackend 以薄封装适配端口，Fox 现有行为不变；第 6 节规则在本阶段定稿并冻结。

## 5.1 最小公共端口

探测（安装、版本、认证状态、能力）/ 创建或打开绑定会话 / 提交 turn / 订阅事件 / 答复反向请求 / 取消 / 恢复（能力项）/ 中途补充或排队输入（能力项）/ 关闭与资源清理。

- 同一会话单活动 turn；忙碌时新提交明确拒绝或进入可见队列，不悄悄解释为 steer。
- 能力用声明，不用“必选空方法”；每个方法明确错误与“不支持”返回值。
- 断线后不自动重提同一输入，先核实原 turn 状态。
- 现有 `KernelSnapshot`、`OutboxEffect`、`RunControlBinding`、`EnginePort` 带 Kernel 语义，不作为公共接口。

# 6 公共基础规则（阶段 2 冻结，三分支共同遵守）

## 6.1 执行拓扑

```
Fox UI
 └─ 公共 Host（Rust）
     ├─ 会话与运行记录、事件归一化与持久化、审计
     ├─ 授权快照、业务工具（MCP 窄接口）、知识库入口、产物验证
     ├─ 进程监督器：启动、健康检查、取消、进程树清理
     └─ AgentBackend 端口
         ├─ FoxBackend → 现有 Kernel（进程内 / 现有 Node worker）
         ├─ PiBackend → pi --mode rpc 子进程（stdio）
         ├─ CodexBackend → codex app-server 子进程（stdio）
         └─ DeepSeekBackend → dsh --profile acp 子进程（stdio，实验）
```

规则：

1. **一个活动会话对应一个原生进程**为默认拓扑。取消、崩溃、强杀只影响该会话；不共享进程，除非阶段 0 证明共享进程能做到按会话隔离取消与环境。若 Codex app-server 选择多 thread 共享进程，须单独评审并有“取消一个 thread 不影响其他 thread”的测试。
2. 每个原生进程由进程监督器以 Job Object（Windows）或进程组（Unix）启动，环境变量按白名单传入，工作目录为会话授权根目录。
3. Host 与原生进程之间每次重连或重启生成新的**连接代次**；旧代次的事件、反向请求、响应只用于审计，不进入当前状态。
4. 空闲会话的原生进程可回收；再次使用时按 6.6 规则重新打开（能力支持时恢复，否则新建并提示）。
5. 业务工具由 Host 执行，经 MCP 窄接口暴露给外部后端；原生进程不直接获得数据库、凭据或 Host 内部接口。

## 6.2 并发上限

| 维度 | 规则 | 建议初值（可配置，阶段 0 后定） |
|---|---|---|
| 单会话活动 turn | 1；忙碌时拒绝或可见排队 | 1 |
| 单会话排队输入 | 有上限，超限拒绝 | 待定 |
| 全局活动原生进程 | 上限，超限新会话排队并提示 | 待定（按内存实测） |
| 每后端活动进程 | 各自上限，防止单一后端占满 | 待定 |
| 单会话待决反向请求 | 有上限；超限视为异常并停止 turn | 待定 |
| Host 工具并发 | 沿用现有 `MAX_CONCURRENT_TOOL_HANDLERS = 32` 全局上限，另设每会话上限 | 每会话待定 |
| FoxBackend 子任务 | 沿用现有 depth / per-parent / concurrency 限制，不外推到其他后端 | 现值 |

所有上限命中都必须是可见状态（排队、拒绝并说明），不能静默丢弃或无限等待。

## 6.3 Agent 反向请求

外部 Agent 主动向 Host 发起的请求统一建模为 ReverseRequest，包括：原生审批（Codex 审批、DeepSeek `request_permission`、pi 扩展确认）、MCP 业务工具调用、扩展 UI 交互。

**字段**：请求 ID、原生请求 ID、后端、会话、run/turn、连接代次、类别、动作、资源、原生提供的选项、有效期、`decision_state`。

**状态机**：

```
pending → user_decided → response_written → native_acknowledged
pending → expired | cancelled | superseded
response_written → outcome_unknown（回执丢失、断线、进程退出）
```

规则：

1. 每个请求只消费一次有效答复；重复点击返回“已处理”，不代表原生已接受。
2. 只提供原生真正支持的选项；不发明“仅这次”“永远允许”等原生无法落实的粒度。
3. 答复发送途中断线、写入失败或无法确认是否送达，记为 `outcome_unknown`。原生协议没有确认机制时，状态停在 `response_written`，不得为走完状态机标成 `native_acknowledged`。
4. 取消、后端重启、会话关闭、超时、连接代次变化时，旧审批卡失效；只有原生协议可核实地重新发起同一请求时才重建可答复状态。
5. 状态变化持久化；重连不能让失效卡重新可用。
6. 答复送达不等于工具执行完成；原生工具成功事件也不等于 Host 执行收据。
7. `outcome_unknown` 不自动重发可能产生副作用的命令，先查询、对账或提示人工确认。
8. MCP 业务工具调用由 Host 按授权快照执行并留收据，逐次检查资源与外发范围。

## 6.4 取消、结果未知与晚到响应

**取消流程**：请求 → adapter 发送原生取消 → 等待原生确认或可验证的进程终止 → 记录终态。命令写入 stdin 或 `queued=true` 只表示请求被接收。

**pending 请求（Host 请求、反向请求、工具调用）的结算结果**：

| 结果 | 含义 |
|---|---|
| 成功 | 有执行方收据 |
| 失败 | 有明确错误 |
| 已取消 | 确认未执行或已中止 |
| **结果未知** | 可能已执行但回执丢失、断线或进程被杀；标“待核对”，保留关联 ID |

规则：

1. 取消或断线时，所有 pending 请求必须**离开等待状态**（结算为上述四种之一），不能永久挂起；不能把“结果未知”强行归入成功、失败或已取消。
2. **晚到响应**按关联 ID 与连接代次识别，持久保存，用于核对“结果未知”项和审计；不进入当前状态，不翻转已确认终态。
3. 每个 run 只接受一个权威终态；完成与取消同时到达时按有序、可审计规则裁决。取消已请求但任务先完成时，如实显示已完成并保留取消记录。
4. 强杀进程后，终态附“可能存在未核实副作用”标记；进程树按 6.1 清理。
5. UI 状态至少区分：运行中、等待审批、取消中、已完成、失败、已取消、连接中断 / 状态待确认。断线不显示为已取消。
6. 事件去重只保证展示和状态不重复，不保证副作用 exactly-once；涉及写入或外发的重试依赖执行方的幂等键、收据或可核对结果。

## 6.5 配置与环境优先级

从高到低，高层覆盖低层，冲突记入审计：

1. **Host 强制策略**：授权目录、外发策略、禁用后端、环境变量白名单、企业策略。任何下层不得放宽。
2. **会话冻结快照**：会话创建时冻结的后端、版本、授权快照引用、模型与关键设置。全局设置变化不影响已有会话。
3. **用户后端设置**：Fox 设置页中按后端命名空间保存的模型、推理强度、技能开关等。
4. **项目级配置**：项目内的 AGENTS.md、后端原生项目配置等；只能在 1–3 允许范围内生效。
5. **后端原生默认**：原生 Agent 自带配置与默认值。

规则：

- **冻结不等于永久保留权限**：权限撤销、企业禁用、安全策略收紧对已有会话立即生效；继续执行、恢复、续做前都按第 1 层重新检查，不满足则停止或只读。冻结只防止“放宽”被静默带入，不防止“收紧”。
- Host 不改写用户的原生全局配置文件，不复制、解析或迁移原生凭据；认证由原生 Agent 自己管理，Host 只读可用状态。
- 子进程环境 = 白名单变量 + Host 显式注入的会话变量；不继承 Fox 进程全部环境。
- 未支持的设置在 UI 禁用并解释；模型或配置不兼容时明确失败，不静默换模型或换后端。
- 技能含可执行脚本、网络访问或安装步骤时，按第 2 节四维度声明其边界。

## 6.6 身份字段与旧会话映射

**字段原则**

- 新增会话级 `agent_backend`（`fox | pi | codex | deepseek`），创建时写入、不可变。
- `engine_id` 保持现有含义与约束（`pi | codex | deepseek_harness`，表示 Kernel 内部使用的引擎适配），不改名、不重定义；FoxBackend 新 run 照旧写入。
- 不复用 `runtime_type` 表达外层后端（已与 `UNIQUE(conversation_id, runtime_type)` 绑定）。
- 日志与审计同时输出 `agent_backend` 与 `engine_id`。

**旧记录映射（迁移时一次性确定，不靠字段缺失推断）**

| 旧记录特征 | 映射 `agent_backend` | 恢复行为 |
|---|---|---|
| `kernel_mode = authoritative`，`engine_id = pi` | `fox` | 经 FoxBackend 照常恢复 |
| `kernel_mode = authoritative`，`engine_id = codex` | `fox` | 经 FoxBackend（Codex 模型适配）恢复；**不得**恢复成新的完整 CodexBackend |
| `kernel_mode = authoritative`，`engine_id = deepseek_harness` | `fox` | 经 FoxBackend（DeepSeek 模型适配）恢复；不得恢复成 DeepSeekBackend |
| legacy 路径（`FOX_KERNEL_MODE=legacy` 产生） | `fox`（标 legacy） | 只读展示；仅在 legacy 开关开启时按旧路径恢复 |
| 无法判断来源 | 不映射 | 只读展示，说明恢复受限，不启动任何运行时 |

**迁移规则**：只增不改；迁移前自动备份数据库并演练恢复；覆盖旧库副本、迁移中断后重试、旧 run 展示、Fox 旧会话恢复、新后端记录写入、关闭新后端后的读取。原生会话数据不写成 Kernel checkpoint；checkpoint 按后端与原生版本隔离。

**回滚**：首选功能开关关闭新后端，旧数据保持可读。现有协议普遍 `deny_unknown_fields`，旧二进制能否读取升级后的数据库须实测；在证实之前按“只能关开关、不能回退二进制”设计备份与发布步骤。

## 6.7 复用优先：以 ACP 作为公共端口

调研结论（2026-10-19，来源见附录 A）：同类产品（Zed、JetBrains、vibe-kanban 等）普遍用 Agent Client Protocol（ACP）一个协议接多家 Agent；Goose 维护者公开表示“把外部 Agent 包在自研 provider 接口后面”会形成两层 agent loop，取消、审批、steer、恢复都变复杂，已降级。这支持“一个会话绑定一个完整后端 + 标准协议”的做法。

| 部分 | 复用 | 许可证 | 备注 |
|---|---|---|---|
| Host 侧 ACP 客户端 | Rust crate `agent-client-protocol`（Zed 所用） | Apache-2.0 | 大版本变化快，锁定版本 |
| CodexBackend | `@agentclientprotocol/codex-acp`（内部启动 Codex app-server） | Apache-2.0 | 已支持审批、MCP 透传、`session/load`，steer 经私有扩展 `_session/steering`；不再自研 app-server 对接 |
| PiBackend | `pi-acp`（Zed 已收录） | MIT | MVP 阶段；支持 `session/load` 与取消；MCP 未真正接到 pi；工具是否映射到 `request_permission` 待原型确认 |
| DeepSeekBackend | 原生 `dsh --profile acp` | — | 支持 list / resume / close / cancel、MCP、一次性审批；不支持 `session/load` 与历史回放 |
| 参考实现 | vibe-kanban Rust executors（通用 ACP harness、进程组清理） | Apache-2.0 | 已停止维护，只参考，可摘抄并保留许可声明，不作依赖 |
| 不复制代码 | Toad、Claude Squad（AGPL）、Conductor（闭源） | — | 只看思路 |

ACP 规范与本方案的对应：`session/cancel` 后客户端必须以 `cancelled` 答复所有挂起的 `request_permission`，直接对应 6.4 第 1 条；`session/load`（回放）、`session/resume`（不回放）、`session/close` 须先读初始化声明的能力再调用，对应 6.6 与 T08。

**仍需 Fox 自研**：能力读取与 UI 降级；`request_permission` 到 Fox 审批卡与 fail-closed 规则的策略层；steer 降级（支持 `_session/steering` 用之，否则排队或取消后重发，明确提示）；进程树清理（ACP 不管进程，按 6.1）；`session/update` 到 Fox 事件模型的映射与扩展字段白名单；Windows 冒烟（npx 启动、路径、编码）。

对阶段的影响：阶段 0 的 B、C、D 改为“用现成 ACP 入口跑通”，原 Codex app-server / pi RPC 直连原型降为备选（ACP 入口不满足最低要求时才做）；阶段 2 的端口以 ACP v1 为基础，只补 ACP 缺的部分。

# 7 阶段 3：三分支并行接入，分批验收发布

**前提**：阶段 2 冻结完成。三个分支从同一冻结提交出发，使用同一端口与测试场景。

## 7.1 共同约束

- 每个分支只拥有：本后端 adapter、进程启动与协议处理、能力声明、专属设置 UI、后端测试。
- 不各自改 Host 状态机、数据库身份、公共审批卡、业务工具协议或第 6 节规则。
- 发现公共接口不足：提交带实例的变更请求，由公共层负责人统一修改、升版本、同步到三个分支。
- 不在 adapter 中重新实现通用 Agent loop。
- 每个分支交付：依赖版本、平台验证、能力声明（四维度）、已知限制、接入文档。

## 7.2 合并与发布规则

- **谁先通过第 8 节门槛谁先合并**，不要求同时发布、同时达到完整能力。
- 合并前须关闭第 4 节“外部后端开放前”条目。
- 每个后端独立功能开关；合并后默认关闭，内测通过再默认开放。
- 后合并的分支在合并前 rebase 到最新主线并重跑全部门槛（含已合并后端的回归），防止互相影响。
- 人手不足时退化为串行：先做阶段 0 结论更好的一个（Codex 或 pi），规则不变。

## 7.3 各分支重点

| 分支 | 交付物 | 重点 |
|---|---|---|
| pi | PiBackend（RPC）、扩展业务工具、会话与取消实测 | `agent_settled` 判定完成；扩展 `tool_call` 钩子审批覆盖；bash 子进程内部行为标“不可观测”；消除 `createFoxAgentSession` 与旧开关、Kernel 身份、UI 的耦合 |
| Codex | CodexBackend（app-server）、锁定版本 schema、thread / turn / 审批桥接 | 启动时校验 schema，不兼容拒绝启动；Windows 沙箱范围如实声明；fork 等能力先隐藏；现有 `codex-kernel-adapter` 仍属 FoxBackend 内部模型适配，不混称 |
| DeepSeek（实验） | DeepSeekBackend（ACP）、能力缺口、实验开关 | 标注官方“developer preview、未做安全审计、会有破坏性变更”；仅只读或受限目录；默认关闭；不设发布承诺 |

## 7.4 共同工作

- 业务工具以 MCP 窄接口暴露，逐后端验证审批、取消、授权与数据外发。
- 安装：只做版本探测与安装引导，不打包分发。
- 诊断：版本、路径、能力声明在设置页可见。

# 9 阶段 4：收敛

- **定 FoxBackend 长期定位**（首批外部后端发布后决定）：长期对等后端，或过渡兼容层（功能冻结只修缺陷，设退出条件，例如外部后端承担多数新会话且门槛持续通过）。

- 团队精力转回 UI 与业务流程；新需求先判断外部后端是否已具备。

| 模式 | 适用 | 边界 |
|---|---|---|
| `sandboxed`（默认） | 除明确授予 full_access 外的一切情况；旧会话未记录模式时一律按此 | 外部后端进程（codex-acp、pi-acp、dsh）整体在 srt（`@anthropic-ai/sandbox-runtime`，Apache-2.0）中运行，一个会话一个沙箱；只读写授权目录 + 私有 HOME + 运行所需系统目录；出站网络只放行该后端模型 API 域名白名单 |
| `full_access` | 用户按会话或项目明确授予 | 不套沙箱，不承诺目录边界；能力声明的沙箱两维为“无” |

两种模式下 Host 底线照旧：环境变量白名单与凭据不下发、取消与进程树清理、记录、原生审批如实转发。

**规则**

1. **fail-closed**：沙箱起不来、依赖缺失（srt、Node ≥ 22.12、Linux 的 bubblewrap/socat/ripgrep）、Windows 未执行 windows-install、策略无效、后端未装在沙箱可读的位置，一律拒绝启动该后端，返回结构化错误（`sandbox_unavailable` / `sandbox_not_installed` / `sandbox_dependency_missing` / `sandbox_policy_invalid` / `sandbox_backend_not_installed`），绝不自动退回 full_access。
2. **读默认放行需配置**：srt 读权限默认全放行，每会话配置必须先拒读用户目录根（`/home`、`/root`、`/tmp`；`/Users`、`/Volumes`；`C:\Users`；Host 可追加），再放行授权目录、私有 HOME、后端安装目录、Node 运行时与 srt 自身。
3. **只能收紧**（沿用 6.5）：域名白名单上限 = 后端默认 + Host 层追加；会话快照、用户、项目各层只能取交集收窄。full_access 只能来自“会话请求 + Host 持有的有效授予”，项目或用户配置不能单独开启；授予撤销对已有会话在下次继续前生效（停进程，按 sandboxed 重启，失败即拒绝）。
4. **私有 HOME**：后端的 HOME / CODEX_HOME / DSH_HOME / XDG / TMPDIR 指向 Fox 管理目录；Host 不复制用户真实 home 中的原生凭据。
5. **能力声明如实**：“沙箱范围”按模式与平台实测声明；Linux 已实测（T04 通过），macOS / Windows 在实测前声明为“待验证”，full_access 下不宣称目录隔离。
6. **Windows 按需安装**：用户首次选择沙箱模式时调用 srt `windows-install`（一次 UAC）；卸载 Fox 时调用 `windows-uninstall`。Windows 支持为 alpha，后端与 Node 须装在 Fox 管理目录（沙箱账户读不到用户目录中的工具）。

**已知限制**：Windows alpha；Windows 上代理令牌在 runner 命令行中可见；网络按域名过滤、不检查内容；macOS / Windows 尚未实测。
