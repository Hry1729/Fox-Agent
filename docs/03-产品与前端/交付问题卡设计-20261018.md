## 1. 问题与目标

### 1.1 现状

交付面板在「交付要求未识别」时，只在面板里渲染一行纯文本：

```tsx
// apps/desktop/src/features/chat/workbench.tsx:199
<p className="fox-delivery-review__question">
  {reason || '请明确要交付的文件名、类型或目录；当前没有可靠目标可自动修复'}
```

配套的顶部说明文字（`workbench.tsx:183-193`）把内部实现暴露在默认视图里：

问题有三类：

1. **只有陈述，没有回答入口。** 用户知道「需要补充」，但卡片里没有输入框，必须自己回到最底部输入框重新组织一句话，并且不知道什么样的句子会被重新识别。

3. **已知文件名时仍在问文件名。** 实测 Run `48bd173a` 同时存在 `file:merged.md`（`target_path=merged.md`，文件名已明确）与 `recognition:delivery_unresolved`，但界面只显示「请明确要交付的文件名、类型或目录」，让用户以为连文件名都没定。

### 1.2 目标

- 把顶部这段冗长提示改为**一张清晰的问题卡**，用户直接在卡片内输入并发送回答。
- 视觉复用现有决策卡 / 交付接受卡，但**业务语义必须区分**：补充信息 ≠ 工具审批 ≠ 交付接受。
- 默认只展示：当前真正缺少的信息、一句必要说明、输入框或适用选项、明确的发送动作、简短等待/执行状态。
- 已知文件名时，不再询问文件名。
- 不改变整体布局、主题与小狐身份。

### 1.3 非目标

- 不重新设计聊天界面整体版式。
- 不实现步骤级并行调度（当前不存在该能力）。
- 不修改 `freeze_concat` 的措辞规则（作为独立问题记录，见 §8）。
- 不改写旧冻结合同，不声称旧 Run 原地恢复。

## 2. 三类卡片的语义边界

这是本设计的核心约束：**可以共用外观，不能共用业务动作。**

| 卡片 | 用户在决定什么 | 主动作 | 提交到哪 | 后端含义 |
| --- | --- | --- | --- | --- |
| **补充信息卡**（本文） | 提供缺失的信息 | 发送回答 | 正常消息提交入口 → 新建后继 Run | 补充上下文，按新要求重新冻结并执行 |
| 工具审批卡 | 是否允许执行某动作 | 允许 / 拒绝 | 审批通道 | 授予或拒绝工具权限 |
| 交付接受卡 | 是否接受无法自动确认的产物 | 接受 / 拒绝 / 撤销 | `delivery_acceptance_resolve` | 记录或撤销交付接受 |

**硬性要求**：补充信息卡的回答**不得**调用 `delivery_acceptance_resolve`，**不得**调用任何工具授权接口。它走的是与底部输入框相同的发送路径。

当前代码里两条链路是分开的，设计要保持这个分隔：

- 提问/审批链：`FoxDecisionCard` → `onSubmitQuestion` → `resumeQuestion(parentRunId, …)`，带 `pendingRuntimeQuestion(runId) === parentRunId` 身份校验（`use-desktop-conversation.ts:1182`）。
- 交付接受链：`DeliveryAcceptanceCard` → `desktopClient.deliveryAcceptanceState` / `resolveDeliveryAcceptance`。

补充信息卡**不复用** `resumeQuestion`：那条链要求存在一个 `RuntimeQuestionRequest`，而 `recognition:*` 行并不是它。这也正是文档 §7.3 的要求——不能为复用外观而强行共用不同业务动作。

## 3. 用户流程

### 3.1 主流程（必填信息缺失）

```text
用户发起任务，提到要做文件但要求不足以冻结合同
        ↓
Run 停车，写入 recognition:delivery_unresolved
        ↓
问题卡出现：只问当前缺的那一项
        ↓
用户输入 → 发送（卡片内或底部输入框，同一入口）
        ↓
新 Run 以补充后的要求重新冻结 → 重新生成 → 重新核验
        ↓
问题卡折叠为「已回答」记录；旧 Run 的停车状态保留为历史
```

要点：

- **旧 Run 不原地恢复。** 旧冻结合同不改写，历史里仍然是「这次没识别出可核验对象」。
- **产品连续性与 Run 身份是两件事。** 用户看到的是一条连续对话；执行层是新的 Run。
- `recognition:*` 行**不会被继承到后继 Run**（`kernel_continuation.rs:549-556` 明确排除）。所以回答后不会出现「旧问题还在」的重复提示。

### 3.2 判定「真正缺少什么」

这是设计的难点，也是当前**能力缺口**。现状只有一个笼统原因码 `delivery.requirements_unresolved`，`stats` 为 `null`，前端无法可靠区分「缺文件名」还是「缺内容要求」。

因此设计分两层：

**当前可实现（只靠现有数据）**

| 已知事实 | 问题卡问什么 | 依据 |
| --- | --- | --- |
| 同 Run 存在 `file:*` 行且 `target_path` 非空 | 问**内容要求**，不问文件名 | `48bd173a`：`file:merged.md` / `target_path=merged.md` |
| 无 `file:*` 行，或 `target_path` 为空 | 问**目标文件名/类型/目录** | `recognition:*` 行 `target_path=null` |

**需要新增（见 §7 最小接口需求）**

后端在 `recognition` finding 里给出 `missing:` 结构化枚举（`target` / `content_requirement` / `source_selection`），并附带已识别的部分事实（已知文件名、已知目录、已知类型）。前端据此直接选中对应问题模板，不再靠推断。

**降级规则**：若新字段缺失，前端必须能够只显示一条中性问题（「这个任务还差一项必要信息」+ 输入框），**不得**编造具体缺失项，也不得把已知文件名又说成未知。

### 3.3 可选问题与跳过

**当前设计不提供「跳过」。** 理由：

- 现有协议没有「可选问题 + 默认行为」的表示方式，也没有非阻塞问题的通道。
- 文档 §5.4 明确：跳过只能用于后端明确支持默认行为的可选问题；必要信息不能靠前端加跳过按钮绕过。
- 在缺失的是执行前提时，跳过等于让用户以为可以不回答而继续，会制造错误预期。

**预留**：等后端出现显式的「可选 + 默认值」字段后，卡片才增加「按默认继续」动作。届时它是**独立动作**，不是「跳过必填」。

## 4. 状态表

| 状态 | 触发 | 卡片展示 | 可用动作 | 对应现有能力 |
| --- | --- | --- | --- | --- |
| **待回答** | 面板有 `recognition:*` 行且 Run 停车 | 标题「补充信息」、一句问题、输入框、发送按钮、等待说明 | 输入、发送 | 现有（但无输入框，需新增组件） |
| **输入中** | 用户已输入未发送 | 同上，发送按钮可用；空输入时禁用并就地提示 | 发送 | 需新增 |

| **已回答** | 后继 Run 已创建 | 折叠记录：问题 + 用户答案摘要 + 「已按补充要求重新执行」 | 查看记录 | 需新增（依赖 §7 关联字段） |
| **提交失败** | 发送调用失败 | 保留输入，显示错误，重试按钮 | 重试 | 需新增 |

说明：

- **已回答与已失效必须区分。** 「已回答」是成功路径的记录；「已失效」是提交被拒绝时的解释。两者的文案与动作都不同。
- **发送中不显示「取消」**：当前没有取消已提交消息的协议，给出按钮会变成假承诺。

## 6. 执行语义

### 6.1 必填信息缺失 → 相关执行等待

当前实现：停车 Run 停止派发模型与工具（`run.awaiting_delivery_review`）。这是准确描述，设计沿用：

> 等待你的回答后继续生成

不能说成「任务仍在后台继续做其他部分」——当前没有步骤级并行调度，那样画会误导。

### 6.2 可选问题 → 仅在有默认行为时不阻塞

当前**不具备**。设计中不出现任何「可选」或「跳过」形态，直到后端提供显式默认值字段。文档记录为新增需求（§7）。

### 6.3 沿用「发送补充消息 → 新 Run」

- 回答经由与底部输入框**相同的**提交入口，创建**新的** Run。
- 旧 Run 保持其原有终态；不修改其冻结合同。
- 新 Run 重新冻结合同（补充后的要求可能改变目标、来源或内容要求）。
- 旧产物可作为输入，但**不无条件继承**旧的核验结论或用户接受记录；需要按新规则重新绑定身份。
- **不声称旧 Run 原地恢复。**

### 6.4 与底部输入框的关系

**共用一个提交入口**

```
                  ┌──────────────────────┐
卡片内输入 ──────→ │  handleSend(text,    │ ──→ 创建新 Run
底部输入框 ──────→ │   {questionId?})     │
                  └──────────────────────┘
```

- 卡片输入与底部输入**调用同一个**发送函数（现有 `resumeQuestion` 之外的普通发送路径），保证两种入口产生完全一致的后继 Run。
- 区别只在**携带的关联信息**：卡片发送时额外带 `questionId`（原 Run + item key），普通聊天不带。这个关联用于：写入回答记录、折叠卡片、事件区分。

**关联原问题与 Run**

回答必须能回答「我在回答哪一个问题」：

| 需要的字段 | 作用 | 现状 |
| --- | --- | --- |
| `parentRunId` | 绑定原 Run，历史动作不串台 | 现有（`recognition` 行有 `run_id`） |
| `questionItemKey` | 绑定具体问题行 | 现有（`recognition:*`） |
| `conversationId` | 防跨会话误投 | 现有 |
| `answerMessageId` / 回答事件 | 已回答状态可读回 | **需新增** |
| 幂等键 | 防重复提交 | **需新增** |

**避免重复提交**

- 发送中禁用输入框与按钮（UI 层）。
- 提交入口按 `(conversationId, parentRunId, questionItemKey)` 做在途去重：同一问题在途时忽略第二次提交。
- 后端需要幂等键，使重复到达的同一回答不产生第二个后继 Run（§7）。

**避免误投到其他任务**

- 卡片提交时校验：该 `parentRunId` 是否仍是当前可回答的问题来源。若已被新 Run 取代或已终止，转「已失效」，**不发送**。
- 底部输入框的普通消息默认**不**关联任何问题（保持普通聊天语义）。文档 §7.3 的要求是「不能把任意一条聊天消息自动提交给所有问题」——因此不做「自动关联最近问题」的猜测。
- 若同会话存在多个待回答问题，卡片各自携带自己的 `questionItemKey`；不提供「一次回答全部」。

### 7.3 需新增（后端最小接口）

**A. 问题内容的可回答性（让卡片知道该问什么）**

```
recognition finding 增加（建议）:
  missing: "target" | "content_requirement" | "source_selection"
  known: { fileName?: string, directory?: string, extension?: string }
```

理由：现状 `reason` 是单一固定文案、`stats=null`，前端无法判断该问文件名还是内容要求。**不新增此字段时，前端只能显示中性问题**（§3.2 降级规则），不能假装知道。

**B. 回答的身份与幂等**

```
submit_answer:
  输入: conversationId, parentRunId, questionItemKey, answerText, idempotencyKey
  输出: childRunId（或重复提交时返回既有 childRunId）
  校验: 该问题仍属于当前任务且仍可回答；否则拒绝并给出可解释原因
```

理由：文档 §7.1 的 5 条要求（仍属当前任务、仍可回答、重复不建重复续作、先保存再执行、可读回）目前只有部分满足。

**C. 已回答/已失效的读回**

```
问题行增加: answeredAt, answerMessageId, childRunId, invalidatedReason
```

理由：前端重新进入页面后要能恢复「已回答 / 等待 / 失败」，否则只能靠内存状态，刷新即丢。

**D. 撤销状态的可见性（承接 §8.2）**

```
delivery_acceptance_state 增加: revokedAt: i64 | null, revokedReason: string | null
```

理由：数据库已存 `revoked_at` / `revoke_reason`（样本 A 实测 `revoked_at=1792308314957`），但 `AcceptanceState`（`delivery_u1.rs:372-380`）只投影 `accepted` / `rejected` / `run_terminal`，**没有 `revoked`**。前端因此无法区分「已撤销」与「从未决定」。

**E. 旧 Run 的历史查看**

```
delivery_history(conversationId): 按 Run 分组的交付记录
  每项: runId, itemKey, description, verificationClass, acceptance(状态+时间+actor), childRunId?
```

理由：见 §8.3。现状 `conversation_load` 只返回 `lastRun` 的清单（`delivery_checks.rs:147-151` 按单 Run 取行），后继 Run 出现后旧 Run 的接受记录在 UI 上不可达。

- 不为复用卡片外观而把回答接到接受或工具授权接口。
- 不在前端伪造 `revoked` 状态。
- 不扩展后端能力到「步骤级并行调度」。
- 不修改 `freeze_concat` 规则。

## 8. 已发现的状态问题

### 8.1 四种接受状态必须分别表达

现状 `DeliveryAcceptanceCard` 只区分 `accepted` / `rejected` / 其他（`accepted === null` → 「未决定」）。因为缺少 `revoked`，**已撤销会显示成「未决定」**，等于把历史写成「从未接受过」。样本 A 撤销后的 UI 实测就是「当前接受 未决定」——语义上损失了「这里曾经接受过、后来撤销」这个事实。

设计要求：

| 状态 | 判据 | 展示 | 动作 |
| --- | --- | --- | --- |
| **有效接受** | `accepted != null && revokedAt == null && rejectedAt == null` | 「已接受（window:main）」+「这不是核验通过」 | 撤销接受 |
| **已拒绝** | `rejectedAt != null` | 「已拒绝」 | 无（当前协议不允许对已拒绝项再接受） |
| **已撤销接受** | `revokedAt != null` | 「已撤销接受」+（可选）「撤销于 <时间>」 | 无；若 Run 仍可决定则不在此列 |
| **从未决定** | 三者皆空 | 「未决定」 | 接受 / 拒绝 |

**文案修正（必须）**：面板副文案「你此前的接受仍在，可以逐项撤销」（`workbench.tsx:191`）在**已拒绝**项上不成立。改为按实际状态分支：

- 有可撤销接受 → 「你此前的接受仍在，可以逐项撤销；任务不会因此重启或重跑。」
- 只有已拒绝/已撤销项 → 「该任务的核验结论保留原样；任务不会因此重启或重跑。」
- 无任何接受记录 → 不显示该副文案。

### 8.2 「已撤销」不得写成「从未接受」

如上。这是数据投影缺口（§7.3 D），不是纯文案问题：必须在 `AcceptanceState` 增加 `revokedAt` 才能正确表达。在前端猜测（例如用 `accepted==null && rejected==false && runTerminal` 推断「可能撤销过」）是错的——「从未决定但 Run 已结束」也是这个形状。

### 8.3 后继 Run 出现后旧接受记录不可见

**问题**：`conversation_load` 的 `deliveryChecklist` 只覆盖 `lastRun`（`delivery_checks.rs:147-151`：`WHERE r.conversation_id=?1 AND i.run_id=?2`），前端面板用 `deliveryRunId = detail.lastRun.id`。一旦产生后继 Run，`lastRun` 指向新 Run，旧 Run 的清单不再返回，面板因无数据而整体消失。样本 A 之后我发了一条普通消息就复现了这个现象。

注意：这不是迁移引入的缺陷，候选实现逐字相同（候选 `workbench.tsx:6006` 同为 `lastRun?.id`）。但它是真实的可用性缺口，用户会「找不到自己刚做过的接受」。

**设计要求：明确的历史查看入口**

- 位置：交付面板底部固定入口「查看历史交付记录」（有历史时始终可见，不依赖 `lastRun` 是否有清单）。
- 内容：按 Run 倒序列出，每项显示 Run 时间、产物名、核验结论、接受状态与时间、以及是否为当前 Run。
- **历史动作必须绑定原 Run**：撤销只能作用于该记录自己的 `runId` + `itemKey`，不能作用于「当前 Run」。
- 进入历史视图时不改变主对话的当前 Run 选择。

**最小接口需求**：§7.3 E（`delivery_history(conversationId)`）。在此之前，前端**不得**用 `lastRun` 冒充历史，也不得把旧记录显示成当前记录。

### 8.4 `freeze_concat` 措辞敏感性（独立问题，不在本设计修复）

**现象**：合同冻结对任务文本的字面形式高度敏感。实测四种措辞才成功：

| 措辞 | 结果 | 原因 |
| --- | --- | --- |
| `md 文件` | `unbound` | 要求字面 `\.(txt\|md)\s*(?:文件\|的文件)` |
| `.md 文件` + `把 "sources" 目录` | `unbound` | 要求 `在 "dir" 目录` 形式 |
| `.md 文件` + `在 "sources" 目录` | **`concat`（v2）** | 通过 |
| 合并子句在逗号后 | `unbound` | `sentence_tail` 以 `，` 等为句末，会截断 |

**处理原则**：

- 作为**独立问题**记录，归属「识别层措辞鲁棒性」，不在问题卡设计内修复。
- **不靠前端文案宣称已修复**：问题卡不得写「已支持各种说法」「自动识别你的意图」。
- 问题卡能做的是：在识别失败时问得清楚、让用户一次答对；这改善的是**交互**，不是识别能力。
- 若要缓解，正确做法是在后端放宽 `freeze_concat` 的文本匹配（或提供结构化输入），需要独立评估与验收。

## 12. 结论

- 顶部冗长提示应替换为**问题卡**：只问当前真正缺少的信息、一句说明、输入框、明确发送动作、简短状态。
- 视觉可复用现有卡片，但**业务动作必须独立**：回答走正常发送入口 → 新 Run，绝不接交付接受或工具授权。
- 「发送补充消息 → 新 Run」语义沿用；旧 Run 不原地恢复，旧合同不改写。
- 三种已知状态问题分别设计：四态接受表达（需 `revokedAt`）、已拒绝不提示「接受仍在」、后继 Run 后提供绑定原 Run 的历史入口（需 `delivery_history`）。
- `freeze_concat` 措辞敏感性作为**独立问题**记录，不以文案掩盖。
- 当前可交付第一步（纯前端）；第二步依赖 5 项最小后端接口。
