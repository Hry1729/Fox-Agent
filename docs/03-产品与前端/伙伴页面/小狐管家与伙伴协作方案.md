## 1 结论

1. 小狐是 Fox 的管家，对应 OpenMausBot 里 MausBot 和 Chief of Staff 两个角色的合体：用户有事先找小狐，小狐自己做，或者交给合适的伙伴，没有合适的就新建一个。
2. 能力分三期：
   - P0 管家能力：小狐能查看所有伙伴、新建伙伴、修改其他伙伴的名称/职责/模型、提议删除伙伴。
   - P1 伙伴协作：伙伴之间可以派活和咨询，结果自动回到发起方；工作页可以 @伙伴。
   - P2 群聊和外部能力：本轮补充实施方案，见第 6 节。
3. **复用原则：凡是 OpenMausBot 已经做好的能力，直接复用它的实现，不自己重新设计、重新写。**具体规则见第 2 节，每项能力的复用来源见第 4、5 节。
4. 小狐始终置顶，不能取消置顶、归档、删除或隐藏。界面规则见《伙伴页面方案》。

## 2 复用 OpenMausBot 的规则

OpenMausBot 仓库：<https://github.com/milind-soni/OpenMausBot>。本机只读副本的位置见《伙伴页面方案》第 12 节。下文的 OpenMausBot 路径都相对于它的仓库根目录。

### 2.1 怎么复用

1. **先找 OpenMausBot 的对应模块。**有就照搬：工具名的含义、参数、工具描述、提示词、数值上限、状态机、拒绝文案和测试用例都按原样移植，只改三类东西：Fox 的命名（bot → 伙伴）、中文文案、Fox 已有的权限和数据模型。
2. **纯函数、提示词、界面组件直接拷贝改编。**
   - 提示词和纯函数（花名册渲染、状态推导、文本清洗、委派信封、重复检测）放进 Agent Runtime（`services/agent-runtime/src/*.mjs`）。这个目录是纯 JavaScript，没有 TypeScript 构建，拷贝时去掉类型标注即可。先例：`companion-memory-prompt.mjs` 改编自 Rakazo。
   - React 组件拷进 `apps/desktop/src/features/companions`，样式换成 Fox 的 `--fox-*` token。
3. **涉及状态、权限、审批、用量的逻辑，按 OpenMausBot 的代码逐段翻译成 Rust。**Fox 的架构规定 Agent Runtime 不能写数据库、不能绕过审批（`docs/02-架构/Agent运行时架构.md`），所以这部分不能直接运行 OpenMausBot 的 TypeScript。翻译时保持它的状态、分支和上限不变，测试也从它的测试文件翻译过来，不另行设计。
4. **偏离 OpenMausBot 必须写明原因。**本方案里的偏离都列在第 7 节。实现时如果发现新的必须偏离之处，先补进第 7 节再写代码。
5. 不要求复用的部分：OpenMausBot 的入口文件 `server/index.ts`（近 1.5 万行，处理函数和它自己的存储、团队云状态绑在一起）。处理函数的逻辑照着翻译，但不整体搬运。

### 2.2 许可和署名

- OpenMausBot 主体是 Apache-2.0，与 Fox 兼容。**`enterprise/` 目录是单独的企业许可，禁止复用**，包括通过 `server/enterprise.ts` 接进来的部分。
- 仓库里已有 `third_party/openmausbot/`（`LICENSE`、`NOTICE`、`FOX-PORT.md`）。每移植一个文件，都在 `FOX-PORT.md` 记下：来源文件、来源提交 SHA、改了什么、哪些没有采用以及原因。改编过的 Fox 文件开头写一行来源说明，格式同 `companion-memory-prompt.mjs`。
- 开工前固定一个 OpenMausBot 提交 SHA，并再次确认 `LICENSE` 仍是 Apache-2.0。
- OpenMausBot 和 MausBot 的名称、吉祥物是商标，Fox 的界面和提示词里不能出现这两个名字。

## 4 P0：管家能力

### 4.1 小狐的身份和提示词

| 内容 | 复用来源 | Fox 落点 |

| 管家人设：帮用户用好 Fox，回答“怎么做”，帮忙建伙伴和定时任务，被问“在忙什么”时概括各伙伴、定时任务和待处理事项 | `server/system-prompt.ts` 的 `MAUSBOT_PERSONA` | 译成中文，放进 Agent Runtime 新模块，例如 `services/agent-runtime/src/companion-team-prompt.mjs`，由 `prompt-composer.mjs` 作为独立分段加入，只给默认伙伴 |

| 首次问候后的一次性跟进（根据有没有模型、有没有伙伴和定时任务说一句话） | `server/helper-followup.ts`、`shared/helper-followup.ts` | P1 |

“Fox 怎么用”的回答：OpenMausBot 没有帮助文档库，只靠人设提示词。Fox 同样先只靠提示词，是否接入帮助资料库列为待决事项。

- 复用 `server/default-bot.ts` 的 `defaultBotRefusal` 和 `defaultBotPatchRefusal`：对默认伙伴的删除、归档、取消置顶请求一律返回固定的拒绝文案，告诉用户为什么不行。
- Fox 现有的 `companion.default_not_deletable` 错误保留，归档和取消置顶补上同类错误。

### 4.5 修改其他伙伴：`companion_propose_profile`、`companion_propose_model`

- 复用 `propose_profile`、`propose_model` 和 `server/profile-requests.ts`：立即生效，对话里显示“已修改 · 撤销”卡片，卡片列出改动前后的值。
- 可以改名称、职责、工作要求和模型。不能改权限和授权，授权仍然只能由用户在伙伴资料里改。这条来自 OpenMausBot 的 `APPLIED_RESULT_PROMPT`：“完全访问不会给另一个伙伴更大的权限”。
- 落点：调用现有的 `edit_companion`、`set_companion_model`。只给小狐；目标不能是小狐自己，小狐改自己仍然用现有的 `companion_profile_update`。

### 4.6 删除伙伴：`companion_propose_deletion`

- 复用 `propose_bot_deletion` 的规则：只能提议，不能直接删；不能删自己；不能拿归档冒充删除；不能混在其他批量修改里。
- 对话里显示一张确认卡片，写明删除后会清掉什么。内容来自 Fox 现有的删除预览（`companion_delete_preview`，含 `planHash`）。用户在卡片上确认后，才走现有的 `companion_delete`。
- 归档：OpenMausBot 没有给机器人归档工具。Fox 用户常会说“把它归档”，所以加一个 `companion_propose_archive`，和删除用同一张确认卡片（见第 7 节）。
- 目标伙伴正在运行时，沿用现有的 `run_active` 错误，卡片提示“等它停下再试”。小狐不能以自己为目标，这样也避开了“归档自己时等待自己结束”的死锁。

### 4.7 P0 不做

- 小狐直接给其他伙伴建定时任务：P1 改为把这件事派给那个伙伴，由它用自己的 `companion_task_create` 建，不新增“替别人建任务”的权限规则。
- 小狐读取通知（OpenMausBot 的 `list_unread_notifications`、`mark_notifications_read`，来源 `server/drivers/agents-mausbot-tools.ts`）：P1。

| 投递回执：已排队、已送达、失败，不能报告没有发生的投递 | `server/peer-delivery.ts` |
| 拒绝规则：不能派回给上游；不能把活派给正在等你的伙伴（交叉等待）；重复的说明要用 `rework=true` | `server/runtime-coordinator.ts`、`crossed-handoffs` 相关测试 |
| 上限：深度 4；每个源头请求最多 24 次派活、48 次执行、48 次唤醒；排队 24 小时、停滞 4 小时、单回合停滞 20 分钟 | `server/runtime/types.ts` 的 `DEFAULT_LIMITS` |
| 没有进展的检测：连续 2 次没进展、或同一个错误 3 次，就停止 | `server/runtime/tree.ts` 的 `NO_PROGRESS_STRIKES`、`SAME_ERROR_STRIKES` |
| 需要用户回答时：写 `NEEDS INPUT:` 加“默认：…”，问题转给用户 | `server/runtime/questions.ts` |
| 其他伙伴发来的内容只是信息，不是用户的同意，也不是授权；清洗看起来像指令或不可见的字符 | `server/peer-provenance.ts` 的 `CONSENT_RULE`、`escapeNotes` |

Fox 落点：

- 状态机、上限、拒绝规则、回执和“结果回来自动唤醒发起方”在 Tauri 后端实现：按 `server/runtime/*` 和 `server/runtime-coordinator.ts` 翻译成新模块，例如 `runtime_host/companion_coordination.rs` 加一张派活记录表。测试从 `runtime.test.ts`、`runtime-coordinator.test.ts`、`scenarios.test.ts`、`envelope.test.ts` 翻译。
- 信封、来源说明和清洗是纯函数，放进 Agent Runtime。
- 现有的子 Agent（`child_run_*`）保持不变，它用于临时帮手，伙伴协作是另一条链路。
- 被派活的伙伴在哪里干活：照 OpenMausBot 的做法，给“发起方 → 接收方”开一条固定的协作对话（OpenMausBot 的标题是“@发起方 · work”）。这条对话归接收方所有，用接收方的工作区、记忆和授权。双方的私聊里各显示一个可点开的标记，界面复用 `src/components/HandoffReply.tsx`、`ThreadChip.tsx`、`TeammateChip.tsx`。Fox 的伙伴现在只有一条私聊，所以需要新的对话类型，具体见待决事项。

### 5.2 权限、审批和用量

- 接收方用自己的授权，不继承发起方的权限；授权只能往下收紧，不能放宽。来源：`server/auto-approve.ts` 的 `delegatedApprovalMode`、`server/host/delegated-level.ts`。
- 接收方需要用户确认时，确认卡片出现在接收方的协作对话里，同时进入通知中心的“需要处理”。不能由发起方代替用户确认。
- 用量算在发起这件事的根运行上；如果根是定时任务，就计入那个任务的当日上限。来源：`server/usage-attribution.ts`，Fox 现有的按 `root_run_id` 汇总可以直接扩展。
- 接收方只看到信封，看不到发起方的私聊和记忆。来源：`server/runtime/envelope.ts`，以及 `session_search` “不含其他伙伴的私有记录”的规则。

### 5.3 所有伙伴都能找伙伴

- 照 OpenMausBot：每个伙伴都能用 `companion_list` 和 `companion_coordinate`，提示词用 `peerRosterSystemPrompt`（伙伴是同事，不是下属；只有真正需要时才找人；新建伙伴要找小狐）。小狐用 `chiefOfStaffSystemPrompt`。
- 新建、修改、删除其他伙伴的工具仍然只给小狐。

### 5.4 工作页 @伙伴

- 《伙伴页面方案》4.4 节说 @伙伴“另写方案”，这里定下来：用户在工作页的对话里 @某个伙伴，就是请当前对话把这件事派给它。独立的活用 `companion_coordinate`，问题用 `consult: true`。
- 提示词来自 `server/system-prompt.ts` 的 `mentionPrompt`。
- 普通对话不是伙伴，派活记录的发起方记为这条对话。

### 5.5 小狐处理其他伙伴的失败

- 复用 Chief of Staff 的“待处理问题”规则：其他伙伴的定时任务失败时，通知小狐；小狐可以重试，同一件事最多重试 2 次，或者用修正后的说明重新派活；只有用户能解决时，直接说明并停下。
- 来源：`chiefOfStaffSystemPrompt` 的事件处理段落、`retry_thread`、`server/host/chief-notices.ts`。

## 6 P2 实施方案

P2 本次交付方案。待确定实施范围后，依次落地历史搜索、本地条件等待和群聊。各阶段可单独验收。代码复用以 OpenMausBot 提交 `1a4e4da9f380804ad98c7fd1b141bb0dbfafced4` 为准，沿用第 2 节的许可和署名规则。工具形状复用上游，Tauri Host 负责数据、权限和持久化，Agent Runtime 负责工具定义和提示词。

### 6.1 搜索自己可见的历史

- 适配 `session_search` 的查询和按 ID 读取两种用法。查询接收关键词和可选时间范围，返回命中片段、日期和会话及消息 ID。读取接收命中的会话和消息 ID，按上游上限返回最多 8,000 字符。使用 `server/message-search-query.ts` 的查询方式和 `server/cjk-search.ts` 的中日韩分词、命中定位和片段清理。
- Host 从当前运行确定搜索主体。伙伴可查自己的私聊、收到的协作记录和已获准读取的记忆。普通工作对话按自己的会话和已授权范围查。群聊上线后，只纳入当前仍可访问的群聊。查询和按 ID 读取都检查归属及授权，发起方的私聊和记忆仍对接收方隔离。索引跟随 SQLite 消息增删和迁移，授权撤销后查询和旧 ID 均失效。结果按来源数据交给模型。
- 验收覆盖混合中文、英文和标点的检索，点击命中打开原消息，以及删除消息后的索引同步。同时验证另一伙伴的私聊、已撤销的共享记录和越权 ID 均不可读。用真实数据库验证升级前的消息也能检索。

### 6.2 本地条件等待

- 适配 `wait_until` 与 `server/waits.ts`。先支持自己工作区内的文件出现、消失或变更，以及可见伙伴从忙转为空闲。输入包含条件、时限和可选后续要求。创建后返回等待记录和状态，用户可在原会话查看及取消。
- Host 保存来源会话、条件、文件初始状态或伙伴忙闲、到期时间、下次检查时间及结案结果。复用现有调度和通知入口，达到条件后先记录结果，待原会话可运行时唤醒一次。基准上限沿用上游的每伙伴 10 项、全局 50 项。文件检查沿用工作区路径权限。周期检查和唤醒时都按当前权限执行，授权撤销或目标伙伴被删除后停止。
- 验收时验证工作区内的文件变更和伙伴由忙转闲各唤醒一次，重启后恢复时限和检查状态，到期、取消、撤权各产生可区分的结果。队列和重复请求行为与上游测试一致。URL 正文变化和进程状态等条件待其权限范围确定后再接入。

### 6.3 群聊

- 适配 `post_to_room` 和 `manage_room`。前者向自己所在群聊发出一条通知并返回投递结果。派活和咨询仍用 P1。后者由小狐按用户要求创建群聊、维护成员和群资料。群内 @成员优先按确切目标路由，其余消息按 `server/decider/room-routing.ts` 在可见成员中选择发言人。匹配不到合适成员或路由超时时，按群聊设置使用默认回应者。使用 `server/room-queue.ts` 安排发言顺序，按 `server/room-reply.ts` 将只有 `(pass)` 的答复记为跳过。
- 新增明确的群聊归属，Host 保存群成员、话题、消息来源、发言队列和投递回执。群成员读取群聊内容时不扩展私聊、工作区、记忆或工具权限。群公告和成员发言保留来源，不能作为用户审批。将 `server/room-post-budget.ts` 的重复检测、频率上限、交叉循环和熔断规则接到 Host 的发言入口。
- 验收时验证指定成员正确回应，单独通知不会触发其他成员运行，只输出 `(pass)` 时界面无消息，多个回应按队列投递，重复发言和循环会被停止。移除成员后用旧房间 ID 读写应被拒绝。重启后队列和回执应能恢复。

### 6.4 外部能力待定

Webhook、应用事件、外部账户连接、网页登录及桌面和浏览器操作需分别确定服务、数据读取范围、触发来源、权限和交互确认方式。外部事件若纳入实施，按来源可追溯、触发可取消和外部输入无审批效力的规则设计。账户授权和登录由用户按所选服务的实际界面确认。当前交付范围为本地方案，外部操作、额外工具和依赖留待范围确定后评估。

## 7 与 OpenMausBot 不同的地方

| 项目 | OpenMausBot | Fox | 原因 |
| --- | --- | --- | --- |
| 隐藏默认伙伴 | 可以隐藏 MausBot | 不能隐藏小狐 | 小狐是总入口，藏起来用户就找不到了 |
| 名称规则 | 最多 80 字，重名只警告 | 1 到 40 字，活动伙伴不能重名 | Fox 数据库已有唯一约束和长度检查 |
| 归档 | 没有归档工具，提示词禁止拿归档冒充删除 | 加 `companion_propose_archive`，和删除用同一张确认卡片 | Fox 有归档功能，用户会直接要求归档 |
| 部门、团队云、多人共享 | 有，权限按部门和所有者划分 | 没有，Fox 是单用户 | 只移植单人场景用得到的部分，部门相关的分支删掉 |
| 引擎能力判断 | 引擎不支持委派时提示换引擎 | 不需要 | Fox 只有一个 Agent Runtime |
| 子 Agent | 用自己的委派体系 | 保留 Fox 现有的 `child_run_*`，伙伴协作另走一条链路 | 子 Agent 已有归属、预算和验收，不能回退 |
| 伙伴状态 | `activity` 包含 `no-signal` | 使用 Fox 已保存的运行、待确认、工作区和模型状态；暂不产生“没有响应”状态 | Fox 还没有对应的伙伴心跳信号，不能将耗时较长推断为没有响应 |
| 协作对话类型 | 独立的派活线程 | 通过 `companion_coordination_threads` 标记协作对话并解析接收方归属 | 保留现有 `conversation_kind` 的主对话与子运行约束，普通对话列表跳过协作对话 |
| 模型标识 | 模型名称 | 支持模型名称，并保留 Fox 的 `providerId` / `modelRef` 精确选择；重名时要求精确指定 | Fox 允许多个模型服务使用相同模型名 |
| 操作结果 | 上游请求对象 | Host 工具返回执行结果及实际改后值；卡片完整前后值和删除清单通过桌面命令读取 | 沿用 Fox 的模型工具结果与用户界面数据边界 |
| 通知已读 | 区分普通通知和待处理问题 | 小狐工具只将 `completed` 通知标为已读，保留失败、问题和其他类型 | Fox 的通知类型不同，避免自动清除仍需用户处理的事项 |
| 历史失败任务 | 按上游事件入口通知管家 | 自动处理仅覆盖升级到 v118 后的失败任务 | 避免升级后自动重试旧失败记录；历史记录仍可查看 |
| 首次跟进 | 按引导状态产生跟进 | 依据已保存的模型、伙伴和定时任务状态生成一次性系统消息 | 不额外调用模型，不承诺尚未配置的外部能力 |

## 9 验收

P0：

- 小狐被问“伙伴们在忙什么”，能列出每个伙伴的状态，并点出等你确认的事项。
- 对小狐说“帮我建一个整理周报的伙伴”，伙伴页立即出现新伙伴，对话里有“已新建 · 撤销”卡片，点撤销后伙伴消失。一回合要建第 5 个时被拒绝。
- 让小狐改另一个伙伴的名称或模型，立即生效，可以撤销；改权限被拒绝。
- 让小狐删除或归档一个伙伴，出现确认卡片；不确认就不执行；目标正在运行时给出提示。
- 让小狐删除、归档自己或取消自己的置顶，都被拒绝。
- 其他伙伴调用不到新建、修改、删除伙伴的工具；子 Agent 也调用不到。
- 移植自 OpenMausBot 的测试（`peer-roster.test.ts`、`default-bot.test.ts`、`team-setup-requests.test.ts`、`profile-requests.test.ts` 中适用于单人场景的用例）翻译后通过。

P1：

- 小狐把一件事派给数据伙伴，结束本回合；数据伙伴完成后，小狐自动继续并给出汇总，中间不需要用户操作。
- 咨询只得到回答，不产生文件改动。
- 派回上游、交叉等待、超过深度和次数上限都被拒绝，拒绝原因写清楚。
- 接收方需要确认时，用户在通知中心和协作对话里都能看到；发起方不能代为确认。
- 定时任务里派出的活，用量计入该任务的当日上限。
- 接收方看不到发起方的私聊和记忆。
- 工作页 @伙伴 能派活，也能提问。
- 移植自 OpenMausBot 的协作测试（`runtime.test.ts`、`runtime-coordinator.test.ts`、`scenarios.test.ts`、`envelope.test.ts`、`peer-provenance.test.ts`、`peer-delivery.test.ts` 中适用的用例）翻译后通过。
