# 助手 / 知识模式切换延迟：实测根因与候选方案

> 状态：维护中
> 适用版本：Fox 0.1.x
> 维护范围：`apps/desktop/src/features/chat/`（侧栏与 Workbench）
> 最后更新：2026-10-14

## 结论

“助手 / 知识”切换时的卡顿来自 **一次 React 提交**，这次提交同时完成两件事：把侧边栏主体整棵拆掉重建，并把主内容区从一种页面换成另一种。提交的全部代价是 JavaScript 执行，不是样式计算或布局。进度指示胶囊与页面内容属于同一次提交，因此不存在“先动胶囊、后换页面”的可能。

**正式版本已实测无阻塞**：切换的点击到绘制约 35–43 ms，主线程阻塞 0 ms。开发服务器上观测到的 104–127 ms 阻塞，主要来自 `<React.StrictMode>` 在开发模式下双跑渲染与副作用，这部分代码不会进入发布产物。

因此当前决定：**不改源码**。本文件记录根因与三个候选方案，供后续需要优化手感时取用。本次排查未留下任何源码改动。

## 现象

- 切换两个方向都可复现一次明显停顿，发生在点击后、页面与胶囊一起变化的瞬间。
- 两个方向代价不同：切到“知识”较轻，切回“助手”较重。原因是对话线程在知识模式下不在 DOM 中，切回时需要重新挂载。
- 用户感知为“切知识很丝滑，切回助手卡半天”。这个不对称是真实的，不是错觉。

## 实测数据

测量环境为 Windows 开发机，Chromium，对同一实例分别测开发服务器与已构建的 `dist`（由本地静态服务提供）。

| 指标 | 开发服务器 | 正式构建 |
| --- | --- | --- |
| 点击 → 绘制 | 128–191 ms | 35–43 ms |
| 主线程阻塞 | 104–127 ms | **0 ms** |
| 胶囊与页面时序 | 同一时刻 | 同一时刻 |

切换一次的长任务归因（LoAF）：

```
dur = 183 ms   blocking = 127 ms
styleAndLayout = 2 ms   render = 3 ms
script = 159 ms (其中 forced reflow = 23 ms)
```

脚本占 159 ms，样式与布局合计 2 ms，说明瓶颈是 JS 执行而非渲染。

提交阶段耗时（CPU profile，含自身与子节点）：

| 阶段 | 含子节点耗时 |
| --- | --- |
| `commitDeletionEffectsOnFiber` | 240 ms |
| `commitLayoutEffectOnFiber` | 1030 ms |
| `commitPassiveMountOnFiber` | 609 ms |

开发模式的额外开销（不进入发布产物）：`recursivelyTraverseAndDoubleInvokeEffectsInDEV` 自身 247.8 ms、开发版 `jsxDEV` 自身 61.4 ms、GC 94.3 ms。这三项解释了开发与正式之间的大部分差距。

方向不对称（开发服务器）：

| 方向 | 点击 → 胶囊 | 主线程阻塞 |
| --- | --- | --- |
| 助手 → 知识 | 135 ms | 88 ms |
| 知识 → 助手 | 175 ms | 121 ms |

## 根因

切入任一模式都会让侧边栏走一条完全不同的渲染分支。当前实现下，分支切换被写成条件渲染，于是 React 不是复用节点，而是**卸载一棵子树再挂载另一棵**。与此同时 `activeView` 变化把主内容区也换掉。两件事落在同一次提交里，胶囊的选中态也由同一次渲染计算，所以三者同时出现。

可以用一句话概括：这不是等待框架或资源，而是这一帧要干的活儿本身就多。

## 已验证排除的假设

| 假设 | 结论 | 依据 |
| --- | --- | --- |
| 懒加载分块未就绪，边界挂住了整次提交 | **不成立** | 新挂载的 `<Suspense>` 边界不会阻塞整次提交。实测同级内容在 +2.8 ms 提交、fallback 在 +3.2 ms 出现、懒加载内容在 +1202.9 ms 到达。fallback 是新边界的初始状态，不是等待 |
| 切换在等图标动画结束 | **不成立** | 图标事件处理全部是即发即忘，只调 `startAnimation` 后返回，没有任何一处 await 动画 |
| 布局 / 样式重算是瓶颈 | **不成立** | LoAF 中 styleAndLayout 合计 2 ms |
| 用 `startTransition` 可以把胶囊提前 | **不成立** | 离散事件中调度的 transition 仍会在下一次绘制前冲刷。且模式状态提升在 `Workbench`，更新它会重渲整个工作台 |

## 候选方案

三个方案代价递增，都能减少这里的一次性开销。**当前均未实施。**

1. **让侧边栏主体不随模式重建**（把两套主体改为原地隐藏而不是条件渲染）。这是唯一能真正压掉那次提交的做法，并会一并消除方向不对称。改动面中等，需要核对两套主体的可访问性与滚动状态。
2. **让对话线程常驻挂载**（知识模式下用 CSS 隐藏而非卸载）。直接针对“切回助手更贵”这一半，改动最小，风险最低。**推荐先做这个**。
3. **只做感知优化**（点击瞬间在侧栏本地点亮胶囊，不经过 memo 层）。按钮会立刻响应，但页面仍需等待，属于手感改善而非提速。

## 已尝试并回退

本次排查中试过方案 1 与方案 3 的组合：让侧栏的三行主入口常驻挂载、用 CSS 隐藏，并让胶囊在渲染期读一个乐观 ref 提前点亮。该改动**未能解决根因**——胶囊与页面同属一次提交，提交内不存在先后——并且在编译前就交付，引入了一处未定义变量引用，导致点击“助手”直接白屏。该改动已全部回退，`fox-sidebar.tsx` / `fox-sidebar.css` / `workbench.tsx` 回到改动前状态，回退后解析检查通过。

教训：本仓库单文件解析检查（esbuild `transform`，loader `tsx`）几秒即可完成，交付任何 `.tsx` 改动前必须执行。

## 已知限制

- 正式版本只确认了**阻塞为 0**，方向不对称未在正式产物上单独复测；按同一机制应成比例缩小，但未取数。
- 正式构建样本量有限，35–43 ms 为多次点击的观测区间，不是分布。
- 本机无法完成 Vite 生产构建（pnpm 符号链接在 Linux 侧不可解析），所有正式版数据均来自既有 `dist`，非本次重新构建。
