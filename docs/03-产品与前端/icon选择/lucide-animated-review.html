lucide-animated 评估

和上一份 animateicons 的对照。结论先说：lucide-animated 更像你仓库现在这套东西的同类，而不是 animateicons 的同类——它是 shadcn registry， 源码逐个拷进仓库，每个图标自己管 hover 动画。这既是它的长处，也是迁移成本所在。

01它和 animateicons 不是一类东西

同样是「lucide + motion 的动画图标」，但分发、结构、触发方式都不同。 这决定了迁移是改一个 import 还是逐个拉源码再重做触发。

对你这个仓库，lucide-animated 有一个别人没有的优势。 你现在用的 animate-ui 也是「本地源码 + motion」这一路数，所以两者是同一个物种： 图标文件躺在 src/components/ 下，动效可以随便改，不受包版本牵制。 从 animate-ui 换到 lucide-animated，是同构替换；换成 animateicons 则是引入一个 外部运行时，动效形态由库决定，你改不了。

02覆盖面对比：82 对 140

按仓库实际在用的 175 个图标逐个比对。lucide-animated 有 468 枚， animateicons 有 676 枚 lucide 图标，差距主要落在「名词性图标」上—— 文件类型、设备、容器这类。

差的都是什么。lucide-animated 覆盖不到的 93 个里，绝大多数本来就不该动： FileCode、FileSpreadsheet、FileArchive 这些文件类型， Database、Server、HardDrive 这些设备图标， CircleAlert、Info、TriangleAlert 这些状态标记。 真正有影响的是 5 枚：BellRing、WandSparkles、 CircleStop、CirclePause、Target—— 它们都在「建议改为动效」的 22 个名单里，但 lucide-animated 没有。 也就是说只靠它一个库凑不齐 22 枚，还得留着 animateicons 或自己写。

04换过去要付的代价

六件事，按实际影响排序。前两件是机械劳动，第三件是真正的设计决策。

逐个拉取源码

468 个图标没有 npm 包，每个都要 npx shadcn add "https://lucide-animated.com/r/<name>.json"，或者用它的 MCP / llms.txt 自己写脚本批量拉。仓库现在 11 个动画图标是本地文件，直接换掉即可；但要扩到 22 个就得新增 11 次拉取。

cn 与 Tailwind 依赖

生成的文件里 import { cn } from "@/lib/utils"，仓库确实有 @/lib/utils，components.json 也配好了 @/components → src/components，所以路径能直接落地，不需要额外配置。

触发方式要重做

这是最实际的一处。仓库现在的 AnimatedIconTrigger 用 asChild 把 AnimateIcon 包在按钮外面，注释写得很明确：让整个动作（含文字标签）一起响应 hover / press，每次手势只播一次。lucide-animated 的 hover 监听在图标自己那个 <div> 上——只有鼠标压到图标本身才播。要保留现在的行为，得给每个图标再加一层 ref 包装。

动效形态不一样

lucide-animated 每个文件都是手写的：bell 是整枚 svg 摇（rotate: [0,-10,10,-10,0]），delete 是盖子 y: -1.1 上移 + 三条线微调。而仓库现有的 animate-ui 体系基于 variants + path / path-loop 描边循环。换库等于把动效语言整体换掉。

减少动效偏好

仓库在 AnimatedIconTrigger 里用 useReducedMotion() 关掉了 hover / tap 动画。lucide-animated 的 hover 是写死的，要保留这个无障碍行为得自己在包装层拦。

体积与署名

单图标源码约 2–4 kB（含 motion 变体），源码是逐个拷进仓库的，不参与 tree-shaking 讨论；MIT 协议，站点明确允许个人与商业项目使用，教程和 demo 不可再分发。

06建议

如果目标是「一个库搞定」，两个都做不到——需要取舍。

如果优先考虑改动小、可控：选 lucide-animated。 它和你现在的 animate-ui 是同一物种，8 个现有图标可以同构替换， components.json 的别名（@/components、@/lib/utils） 已经配好，拉下来的文件能直接落地。代价是要逐个拉源码，并且要补一层 ref 包装 才能保住「整个按钮一起响应 hover」的现有行为。缺口用 animate-ui 现有的图标补， 或者自己写 5 个。
如果优先考虑覆盖面：选 animateicons。22 个建议改动的图标它全有， 一个包改 import 就能上。代价是动效形态由库决定、单图标体积更大， 以及要接受一个 `<div>` 外壳。
两个都上是最差的选择——那还是两个库。你原本的目标是收敛到一个。 真要收敛，把「8 个同构替换 + 5 个自写」这条路走完，比引入第二个包更接近目标。
