# 工作闭环使用指南

> 状态：生效<br>
> 适用版本：Fox 0.1.x<br>
> 维护范围：工作模式（Goal / Task / Evidence）的界面与用户操作：`apps/desktop/src/features/chat/components/GoalProgress.tsx`、`TaskItem.tsx`、`EvidenceList.tsx`、`ActivityDetailPanel.tsx`，进入规则 `apps/desktop/src-tauri/src/work_mode_gate.rs`<br>
> 最后更新：2026-10-25

## 结论

- 工作模式**只在显式请求时进入**：消息以 `/目标`、「进入工作模式」「创建一个目标」等前缀开头，或 Runtime 提出目标建议。普通请求（包括修改代码类请求）不会自动进入工作模式（`work_mode_gate.rs` 的 `evaluate`）。
- 进入前总要用户确认：输入框上方出现确认卡，「继续执行」或「暂不执行」。
- 进度和证据在对话右侧栏的「运行详情」里查看，那里也能「暂停 / 继续」和「删除目标」。
- 输入框上方的完整进度卡（`GoalProgress`）只在有待决定事项时出现：目标待确认、计划待批准、专家工作流 Gate 待批准。

## 目标与范围

面向用户支持和前端工程师，说明工作模式在界面上的进入方式、进度查看、状态含义和中断恢复。Goal / Task / Evidence 的数据模型和 Runtime 协议见文末相关文档。

## 什么时候进入工作模式

Host 在发送消息前调用 `work_mode_gate::evaluate`，规则按顺序：

1. 消息包含「暂不修改」「不要修改」「只讨论」「只解释」「只给方案」等短语（`NO_CHANGE_PHRASES`，含英文对应）→ 保持普通对话；
2. Runtime 提出目标建议 → 请求确认；
3. 消息以显式前缀开头（`EXPLICIT_GOAL_PREFIXES`，如 `/目标`、`/goal`、「请创建一个目标」「列个目标」「进入工作模式」「把这个任务作为目标跟踪」）→ 请求确认；
4. 其他情况 → 保持普通对话。

在输入框输入 `/` 选择「目标」（说明「显式进入需要持续跟踪的工作模式」），发送时会在消息前加 `/目标 `（`fox-slash-commands.tsx`）。

注意：第 2 步中检查「暂不修改」等短语的是 Runtime 建议的标题、目标和验收文本，不是用户原话（代码现状）。

## 确认

请求确认时，Goal 以 `proposed` 状态创建，这次 Run 处于 `awaiting_confirmation`，尚未发给 Runtime。

输入框上方出现决策卡（`fox-decision-card.tsx` → `GoalProgress`）：

> Fox 将为这项工作跟踪任务、执行过程和证据。是否进入工作模式并继续执行？

| 按钮 | 结果（`work_mode_confirmation_resolve`） |
| --- | --- |
| 继续执行 | Goal 变为 `active`；释放暂存的这次 Run，交给 Runtime（本机或资料库服务 Runtime）执行 |
| 暂不执行 | Goal 变为 `cancelled`；暂存的 Run 标为 `cancelled` |

确认带 `expectedVersion`，版本不符会失败。待确认状态保存在 SQLite，刷新或重启不会自动放行。

决策卡一次只显示一类事项，优先级：工具审批 > 需要回答的问题 > 目标确认 / 计划批准 / 工作流 Gate。

## 查看进度

### 输入框上方的进度卡

`GoalProgress` 只在有待决定事项时渲染，默认折叠。内容：

- 目标标题和状态标签：进行中 / 已阻塞 / 已完成 / 待确认；
- 「N / M 任务已完成」和「当前: 〈任务〉」；
- 阻塞原因（如有）；
- 计划待批准时：「计划 vN 待批准：〈标题〉」、任务列表、「退回修改 / 批准计划」；
- 专家工作流：阶段、尝试次数；Gate 待批准时「拒绝并停止 / 批准阶段」；
- 专家团队运行中：「停止协作」；
- 展开后：目标说明、每个 Task（见下）、以及「修改计划 / 独立复查 / 最终验收」状态汇总。

### 右侧栏「运行详情」

右侧栏 `activity` 页（标签「运行详情」）渲染 `ActivityDetailPanel`，任何时候都可以打开：

- 「最近一次运行」状态和错误；
- 目标：标题、状态（进行中 / 已暂停或阻塞 / 已完成 / 等待确认）、「N/M 项任务完成」；
- 按钮：「暂停」（Goal 为 `active` 时）/「继续」（Goal 为 `blocked` 时）、「删除目标」；
- 「查看计划、任务和证据」折叠区：计划版本、每个 Task 的状态和证据（显示原始英文状态值，如 `in_progress`、`valid`，代码现状）；有验收记录时提示「任务完成不代表验收通过」；
- 「工具记录」（最近 100 条）和「运行记录」（最近 30 条）。

### Task 与证据

`TaskItem` 显示 Task 标题、状态标签、「尝试 N」（attempt > 1 时）、阻塞原因、「N 个证据」；展开后显示详情和证据列表。

证据类型（`EvidenceList.tsx`）：工具调用、执行跟踪、测试结果、文件变更、Artifact、用户确认、外部引用。

证据有效性：

| 值 | 标签 |
| --- | --- |
| `unverified` | 未验证 |
| `valid` | 有效 |
| `stale` | 已过期 |
| `missing` | 缺失 |
| `invalid` | 无效（附 `invalidReason`） |

点击证据（`openEvidence`，`workbench.tsx`）：指向消息时滚动到该消息并高亮；指向 Artifact 时滚动到产出它的回复；指向资料来源（带资料库和文档 id）时打开远程资料详情 `knowledge-detail`；指向工具调用或运行事件时打开右侧栏，`file_diff` 类型进「更改」页，其余进「运行详情」并定位对应工具记录；都不匹配时提示「该证据的原始对象已不可用」。

## 状态含义

Task 状态（`WorkTaskRecord.status`）：

| 状态 | 界面标签 | 用户动作 |
| --- | --- | --- |
| `queued` | 排队中 | 通常无需操作 |
| `in_progress` | 进行中 | 可在「运行详情」查看过程，必要时暂停 |
| `blocked` | 已阻塞 | 阅读阻塞原因，补充信息 |
| `interrupted` | 已中断 | 确认现场后重试，attempt 会增加 |
| `completed` | 已完成 | 检查证据是否仍有效 |
| `skipped` | 已跳过 | 无需操作 |

Goal 状态：`proposed`、`active`、`blocked`、`completed`、`cancelled`。

Task 已完成不等于证据永久有效，也不等于验收通过。

## 暂停、删除与中断恢复

- **暂停**（`goal_running_set`，`running = false`）：Goal 变为 `blocked`，原因记为 `Paused by user`；若对话有正在进行的 Run，会一并取消。
- **继续**（`running = true`）：Goal 重新变为 `active`。
- **删除目标**（`goal_delete`）：对话有进行中的生成时拒绝，提示「请先停止当前生成，再删除目标」；否则删除 Goal。`work_tasks`、`task_evidence` 等表对 `goals` 设置了 `ON DELETE CASCADE`，Task 和证据会一并删除。界面上没有单独的「取消目标」按钮。
- **App 关闭或 Sidecar 崩溃**：运行中的 Task 不会被标为完成。下次启动时 `audit_interrupted_tasks`（`lib.rs` 启动流程）把属于已结束 Run 的 `in_progress` Task 改为 `interrupted`，并收口对应的 attempt。
- **重试**从原工作图继续，attempt 增加，旧证据保留，新证据追加（Runtime / Host 行为，本次未逐条复核）。

刷新或重启后，界面从 SQLite 读取 Goal、Task 和证据（`useGoalProgress(detail)`），再叠加新的 Runtime 事件。

## 诊断

Tauri 侧有 `diagnose_work_state` 和 `export_work_trace` 两个命令，前端客户端也封装了 `diagnoseWorkState` / `exportWorkTrace`，但当前**界面上没有调用入口**，只能由开发或支持人员直接调用。导出内容的范围（是否排除对话正文、项目文件、凭证）本次未核对。

如果刷新后状态仍异常，请记录 Conversation ID 和 Run ID 再排查（见 `docs/06-运维指南/诊断与故障排查.md`）。

## 与完整工作图的关系

本页只讲 Goal → Task → Evidence 的基础操作。界面上还能看到计划修订（Plan Revision）、独立复查（Review Finding）、最终验收（Acceptance）、专家工作流和专家团队的状态，它们复用同一份 SQLite 工作数据。工具写入和高风险操作仍走 Host 的权限和审批。

## 测试与验证

人工回归：

1. 以 `/目标` 开头发送消息，出现确认卡；「暂不执行」后 Run 取消、Goal 为 cancelled；
2. 「继续执行」后 Runtime 开始执行，Task 出现；
3. 普通的修改类请求不出现确认卡；含「只讨论」时即使带 `/目标` 也不进入；
4. 「运行详情」中暂停 / 继续 / 删除目标；运行中删除被拒绝；
5. 运行中关闭应用，重启后 Task 为「已中断」；
6. 点击各类证据的定位行为。

自动化测试本次未逐个核对；Rust 侧 `work_graph.rs` 中有 `startup_audit_interrupts_tasks_owned_by_terminal_runs`。

## 已知限制

- 「运行详情」中的 Task 和证据状态显示原始英文值，与进度卡的中文标签不一致。
- 进度卡只在有待决定事项时出现，平时需要打开「运行详情」查看进度。
- 诊断与导出命令没有界面入口。
- `GoalProgress`、`TaskItem`、`EvidenceList` 使用写死的 Tailwind 颜色（如 `text-blue-600`、`bg-yellow-100`），不跟随配色主题（见 [设计系统](设计系统.md)）。
