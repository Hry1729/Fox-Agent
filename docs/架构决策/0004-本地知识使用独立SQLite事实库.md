# 0004：本地知识使用独立 SQLite 事实库

> 状态：已接受<br>
> 决策日期：2026-08-22<br>
> 影响范围：本地知识库、文档导入、索引、任务恢复、备份与存储迁移

## 背景

Fox 的 `fox.db` 已经承载会话、消息、运行、项目、配置和插件等核心产品事实。本地知识库会新增原始文档元数据、分块、向量索引代次、Embedding 模型状态和长时间运行任务，数据量、写入节奏与恢复方式都不同于会话数据。

如果继续把这些数据写入 `fox.db`，文档批量导入和重建索引会扩大锁竞争、备份体积与损坏影响面，也会让用户迁移本地知识目录时必须搬迁整个 Fox 产品数据库。

## 决策

本地知识使用独立的 SQLite 数据库 `knowledge.db`，并与 `fox.db` 保持明确边界。

- `fox.db` 保存会话、专家、本地知识引用、插件安装状态和全局产品配置。
- `knowledge.db` 保存本地知识库、文档、分块、索引代次、检索诊断、Embedding 模型状态、导入与迁移任务。
- 两个数据库不使用跨库事务或外键；跨库关联只保存稳定 ID，并通过幂等操作、状态机和对账修复一致性。
- 向量数据由 `VectorStore` 管理，SQLite 只保存索引代次、Provider 类型、格式版本和激活状态。只有完整构建并校验成功的代次可以切换为 active。
- 存储目录迁移先关闭数据库和索引句柄，再复制、校验并原子切换配置；失败时继续使用原目录。
- 备份与恢复按数据库分别执行。恢复 `knowledge.db` 后必须校验受管文件、模型和 active 索引代次是否仍存在。

## 后果

正面影响：

- 隔离大批量导入、索引重建与会话写入的故障域。
- 用户可以独立迁移、备份或清理本地知识数据。
- 为 Zvec 或其他 `VectorStore` 实现保留可替换边界。
- 本地知识任务可以独立恢复，不阻塞 Fox 核心数据打开。

成本与风险：

- 跨库更新不能依赖单个 SQLite 事务，必须设计幂等补偿和降级提示。
- 删除知识库后，`fox.db` 中的历史引用仍可能存在，需要保留展示快照并标记不可用。
- 迁移和备份流程必须显式管理 Windows 文件句柄。
- 两套 Schema 都需要独立迁移、完整性检查和测试样本。

## 未采用方案

- **全部写入 `fox.db`**：实现简单，但会放大锁竞争、备份和损坏影响面。
- **只使用向量数据库保存知识事实**：不适合保存任务状态、文档版本、解析错误和可审计引用。
- **由 Runtime 直接管理本地知识目录**：会绕过 Host 权限边界，并增加进程重启后的恢复复杂度。

## 后续要求

- `knowledge.db` Schema 变更必须包含升级、约束和重启恢复测试。
- Zvec 与 ONNX Runtime 进入发布构建前必须通过 Windows x64 离线加载 Smoke。
- 跨库关联不得依赖可变名称，必须使用来源、连接和对象 ID 组成的稳定引用。
- 存储迁移不得在数据库或索引句柄仍打开时移动目录。
