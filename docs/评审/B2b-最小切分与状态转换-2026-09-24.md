**v86 仅加两个 nullable `kernel_runs` 投影列：** `wait_deadline_wall_ms`、`wait_accounted_until_wall_ms`（正值且后者不大于前者），随 `RehydratedRun`/`KernelPersistCommand` 原子写读；`running_elapsed_ms` 沿用现列。`run.waiting_jobs` 事件冻结 `parkedAtWallMs`、已结算但未发布的原模型响应及其输入/完整历史与游标、排序后的必要 jobId/attempt、来源 checkpoint seq；事件 seq 是本次 wait 身份，不另建队列表。`kernel_runs.state` 现无 SQL CHECK，v86 无需重建，但 `RunState` 编解码、`kernel.rs::valid_run_state`、rehydrate/终态不变量均同步。WaitingJobs 时 `runs.status=running`、`terminal_written=0`、`model_request_since_wall_ms=NULL`，两 wait 列同时非空；其他态同时清空。park 事务重新联查本 root/conversation/Run 的冻结 Job 集与正值原 `deadline_ms`，缺失明确 `kernel.job_deadline_missing`，不补新期限。

**转换/预算：** Running→WaitingJobs 的同一响应事务结算原 model lease、确认 B2a 通知、记 `run.waiting_jobs`；有未终态 Job 时绝对截止固定为有限 Run 的 `min(parkWall+原剩余执行预算,max(Job原deadline))`，无限 Run 为 `max(Job原deadline)`。每次 wake/重开只在 CAS `(runId,state,parkSeq,accountedUntil)` 下把 `min(now,deadline)-accountedUntil` 加到 `running_elapsed_ms` 并推进游标；时钟倒退拒绝，重开/再次 park 不刷新截止或重复扣费。截止时按原 deadline 结算/取消 Job，仍不确定则有界显式阻断；16 KiB 不可交付通知同样显式阻断，均不得放行 Final。全部 Job 终态时 WaitingJobs→Running，依据冻结响应和历史生成 **一次** `engine.continuation_requested`/原 ContinuationModel outbox（`continuation:<wakeEventSeq>`，`lane=job_notice`），由新模型 lease 按 B2a 绑定真正 pending 事实；若只有 pending 通知则直接走此确定分支。普通预读/Final 竞争用已保存响应重规划，未 leased 才可重试；原模型及作业绝不重发。

**Host 资源与恢复：** 现在 `CancellationRegistry::retire_run` 会取消现有 Job 父 token；Parked 出口只能移除 active 执行占用，保留未取消 scope 供后台 Job，终态才 retire。重新 `register_run` 可复用该 scope；重启创建新 scope，但孤儿 paused 只等显式恢复且沿用原 deadline。`kernel_host_recoverable_runs` 会选中非终态 waiting，恢复入口应先辨认 Parked 并扫描 Job/截止，不能走普通 initial 或把 Parked 当 Err 调 `mark_run_failed`。等待期间新 steering 保持原持久队列，首版不因 steering 单独启动模型；唤醒组帧读取当前队列并遵守 F3 交付检查，取消/截止无需模型即明确终结且不能声称未答的 steering 已处理。验收必须在真实 `start_kernel_run`/detached 回调后再次取得同 Run 锁、验证后台 Job 继续、最终答复仅一次；纯 SQL/组件用例分开列证据。
