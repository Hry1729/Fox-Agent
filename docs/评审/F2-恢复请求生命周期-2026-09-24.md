## 范围与接口

本次只处理 `restore_version_with_seam`、托管文件版本仓库和 schema 83。桌面命令仍传入会话、版本、`force` 与稳定 `requestId`；文件仍走原有受控原子提交、锁内基线复验和备份/替换日志。未修改 Pi、F3、后台 Job、普通写入准入或主工作树。

首次执行在读取并验证候选快照、确认目标当前基线后，用 SQLite `IMMEDIATE` 事务认领 `(conversation_id, request_id)`。请求意图摘要按固定格式包含会话、版本 ID 和 `force`。事务只让插入成功的一方取得随机 `attempt_owner`，并绑定目标路径、基线和 dispatch ID；竞争者读取已存在请求，绝不进入本次文件提交。已提交请求只从持久的 `result_version_id` 取回版本，并核对其会话、目标、来源版本与恢复类型。恢复是 Host 用户动作，版本行的 `tool_call_id` 仍为空；dispatch 身份由请求认领和提交 CAS 校验，不伪装为模型 ToolCall。`running` 与无法辨认的终态返回不确定结果，不声称目标未变。

文件提交临界区内，恢复版本行和请求的 `committed/result_version_id` 在**同一个 SQLite 事务**写入，且更新必须匹配 `running`、本次 owner、目标、来源版本和 dispatch ID。任一数据库写失败，两条事实一同回滚；物理文件可能已经变化，因此保留恢复材料并按不确定结果处理。普通结算只允许 `not_applied`、`recovery_required`、`indeterminate`，并要求 `running + attempt_owner` 的 CAS；不能把成功回执降级。完成判断使用锁内版本与请求事务的回执，不再用锁外当前文件 hash 改判；后续合法写入是另一笔事实。

schema 83 只为 `kernel_restore_requests` 增加可空 `intent_digest` 和 `attempt_owner`，不改旧迁移。v82 行缺少 `force`，升级后这两列保持 NULL；旧 requestId 的再投递保守返回 `identity_conflict`，不猜测意图，也不自动重放。新请求在首次认领时才绑定目标和基线。重开后，已原子提交的请求可按持久回执重放响应；仍为 `running` 且没有可信回执的请求保持不确定，需人工检查恢复材料，不能仅凭目标当前 hash 归因或自动重新执行。结算触发器失败等情形可能留下这种 `running` 行。

## 定向用例与证据层级

测试文件 `runtime_host/kernel_coordinator/f2_restore_lifecycle_tests.rs` 有 **5 个**真实 `restore_version_with_seam` 入口用例，使用合成临时文件和真实 `Database`，不调用付费模型：

1. 同一个 requestId 首次恢复后改版本或 `force`，应得到 `identity_conflict`；同时检查 v82 形状的旧请求不能推断意图、非 owner 和原 owner 都不能降级成功终态。
2. 第一次恢复在真正认领后的文件提交阶段被 seam 阻塞；第二个独立 `Database` 连接重试，必须报告进行中或结果不确定，非 owner 不能结算，原请求放行后正常提交。
3. 恢复提交后，另一笔经真实 Host 写入口的合法写入改变目标；恢复仍返回原成功回执。模拟响应丢失并重开数据库后，同 ID 取回相同版本，不覆盖后续写、不新增恢复版本。
4. SQLite 测试触发器拒绝请求结算；物理文件变化后，版本行与成功回执同事务回滚，保留 `running`，关库重开重试不执行第二次文件写入。
5. 两个独立 `Database` 连接在旧版“先查无记录”窗口会合，同时提交同 ID；`after_claim` 计数要求仅一方进入文件提交路径，文件、恢复版本行和最终请求终态对应同一次恢复，败者不能覆盖胜者终态。所有会合等待均有 10 秒上限。

迁移用例 `migration_83_preserves_v82_restore_requests_without_inventing_force` 用合成 v82 表形状验证旧请求原值保留、新列为 NULL，以及再次打开的幂等性。既有 REV 恢复用例和 v53 历史迁移用例仍需协调者回归。
