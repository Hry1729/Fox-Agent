# App 产品能力完善清单

本文用于统一 Fox 桌面端后续完善范围。目标不是继续增加按钮，而是让用户看到的每个状态、入口和操作都真实可用，并把已经存在于底层的 Agent 能力做成完整、可理解、可诊断的产品闭环。

## 一、总体判断

Fox 的 Agent 执行内核已经具备工具调用、权限控制、任务闭环、子 Agent、数字同事和产物追踪等基础能力。当前短板主要在 App 层：部分界面展示的状态比底层真实能力更超前，部分功能只有入口没有完整流程，知识库已有文本检索、向量模型和向量库的部分零件，但尚未组成真正可用的向量检索闭环。

因此执行顺序应当是：

1. 先消除误导性入口和虚假状态，恢复用户信任。
2. 再打通知识库向量检索的完整闭环。
3. 补全任务、项目、数字同事、反馈等管理能力。
4. 最后扩大全局搜索、浏览器、诊断和 UI 体验。

## 二、产品建设原则

### 1. 界面可见，就必须真实可用

按钮不能只弹出“即将接入”，状态不能用写死的数据伪装完成度。暂时做不完整的功能直接隐藏，不用“开发中”的入口占据正式界面。

### 2. 后端状态是唯一事实来源

文档数、分块数、索引代次、向量数、模型、维度、构建进度和失败原因，都必须由 Host 或数据库真实返回。前端不能自行猜测“已就绪”，也不能用 `0` 或“未提供”冒充真实统计。

### 3. 明确区分三种检索能力

- 关键词检索：按文字和词语匹配，当前已经可用。
- 向量检索：把文本转换成向量，按语义相似度搜索，目前尚未形成产品闭环。
- 混合检索：合并关键词和向量结果，需要在前两者均真实可用后开放。

### 4. 每项功能都要形成纵向闭环

一个功能只有同时具备“入口、配置、执行、进度、结果、失败处理、恢复与诊断”才算完成。不能只完成页面，也不能只完成底层接口。

### 5. 高风险动作继续经过统一权限边界

删除文件、修改项目、执行外部程序、访问网络或调用插件等操作，继续通过工具白名单、作用域限制、审批和审计记录执行，页面不能绕过 Agent Runtime 直接做高风险动作。

### 6. 当前明确不做的功能不留入口

- 不提供内置终端界面。
- 不提供语音输入。
- 不提供应用内自动更新。
- 不把“网络调用记录”宣传为完整的 Agent 浏览器。

这些能力只有在形成完整实现、权限和测试方案后，才重新进入产品评审。

## 三、当前真实能力基线

| 模块 | 当前真实能力 | 主要缺口 |
| --- | --- | --- |
| Agent 对话 | 可调用工具、产生文件、展示过程和产物 | 全局任务聚合、统一失败恢复仍不足 |
| 子 Agent | 已有真实任务和事件数据 | 详情、产物关联、重试与结果采纳状态不完整 |
| 数字同事 | 已有调度与运行记录基础 | 页面仍存在“自动任务 0 / 尚未启用”等断链展示 |
| 本地知识库 | 可导入、解析、分块并用 SQLite 做关键词检索 | 没有完整的向量生成、写入、校验、激活和检索闭环 |
| 向量基础设施 | 有本地 Embedding Provider、VectorStore 与 Zvec 的代码零件 | 尚未接入桌面应用主流程，模型管理和真实状态缺失 |
| 插件 | 已安装插件的发现和启用/禁用有基础 | 安装、更新、卸载没有完整生命周期 |
| 浏览器侧栏 | 可做手动网页预览并展示 Agent 网络活动 | 不能称为可操作网页的 Agent 浏览器 |
| 文件产物 | 对话结束可展示本轮文件并在右侧文件栏打开 | 大文件、异常格式和外部打开失败仍需统一处理 |

## 四、P0：立即消除误导和断链

P0 的目标不是增加新功能，而是保证用户看到的所有内容都符合真实能力。

### P0-1 本地知识库状态真实化

当前不能再用“有文档”或“有代次”推断向量检索已经就绪。建议不要只增加一个笼统的 `status`，而是分别返回能力状态：

```ts
interface KnowledgeBaseCapabilityStatus {
  textIndexReady: boolean;
  vectorIndexReady: boolean;
  searchMode: 'keyword' | 'vector' | 'hybrid';
  embeddingModel: {
    id: string;
    name: string;
    version: string;
    dimension: number;
  } | null;
  chunkCount: number | null;
  vectorCount: number | null;
  lastIndexedAt: string | null;
  fallbackReason: string | null;
}
```

界面规则：

- 只有文本索引可用时显示“仅关键词检索”。
- 未配置向量模型时显示“未配置向量模型”，不显示“向量索引已建立”。
- 统计暂时无法提供时显示“暂无统计”，不显示具有误导性的写死 `0`。
- 向量构建失败时显示失败阶段、原因、可重试动作和仍可使用的降级模式。
- 只有通过向量数量、维度、模型和读写校验后，才显示“向量检索就绪”。

### P0-2 删除终端和语音功能

当前版本不保留“开发中”占位：

- 删除工作台内置终端抽屉和标题栏终端入口。
- 删除输入框麦克风按钮。
- 删除设置中的语音输入开关。
- 删除对应的本地偏好、状态和专用样式。
- 通用组件库中的独立组件可以保留，但不得被正式产品页面引用或宣传为现有能力。

### P0-3 收敛插件中心

在 Host 尚未支持完整生命周期前：

- 隐藏“添加插件”“安装”“更新”“卸载”等入口。
- 仅保留已安装插件列表，以及真实生效的启用/禁用开关。
- 清楚展示插件来源、版本、权限、运行状态和最近错误。
- 未来重新开放安装时，必须同时具备包校验、依赖检查、权限确认、失败回滚和卸载清理。

### P0-4 清理设置中的幽灵开关

逐项检查“保存后是否有业务代码读取”。没有消费者的设置先从界面移除；需要保留的设置必须先接通逻辑。

| 设置项 | 处理建议 |
| --- | --- |
| 新项目默认权限 | P0 接入项目创建流程；这是安全边界，必须用自动化测试验证“创建项目时真实读取该设置值、写入项目权限并由 Runtime 执行”，防止设置与实际权限脱节造成越权 |
| 回复完成通知 | 通知中心完成前先隐藏 |
| 关闭窗口行为 | 接入 Tauri 窗口关闭事件后再显示 |
| 默认推理深度 | 接入新对话和运行时请求后再显示 |
| 启动时恢复对话 | 接入启动恢复逻辑后再显示 |
| 跟随系统主题 | 接入系统主题变化监听后再显示 |
| 保持登录、忘记密码 | 没有真实账户流程时隐藏 |
| 自动更新 | 整行删除，不纳入本产品路线 |

### P0-5 修复知识库入口断链

- 侧栏“新建知识库”必须直接打开创建弹窗，不能只跳转到列表页。
- 列表页、空状态页和侧栏的创建入口复用同一个创建流程。
- 创建成功后直接进入详情页，并显示真实的初始化和索引状态。

### P0-6 清理其余占位交互

- 点赞、点踩在未支持持久化前不得提示“已记录”。
- 帮助、登录、插件、模型或项目操作中，只弹 Toast 的入口逐个隐藏或接通。
- 所有禁用按钮必须说明是权限不足、条件不满足还是暂不可用，不能让用户猜测。

### P0 验收标准

- 界面上不存在点击后只显示“即将接入”的主功能入口。
- 没有向量索引时，任何页面都不会显示“向量检索就绪”。
- 每个可编辑设置都能找到明确的业务读取方和测试。
- 工作台和设置页不再出现终端、麦克风或语音输入入口。
- 插件中心只展示真实可执行的操作。

## 五、P1：打通知识库向量检索闭环

### P1-1 接通运行时基础设施

- 将本地 Embedding Provider 接入桌面应用主库，而不是只存在于独立测试程序。
- 明确 ONNX Runtime 的打包、加载、版本兼容、CPU 指令集和失败降级策略。
- 将 VectorStore 接入知识库服务，完成 Zvec 可用性检测和一次真实写入/读取自检。
- 建立可回滚的索引代次：新代次全部校验成功后再原子切换，失败时继续使用旧代次。
- 所有长任务支持取消、重试、重启恢复和进度持久化。

### P1-2 向量模型管理页面

位置：`本地知识库 → 向量模型`。

已安装模型列表应展示：

- 模型名称、版本、语言、维度、文件大小。
- 模型文件、Tokenizer、配置和校验哈希是否完整。
- 安装状态、加载状态、最近测试结果和错误。
- 操作：测试向量、设为默认、删除未被使用的模型。

页面分为三部分：

```text
向量模型
├─ 已安装
├─ 推荐模型
│  ├─ bge-small-zh-v1.5（中文、384 维）
│  ├─ all-MiniLM-L6-v2（384 维，语言适用范围待实测标注）
│  └─ 下载 → 校验 → 安装 → 测试向量
└─ 手动导入（高级用户）
```

推荐模型使用内置、可维护的模型清单提供下载入口。清单必须包含下载源、许可证、模型版本、文件列表、维度、适用语言、预计下载体积和 SHA-256；体积不能在页面代码中写死，应以实际发布的 ONNX 模型包为准。下载需要支持进度、取消、断点续传、哈希校验、安装回滚和失败重试，校验通过后才能进入已安装列表。

模型导入不能只允许选择一个 ONNX 文件。一个可运行的模型包至少需要模型文件、Tokenizer、配置清单、版本和哈希；导入流程必须验证这些内容，自动识别维度，并展示安装进度和失败原因。

`bge-small-zh-v1.5`、`all-MiniLM-L6-v2` 可以作为首批候选，但需先完成许可证、下载来源、运行时兼容性、中文效果、体积和速度验证；只有通过验证并进入受控模型清单后，页面才能显示为“可下载”。

### P1-3 知识库创建与编辑

```ts
interface KnowledgeBaseConfig {
  name: string;
  description?: string;
  vectorModelId: string | null;
  chunkSize: number;
  chunkOverlap: number;
  searchMode: 'keyword' | 'vector' | 'hybrid';
}
```

交互要求：

- 默认分块大小可以是 512、重叠 50，但必须说明单位是字符还是 Token。
- 校验 `chunkOverlap < chunkSize`。
- 没有可用模型时禁用向量和混合模式，并解释原因。
- 切换模型不会直接破坏旧索引，而是创建新代次，完成后再切换。
- 高级参数默认折叠，普通用户只需选择“关键词”或推荐的“混合检索”。

### P1-4 知识库详情页重构

详情页分为四块：

1. 基础信息：文档数、有效文档数、总大小、最后更新。
2. 文本索引：代次、分块数、解析器版本、构建时间和错误。
3. 向量索引：代次、模型、维度、向量数、存储大小、构建时间和错误。
4. 操作区：导入文档、重建索引、切换模型、测试检索、查看任务。

状态必须细分为 `等待中、解析中、分块中、向量化中、写入中、校验中、已就绪、部分可用、失败、已取消`，不能全部归并成“处理中”。

### P1-5 文档导入和索引流水线

完整流程：

```text
复制或登记文件
  → 解析文档
  → 文本分块
  → 保存关键词索引
  → 批量生成向量
  → 写入向量库
  → 校验数量、维度和抽样检索
  → 原子激活新代次
```

前端进度应使用后端事件和持久化任务状态，例如：

```text
✓ 解析文档 3/3
✓ 文本分块 128 块
● 生成向量 45/128（35%）
○ 写入向量库
○ 校验并激活
```

失败后保留已完成阶段，允许从安全检查点继续，不应让用户重新导入全部文件。

### P1-6 检索测试台

位置：`知识库详情 → 测试检索`。

测试台需支持：

- 输入问题，选择关键词、向量或混合检索。
- 展示每种检索的耗时、召回数量和降级原因。
- 展示 chunk ID、来源文件、页码或段落、文本片段和分数。
- 混合检索展示融合方式及综合排名；可先采用 RRF，但算法需要配置版本。
- 支持打开原文、复制引用、查看分块上下文。
- 支持保存 10～20 条典型问题作为测试集，并为每条问题标注期望命中的文档或分块。
- 切换模型、分块参数或融合算法后，可以批量运行同一测试集。
- 提供模型 A 与模型 B 的对比表格，展示有标注数据时的 Recall@K、耗时、Top-3 重合度、命中来源和失败样例。
- 没有人工标注的“正确结果”时，不得把返回数量当作召回率；此时只展示耗时、Top-K 重合度和结果差异。
- 支持导出脱敏的 Markdown 或 JSON 报告，用于文档记录、团队评审和版本回归。

### P1-7 文档管理

- 单文档删除，并同时清理文本块、向量和来源文件引用。
- 重新解析，处理解析器升级或 PDF 解析失败。
- 重新索引，处理模型或分块参数变化。
- 分块预览，帮助用户检查切分是否合理。
- 用内容哈希识别重复文件；同名但内容不同不能误判。
- 删除和重建均显示影响范围，必要时进入审批流程。

### P1 验收标准

- 重启应用后，未完成的索引任务可继续、重试或明确取消。
- 新向量代次失败不会破坏仍在使用的旧代次。
- 向量数、维度、模型、代次和构建时间均来自真实数据。
- 关键词、向量、混合三种模式可以在测试台得到可解释结果。
- 向量不可用时自动降级为关键词检索，并向用户说明原因。
- 搜索结果能够跳转到原文位置或明确的来源片段。

## 六、P2：补全核心管理闭环

### P2-1 全局任务与通知中心

右上角通知中心统一聚合：

- 待审批：文件删除、越权访问、外部程序调用等。
- 等待回答：工作流或 Agent 需要用户选择。
- 进行中：知识库索引、数字同事、长任务。
- 已完成：任务摘要、文件、提交或报告。
- 失败：失败阶段、原因、重试和诊断入口。

通知必须持久化到数据库，重启后仍能查看；同一事件不能在 Toast、对话和通知中心重复制造多份互不关联的状态。

通知还需要提供静默策略：

- 用户可分别设置哪些事件需要系统弹窗、声音、角标或仅进入通知中心。
- “进行中”任务按任务 ID 合并更新，并进行节流；不能把每个进度事件都新增为一条通知。
- 待审批和等待回答默认具有较高提醒等级，普通进度默认静默。
- 支持已读、未读、全部标为已读和按条件批量清理。
- 通知偏好必须被实际分发逻辑读取，并纳入设置回归测试。

### P2-2 独立项目管理页面

项目卡片展示路径、路径有效性、Git 状态、磁盘占用、最近对话、最近产物和授权范围。支持打开文件夹、更新路径、重新授权和归档。

项目被移动或删除时进入“失效”状态，不自动创建同名目录，也不静默切换到其他路径。

### P2-3 数字同事运行记录

打通数字同事调度记录与 Agent 页面，展示：

- 触发方式、触发时间、执行时长和最终状态。
- 创建的子 Agent、任务依赖和事件流。
- 产生的文件、提交、报告和引用证据。
- 停止、重试、查看详情。
- 结果是否被上层任务采用，以及未采用原因。

删除“自动任务 0 / 尚未启用”这类与真实后端状态矛盾的写死展示。

### P2-4 点赞与点踩持久化

点赞直接保存；点踩允许选择“答非所问、代码错误、理解偏差、其他”并补充说明。保存消息 ID、模型、工具、项目和必要的运行上下文，但默认不保存密钥、完整文件内容或模型隐私推理过程。

反馈主要用于问题诊断、提示词迭代和回归测试，不应用一条反馈自动切换全局模型。

### P2-5 插件完整生命周期

只有在 P0 收敛完成后再建设：插件包来源、签名与哈希、依赖安装、权限预览、启用、更新、禁用、卸载、失败回滚和残留清理。完成前不恢复插件市场式入口。

## 七、P3：搜索、浏览器、诊断与 UI 质量

### P3-1 全局搜索

统一搜索对话标题与内容、项目、专家、数字同事、知识库、文档、任务和产物。结果按类型分组，并标明来源项目和更新时间；权限不足或已归档的内容不能被越权展示。

### P3-2 子 Agent 详情增强

- 实时事件流：状态变化、工具调用、输出和失败。
- 产生的文件可直接打开并定位到本轮产物。
- 展示父任务、兄弟任务和依赖关系。
- 支持停止、重试和重新委派。
- 明确返回结果是否已被主 Agent 采用。

“思考”只展示可公开的过程摘要、计划和工具证据，不展示模型私有推理链。

### P3-3 浏览器能力边界

短期继续定位为“手动网页预览 + Agent 网络调用记录”，页面文案不得称其为能自动点击网页的 Agent 浏览器。

若未来建设完整浏览器能力，至少需要：

- 页面截图和可操作 DOM 快照。
- 点击、输入、导航和下载动作记录。
- 域名白名单、登录态和敏感操作审批。
- 浏览会话恢复、失败重试和替代方案。
- 动作回放、审计和页面变化检测。

### P3-4 统一诊断页面

位置：`设置 → 诊断`。

覆盖：

- 模型连接：配置完整性、可用模型、速率限制和最近错误。
- Runtime Host：版本、进程、WebSocket 和协议兼容性。
- 本地知识库：数据库版本、迁移、任务队列和目录权限。
- 向量模型：安装完整性、ONNX Runtime、测试向量。
- Zvec：版本、路径、维度兼容和测试读写。
- MCP：配置、连接状态、权限和最近失败。
- 插件：版本、依赖、权限和沙箱状态。
- 系统：磁盘空间、Git、文件打开能力和路径限制。

诊断报告支持复制脱敏摘要，但不得包含 API Key、Token、Cookie 和用户文件正文。

诊断项可以提供“一键修复”，但仅限目标明确、可验证、可回滚的动作：

```text
诊断结果
├─ ❌ 向量模型缺少 Tokenizer
│  └─ 自动修复 → 显示下载源与权限 → 下载 → 校验 → 补齐
├─ ⚠️ Zvec 版本或数据格式不兼容
│  └─ 修复 → 兼容性检查 → 备份 → 迁移 → 读写验证 → 必要时回滚
└─ ✓ Runtime Host 正常
```

- 修复前展示将下载、替换或迁移的具体内容，不得静默修改环境。
- 涉及网络下载、外部程序、覆盖文件或数据库迁移时，必须经过权限确认。
- 每个修复器返回结构化步骤、结果和日志，并在完成后重新运行对应诊断。
- 无法可靠回滚的项目只提供修复说明和手动操作，不显示“一键修复”。
- Zvec 等底层依赖不能只按版本号直接替换，必须先验证应用支持范围和数据格式兼容性。

### P3-5 UI 质量统一

- 建立统一的 `Loading、Empty、Error、Partial、Waiting、Offline` 状态组件。
- 表单支持字段校验、未保存提示和离开确认。
- 长对话、文档列表、任务事件流使用虚拟滚动。
- 补齐 Tab 顺序、焦点样式、快捷键和屏幕阅读器标签。
- 验证窄窗口、高缩放比例、深浅主题和中英文长文本。
- 所有外部打开动作都要有成功、失败和替代操作反馈。

## 十、统一完成标准

每个功能交付前必须同时满足：

- 界面状态来自真实后端数据，没有写死的完成度或数量。
- 正常、空、加载、部分可用、失败、离线和取消状态均有处理。
- 长任务可观察、可取消、可重试，重启后不会丢失关键状态。
- 高风险动作经过权限检查和审计，且不会绕过 Agent Runtime。
- 数据迁移、降级和失败回滚有测试。
- 用户可以从错误信息进入明确的修复或诊断路径。
- 产品介绍、设置、帮助文档与实际能力保持一致。
- 没有为了“看起来功能多”而保留的空壳入口。

## 十一、回归测试矩阵

P0 清理和每个后续切片完成后，都必须执行核心回归，防止删除假入口时破坏真实能力。

| 功能 | 测试路径 | 预期结果 |
| --- | --- | --- |
| 对话基本流程 | 新建对话 → 发送消息 → 查看回复 | 消息、状态和回复正常，没有终端或语音残留入口 |
| 文件产物 | 让 Agent 创建或修改文件 → 打开本轮产物 → 外部打开 | 文件标签、预览、所在目录和系统打开动作正常 |
| 知识库关键词检索 | 导入文档 → 搜索 → 查看结果 | 结果可用，状态只显示“关键词检索”或“仅关键词检索” |
| 知识库向量降级 | 未安装模型时选择知识库检索 | 不伪装向量就绪，自动降级并说明原因 |
| 新项目默认权限 | 修改默认权限 → 创建新项目 → 发起受限工具操作 | 项目真实读取并持久化该值，Runtime 按该权限拦截或放行 |
| 项目切换 | 在不同权限项目间切换 → 发起文件和工具操作 | 权限跟随当前项目，无跨项目继承和越权 |
| 数字同事启用 | 创建并触发数字同事 → 查看 Agent 页面与运行历史 | 显示真实状态，不出现“0 / 尚未启用”等写死内容 |
| 子 Agent | 创建子任务 → 查看事件、结果和产物 | 父子关系、状态和返回结果一致 |
| 插件开关 | 启用插件 → 重启 → 禁用插件 → 再次调用 | 状态持久化，禁用后能力不可被调用 |
| 通知静默策略 | 配置静默 → 运行长任务 → 触发审批 | 进度合并且不刷屏，审批仍按配置提醒 |
| 设置清理 | 遍历可见设置 → 修改 → 重启 → 触发对应功能 | 每项设置均有真实消费者，不存在只保存不生效的开关 |

测试分为三层：纯函数和状态映射单元测试、前端与 Tauri 网关集成测试、覆盖用户关键路径的端到端测试。涉及权限、迁移和索引代次的用例必须在 CI 中执行，不能只依赖人工回归。

## 十二、数据迁移策略

P0 和向量检索建设会影响 localStorage、知识库状态和数据库结构，必须在改字段之前定义老用户数据如何升级。

### 12.1 迁移范围

- 删除或忽略终端、语音及其他已下线功能对应的 localStorage 偏好。
- 将原有笼统知识库状态迁移为 `textIndexReady`、`vectorIndexReady`、当前检索模式和降级原因。
- 将旧“索引代次”语义拆分为文本索引代次与向量索引代次；不能默认把旧代次标记成向量代次。
- 为模型清单、模型安装、向量任务、通知偏好和诊断记录增加带版本的数据结构。

### 12.2 实施方式

1. 在 `apps/desktop/src-tauri/src/database/migrations.rs` 增加幂等、按版本顺序执行的数据库 migration。
2. localStorage 迁移单独维护版本号，成功迁移后再清理废弃键；重复启动不会重复执行或覆盖新值。
3. 首次检测到需要较长时间的数据升级时，显示专用迁移页面：“检测到旧版本数据，正在升级”，并展示当前步骤和进度。
4. 迁移前创建可识别版本的数据库备份；迁移成功并完成完整性检查后再切换到新结构。
5. 迁移失败时保留原数据和错误日志，优先提供自动回滚、重试和导出诊断。
6. “重置数据”只能作为最后手段，必须明确影响范围、再次确认，并优先允许用户导出或保留备份。

### 12.3 迁移验证

- 使用真实旧版数据库样本覆盖空库、纯关键词库、有未完成任务和异常数据等情况。
- 验证迁移前后文档数、分块数、项目权限、对话和插件状态不丢失。
- 验证旧知识库迁移后默认处于“仅关键词检索”，不会凭旧代次误判为向量就绪。
- 验证中途退出后再次启动可以安全继续或回滚。
- 验证新版应用拒绝打开高于自身支持版本的数据库，并给出可理解的处理方式。
