## 执行路径与 Kernel

- Fox 会话默认走 Kernel / Authoritative。Legacy 仍在代码里，只能用 `FOX_KERNEL_MODE=legacy` 显式开启，用于调试和兼容旧 Run；Legacy 和 Shadow 路径的清理（四 Agent 方案阶段 4）**还没开始**。
- [Issue #25](https://github.com/Hry1729/Fox-Agent/issues/25)：工作工具的 `attemptId` 仍由模型必填。保留历史的会话里模型容易重复使用 `attempt-1`，冲突会作为可纠正错误返回，但消耗连续拒绝预算（上限 5）。
- [Issue #24](https://github.com/Hry1729/Fox-Agent/issues/24)：纯文本任务只能用 `tool_call → tool_call` 作证据，证明“调用完成了”，不能证明结果正确；正确性依赖强验收。模型自我验证证据的方案待产品决定。
- 测试授权语义（四 Agent 方案阶段 1 第 2 项）**未关闭**：`test_run` 的授权按工具输入的哈希划定范围，可以选「本会话允许」，没有绑定工作区修订或脚本内容；授权之后脚本或依赖变了，不会重新审批。
- 子进程收尾（阶段 1 第 4 项）：Windows 用 Job Object 终止整棵进程树；非 Windows 只杀直接子进程。产品只发布 Windows。
- `plan_recovery` 纯函数没有接入生产启动恢复（生产使用 `recover_kernel_runs_detached`）。
- 真实进程崩溃后 UI 续跑的端到端验收没有找到记录；Resource Gateway 是否覆盖全部资源类别、React 是否全部只读 Kernel 快照，都**未逐项确认**。
- Runtime 能力清单声明 `dynamicModelSwitch: false`，运行中切换模型没有稳定协议保证。

## 外部 Agent（pi、DeepSeek Harness、Codex）

- **没有「自定义 ACP Agent」入口（待办）。** 只能用内置的 Fox、DeepSeek Harness（实验）、pi；用户不能自己接入其他 ACP Agent。
- Codex 已实现但界面隐藏：不能新建 Codex 会话（`agent_backend_hidden`），已有 Codex 会话照常可用。
- 会话创建后不能更换外层 Agent；外部会话不支持 resume（`agent_backend_entry_unsupported`），应用重启时外部 Run 会被标为中断。
- 外部会话启动 Run 时必须绑定项目（`agent_backend_project_required`）。
- 完全访问只在创建会话时授予，会话中只能撤销不能开启。
- DeepSeek 切换权限要到下一轮重启 dsh 才生效；Codex 的「帮我批准」只在 OpenAI 供应商下可用。
- 模型 API Key 按 base URL 全局共享：删除一个供应商会同时删掉同一地址其他条目在用的 Key（有意设计，不做检查）。
- 外部 Agent 的工具在其自身进程里执行，由 srt 沙箱和 ACP 权限请求约束，不经过 Fox Host 的工具门禁；能力按“审批覆盖 / 沙箱范围 / 取消能力 / 可观测性”声明，各后端覆盖程度不同，见 `crates/fox-agent-backend/docs/`。
- 真实外部 Agent 和 srt 沙箱测试默认关闭，不在 CI 里，依赖人工 Windows 复测（`sandbox.md` 第 13 节）。
- 外部 Agent 不在离线 Eval 范围内。

## Agent 与任务

- Child Run 深度最多 1；单个 Child Run 时长 1 秒–15 分钟（默认 5 分钟），受父 Run 剩余预算约束。Kernel 路径不再单独限制每个父 Run 的总数或同时活动数。共享项目没有自动 Git worktree，父 Agent 必须避免重叠的写任务。
- 以下条目沿用 2026-09-22 的结论，本次没有重新核对：
  - A1 已提供 PlanRevision、独立 Reviewer 与 Acceptance；不把任意 Task 状态变化升级为单独审批，审批聚焦计划版本和高风险工具。
  - A4 有本地 Span Tree 和离线评测历史，但没有 OTLP 导出、官方外部 benchmark 成绩或版本化货币成本表。
  - 远程 Yuxi Agent 不消费本地 Memory，也不参与本地 Child Run。
  - 每个会话最多一个 active Expert；Team v1 不支持 mailbox、共享任务领取或并行 Member。
  - 已有消息后不能在原会话热切换或移除专家，产品会新建 Assistant + Expert 草稿。
  - 知识库服务提供的远程 Expert 只注入名称、公开描述和资源元数据，不复用远端私有 System Prompt。
  - 专家能力包没有发布者签名、远程市场和信任分级。
  - Workflow 是有序 Stage 状态机，每会话最多一个 active Workflow；不支持 DAG、循环、动态 Stage 或后台自动续跑。
  - 数字同事不支持 Cron / 时区日历、并发队列、内置公网 Listener、专用 IM Adapter、实例热升级或私有 Memory Scope。
  - 专家详情的工作记录仍按基础 Assistant 聚合。
- 专家被删除后：正在运行的 Workflow 能否继续没有测试；数字同事所用专家被删后用户手动“恢复”再触发的行为没有测试（恢复时不检查专家是否存在）。

## 多模态与附件（沿用）

- 图片理解取决于模型配置、Runtime 能力声明和供应商协议，需要跨供应商验收。DeepSeek Harness 作为 Kernel 引擎时不接受图片：`services/agent-runtime/src/deepseek-kernel-adapter.mjs` 的 `deepSeekHistory` 遇到文本、思考、工具调用以外的内容块直接报错。
- 不支持的文件类型可能只能作为附件保留。
- 产物卡片没有接入按 Artifact ID 校验的 Host 文件网关，不能直接预览、系统打开或在文件管理器中定位。（沿用，本次未核对是否已改。）

## 知识库

- 远程智能体、知识库、原文件和知识图谱依赖外部知识库服务的可用性和接口兼容性。
- 远程 Office 文档用 Fox 客户端预览，不提供在线编辑和完全一致的排版。
- 本机资料库的聊天检索（`search_knowledge` 本地分支）仍只用关键词检索 `search_lexical`；向量和 RRF 混合检索只在检索测试入口可用。BM25 方案没有实施，见[本地知识库 BM25 计划](本地知识库-BM25向量与RRF-实施计划-2026-09-14.md)。
- 配置的资料库路径不可写时只读或空库降级，绝不回退到默认目录；`#[cfg(unix)]` 的降级测试在 CI 里没有执行过。

## 前端与性能（沿用）

- 生产构建仍有超过 500 kB 的 Chunk（知识图谱、Mermaid、Office 预览、语法高亮）。CI 会运行体积预算检查（`check-bundle-budget.mjs`）。
- `Workbench` 等大型页面承担较多状态编排。
- 大型 DOCX、PPTX、XLSX 和复杂图谱仍可能有明显内存和渲染压力。
- 设置页「通用」仍是旧的卡片结构，其余 6 页已用统一布局。

## 平台与安全

- 只在 Windows 上开发、验证和发布；CI 也只跑 Windows。
- Windows 人工测试必须以 Medium 完整性运行 exe（从普通目录启动），否则会出现与功能无关的“拒绝访问”或 `sandbox_unavailable`。
- Fox Host 的命令执行没有操作系统级隔离（沙箱、受限用户、ACL、防火墙）。生产没有经过验证的命令后端，任意 Shell 启动保持拒绝；固定能力工具（`git_read`、`test_run`、`code_check`、`format_code`）只有进程回收和资源限制，不是隔离（2026-10-25 已对照代码复核，见[安全架构](../02-架构/安全架构.md)）。
- `http_request` 只面向无需凭据的公网 API；认证 API 需要 OpenAPI Connector。`sqlite_read` 只支持项目内单条只读语句。（沿用）
- Tauri 已配置 `csp` 和 `devCsp`；缺浏览器端策略回归。
- MCP/OpenAPI 限制固定基址、禁止重定向、限制超时和响应大小；用户显式配置的本地或私网端点视为受信任配置，没有 OAuth、证书固定或细粒度速率配额。

## 数据与兼容

- SQLite 是本地事实源；降级不能依赖逆向迁移，要恢复迁移前备份（启动时自动备份，保留 5 份）。
- 迁移后的外键检查：父表是 `agents` 的孤立引用交给启动修复处理，其他外键问题仍会中止迁移并报可读错误。
- 历史阶段文档里的接口、进度和路径可能已经过时；以 [docs/README](../README.md) 的导航和常青文档为准。

## 验证与发布状态

- CI：`.github/workflows/windows-ci.yml` 有 6 个 job（`desktop-build` 20 分钟、`agent-runtime` 60 分钟、`rust-host` 45 分钟、`agent-backend` 45 分钟、`vector-runtime-smoke` 10 分钟、`onnx-runtime-smoke` 15 分钟），支持手动定向模式（只跑过滤后的 Rust Host 测试和 Runtime 打包检查）。两个 Smoke job 是资源门控的，缺官方 DLL / 模型包时跳过而不伪造成功。是否通过要看具体 run，不能从文件存在推出。
- 不在 CI 里的：安装包构建与验收、离线 Eval、Sidecar Smoke、Markdown 链接检查、`cargo fmt` / `clippy`、真实外部 Agent 和 srt 沙箱测试。
- 安装包：`tauri:build`、`tauri:build:windows`（NSIS）、`tauri:build:kernel-preview`（NSIS + `kernel-default`）。没有代码签名证书、更新服务器和 SBOM 流程。
- 没有浏览器端 e2e（无 Playwright / Cypress / Puppeteer）；`apps/desktop/scripts/` 下的 smoke 脚本是手工诊断用。
- 离线 Eval 的完整清单已扩到 129 个 case，但新基线没有重跑。
