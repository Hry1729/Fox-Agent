> 维护范围：当前产品与工程限制<br>

本文件记录已确认但尚未解决的限制，不代替 GitHub Issue。准备修复的事项应建立 Issue 并在此添加链接。页面、文件体验和 UI 的实施顺序见[App 产品能力完善清单](App产品能力完善清单.md)。

基线与成熟度口径（已实现/已提交/已推送/已发布/已验收）见[当前状态与核验基线](../01-项目概览/当前状态与核验基线.md)；本文件只写「限制是什么」，不重复基线数字。

## Agent 与任务

- A1 已提供 PlanRevision、独立 Reviewer 与 Acceptance；当前仍不把任意 Task 状态变化都升级为单独审批，审批 Gate 聚焦计划版本和高风险工具。
- A4 已提供本地 Span Tree 和离线评测历史，但尚无 OTLP 导出、官方外部 benchmark 成绩或版本化货币成本表。
- A2 Memory、A3 Fork/lifecycle 和 A5 Child Run 已落地；远程 Yuxi Agent 尚不消费本地 Memory，也不参与本地 Child Run 池。
- Runtime 能力清单当前声明 `dynamicModelSwitch: false`，运行中动态切换模型没有稳定协议保证。
- Child Run 只支持本地 Pi Agent、深度 1、每 root 并发 3、每父 Run 总数 8。上下文/进程已隔离，但共享项目没有自动 Git worktree；父 Agent 必须避免重叠 writer。
- 每个会话当前最多一个 active Expert；该 Expert 可以携带单 Agent Workflow 或串行 Supervisor Team。Team v1 不支持 mailbox、共享任务领取或并行 Member。
- 已有用户/助手消息后不能在原会话热切换或移除专家；产品会创建新的 Assistant + Expert 草稿。
- 远程历史会话继续保留兼容读取；五个内置 Expert 主会话由迁移 v20 自动转换，迁移 v21 冻结已有绑定在升级时可见的专家执行包。
- 知识库服务提供的远程 Expert 当前只把 Fox 可见的名称、公开描述和资源元数据注入本地运行时，不复用远端私有 System Prompt，也不会转交远端执行器；需要完整远端行为时仍走兼容历史会话。
- 专家能力包已支持本地 `.foxexpert` 导入导出、Hash 校验、升级、回滚、Schema v2 Workflow 与 Schema v3 Team；尚未提供发布者签名、远程市场与信任分级协议。
- Workflow 首版是有序 Stage 状态机，每个会话同一时间最多一个 active Workflow；不支持 DAG 分支、循环、动态 Stage 或后台自动续跑，Gate 后由下一次会话执行继续。
- 数字同事首版冻结专家版本和项目/知识作用域，支持严格非重叠的 Interval Schedule 与签名 Channel；不支持 Cron/时区日历、并发队列、内置公网 Listener、专用 IM Adapter、实例热升级或同事私有 Memory Scope。
- 专家详情工作记录仍按基础 Assistant 聚合，尚未增加按专家绑定的统计查询。

## 多模态与附件

- 附件上传和文本类读取已可使用；图片理解取决于模型配置、Runtime 能力声明和供应商协议，仍需跨供应商验收。
- 不支持的文件类型可能只能作为附件保留，不能保证模型理解其内容。
- 对话可以展示 Agent 产物记录，但产物卡片尚未接入按 Artifact ID 校验的 Host 文件网关，不能直接预览、系统打开或在文件管理器中定位。

## 知识库服务

- 远程智能体、知识库、原文件和知识图谱依赖外部知识库服务的可用性与接口兼容性。
- 服务不可用时本地 Fox 能力应降级可用，但远程列表和历史任务恢复可能暂时缺少最新状态。
- 远程 Office 文档采用 Fox 客户端预览，不提供在线编辑和完全一致的 Office 排版保证。
- 引用定位受服务返回的页码、文档结构和源文件映射质量影响。

## 前端与性能

- 生产构建仍存在部分超过 500 kB 的 Chunk，知识图谱、Mermaid、Office 预览和语法高亮是主要来源。
- `Workbench` 和部分大型页面承担较多状态编排，继续扩展前需要逐步拆分路由和业务边界。
- 大型 DOCX、PPTX、XLSX 和复杂知识图谱仍可能产生明显内存和渲染压力。

## 平台与安全

- 当前主要开发和人工验证环境是 Windows；其他桌面平台需要独立完成安装、文件选择、Keyring、图标和打包验收。
- `http_request` 只面向无需凭据的公网 API，必须逐次审批并精确列出 Host；认证 API 需配置 OpenAPI Connector。`system_info` 不返回进程命令行或任意环境变量。`sqlite_read` 只支持项目内 SQLite 单条只读语句，不是通用数据库客户端。
- 操作系统级隔离仍未完成：没有安装沙箱、受限用户、ACL 或防火墙规则。生产环境没有经过验证的命令后端，因此任意 Shell 启动保持拒绝（状态查询、输出读取和取消保留）；测试中的可用后端只在 `cfg(test)` 下存在，不能进入发布构建。内部自动命令推广需要先完成真实隔离后端验收。
- Tauri `app.security` 已配置 `csp` 和 `devCsp`（均非 `null`，见 `apps/desktop/src-tauri/tauri.conf.json`）。剩余工作是补充浏览器端策略回归，并对新增外部内容逐项收紧白名单。
- MCP/OpenAPI 与命令执行具有较高风险。当前扩展源限制固定基址、禁止重定向、限制超时/响应大小并保留健康与 Hook 审计；但用户显式配置的本地或私网端点仍属于受信任配置，尚无 OAuth、证书固定或细粒度操作速率配额。

## 数据与兼容

- SQLite 是本地事实源，但跨版本降级不能简单依赖数据库逆向迁移，应通过备份恢复流程处理。
- Runtime Session、远程任务和 SQLite 之间的恢复链路复杂，新增状态必须同时考虑异常退出与旧版本事件。
- 历史阶段文档中的接口、进度和路径可能已经过时；完成常青文档迁移前需要结合当前代码核实。

## 验证与发布状态

- **CI 存在但通过情况未在本轮核验**：`.github/workflows/windows-ci.yml` 有 5 个 job（desktop-build 20m、agent-runtime 60m、rust-host 45m、vector-runtime-smoke 10m、onnx-runtime-smoke 15m）。后两个是资源门控的，仓库缺官方 DLL/ONNX 包时显式跳过而不会伪造成功。远端是否对当前 HEAD 跑过、结果如何，需联网核对，不能从文件存在推出「CI 通过」。
- **安装包配置存在但没有本次产物哈希**：`tauri:build`（`bundle.targets = "all"`）、`tauri:build:windows`（NSIS）、`tauri:build:kernel-preview`（NSIS + `kernel-default`）。缺少代码签名证书、更新服务器与 SBOM 流程，未展示正式自动发布。没有与本次基线对应的安装包，就不能记录安装包验收结论。
- **浏览器端 e2e 未进入门禁**：根、`apps/desktop`、`services/agent-runtime` 三份清单中都没有 Playwright/Cypress/Puppeteer；`apps/desktop/scripts/` 下的 `prof-smoke.mjs`、`realapp-smoke.mjs`、`webview2-smoke.mjs`、`html-preview-smoke.mjs` 是手工/诊断脚本。前端目前以模型与工具函数测试为主。
- **跨平台未验收**：主要开发和人工验证环境是 Windows；macOS/Linux 的安装、文件选择、Keyring、图标和打包需要独立验收。
