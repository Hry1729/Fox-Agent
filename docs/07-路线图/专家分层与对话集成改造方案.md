# 专家分层与对话集成改造方案

> 状态：生效<br>
> 适用版本：Fox `0.1.x` 及后续版本<br>
> 维护范围：桌面端 Agent、专家中心、对话、SQLite、Tauri Command 与 Agent Runtime<br>
> 最后更新：2026-08-21

## 1. 结论摘要

Fox 应把当前混在同一 `Agent` 概念中的对象拆成三类：

1. **助手（Assistant）**：会话的基础执行者，可以出现在聊天输入框的助手下拉菜单中。
2. **专家（Expert）**：按会话绑定的专业人格与能力包，只从专家中心选择，不进入助手下拉菜单。
3. **工作成员（Worker）**：只供工作流或父 Agent 调用的子智能体，不出现在任何普通选择界面。

`conversations.agent_id` 继续表示基础助手；专家改为独立的会话绑定，不再通过替换 `agent_id` 占用会话主身份。第一阶段继续复用现有 `expertPackage`、Host 权限和 Pi Runtime，不引入 Child Run，也不把单上下文人格切换包装成“专家团队”。

专家选择后提供两种展示：

- 对话时间线插入一次可持久化的“已启用专家”卡片，用于回溯何时启用或更换专家。
- 当前专家使用一个紧凑胶囊持续显示在聊天框底部工具栏中，位置固定在 **“执行前询问”右侧**，不再放在输入框上方。

本方案的 P0-P2 及审查补强已于 2026-08-21 完成：数据库 Schema v21、Tauri 稳定错误码、前端草稿与恢复、专家中心/聊天菜单分层、时间线卡片、底部胶囊与工具状态、冻结执行包、Runtime Overlay、Prompt 预算、工具/MCP 权限交集诊断和历史内置专家会话迁移均已落地。

## 2. 目标与非目标

### 2.1 目标

- 清理聊天助手下拉菜单，只展示真正可作为会话基础执行者的助手。
- 保留专家中心的搜索、浏览、详情和“召唤专家”入口。
- 让专家成为会话的独立、可追踪、可恢复绑定。
- 在不削弱 Host 权限边界的前提下复用专家 Prompt、Skills、Tools、MCP 和知识资源。
- 为后续工作流专家、专家团队和数字同事保留清晰的数据与运行时扩展点。

### 2.2 非目标

- 本阶段不实现多个专家同时激活。
- 本阶段不实现 Child Run、Lead/Member、mailbox 或共享任务列表。
- 本阶段不实现远程专家市场、自动安装脚本或不受限 Hooks。
- 本阶段不允许专家包直接扩大文件、命令、网络、MCP 或知识库权限。
- 本阶段不重做模型选择、项目授权、知识库绑定和执行方式控件。

## 3. 当前问题与代码基线

当前桌面端把内置通用助手和调试、前端、审查、安全、架构等专家都写入同一张 `agents` 表；`list_agents` 返回全部记录，`Composer` 再直接渲染 `agents.map(...)`。因此只要新增 Agent，就会继续扩大聊天输入框下拉菜单。

同时，专家中心的“召唤专家”和聊天下拉菜单选择最终都会走“为该 Agent 创建会话”，导致：

- 会话基础助手和专业能力包没有语义区分。
- `conversation.agent_id` 同时承担“谁负责对话”和“当前加载什么专家”的双重职责。
- 对话中缺少可持久化的专家启用事件。
- Runtime 已经支持 `expertPackage`，但前端和数据层仍把专家当成顶层助手。

## 4. 概念与分类模型

### 4.1 三类对象

| 类型 | 语义 | 普通界面可见性 | 运行方式 | 第一阶段示例 |
| --- | --- | --- | --- | --- |
| `assistant` | 会话基础执行者 | 聊天助手下拉菜单 | `primary` | Fox 通用助手、明确标记为默认的远程助手 |
| `expert` | 专业人格与能力包 | 专家中心、对话专家卡片 | `inline` | 调试、前端、代码审查、安全、架构专家 |
| `worker` | 工作流内部成员 | 隐藏 | `child` | 知识库服务的 `is_subagent=true` Agent、未来团队成员 |

### 4.2 建议字段

Agent 记录增加以下明确字段，不再依赖名称或分类文本推断：

```text
agent_kind: assistant | expert | worker
invocation_mode: primary | inline | child
visibility: chat_selector | expert_center | hidden
```

第一阶段只允许下列组合：

| `agent_kind` | `invocation_mode` | `visibility` |
| --- | --- | --- |
| `assistant` | `primary` | `chat_selector` |
| `expert` | `inline` | `expert_center` |
| `worker` | `child` | `hidden` |

保留三个字段是为了避免未来把“工作流专家 Lead”“可见但不可直接对话的团队包”等对象再次塞回单一布尔值。Repository 保存时必须校验组合，前端不能自行改变运行类型。

## 5. 产品与交互方案

### 5.1 聊天助手下拉菜单

- 只展示 `agent_kind=assistant`、`visibility=chat_selector` 且当前可用的记录。
- 专家和 Worker 即使已经安装、同步或可运行，也不得出现在该菜单。
- 菜单仍表示“本会话由哪个基础助手负责”，不承担专家选择。
- 现有右侧助手选择控件保留，语音与发送按钮顺序不变。

### 5.2 专家中心召唤

用户在专家中心点击“召唤专家”后：

1. 读取专家详情、可用状态和能力摘要。
2. 没有活动会话时，创建以默认基础助手为主身份的草稿会话。
3. 为会话写入专家绑定，而不是把 `conversation.agent_id` 改成专家 ID。
4. 写入一条专家启用记录，供对话时间线渲染卡片。
5. 返回聊天页；`defaultInitPrompt` 只预填输入框，不自动发送。

已有消息的会话默认选择“在新对话中使用”。第一阶段不支持在已有上下文中直接热切换专家，以避免旧人格、旧工具结果和新专家规则互相污染。空草稿或尚未发送首条消息的会话可以原位更换。

### 5.3 输入框底部专家胶囊

专家胶囊放入 `PromptInputFooter` 的左侧 `PromptInputTools`，紧跟执行方式控件之后：

```text
[＋] [执行前询问 ▾] [专家头像 专家名 ▾]      [Fox 通用助手 ▾] [语音] [发送]
```

交互约束：

- 没有激活专家时不显示空胶囊，避免增加固定噪声。
- 激活后显示 `16px` 左右头像、专家短名称和下拉箭头。
- 名称过长时单行截断；窄窗口优先保留头像和截断后的名称。
- 点击胶囊打开轻量菜单：查看详情、更换专家、移除专家。
- 运行中、等待审批或等待用户补充时允许查看详情，但禁用更换和移除。
- 胶囊属于当前会话状态，不属于待发送消息内容，不随输入框清空消失。
- 胶囊不得移动到右侧发送区，也不得重新放回输入框上方。

实现位置以 `apps/desktop/src/features/chat/workbench.tsx` 的 `Composer` 为准。组件应拆成独立的 `ExpertBindingChip`，避免继续扩大 `Composer` 的条件分支。

### 5.4 对话时间线专家卡片

首次启用专家时，在对话时间线中插入一张紧凑卡片：

- 标题：`已启用 {专家名称}`。
- 内容：头像、职业/分类、一行说明。
- 能力摘要：最多展示 Skills、知识、MCP、工具范围中的三项摘要，不展示完整 Prompt。
- 状态：可用、资源缺失、服务离线或版本不可用。
- 操作：查看专家详情；历史卡片不直接执行更换或移除。

卡片是 Host-owned 会话事件，不应作为普通用户消息或 Runtime 对话文本发送给模型。刷新、重启和历史会话加载后必须出现在原位置。

### 5.5 更换与移除规则

| 会话状态 | 更换专家 | 移除专家 |
| --- | --- | --- |
| 空草稿、未发送首条消息 | 原位更换 | 允许 |
| 已有用户或助手消息 | 默认新建对话 | 第一阶段默认新建无专家对话 |
| Runtime 运行中 | 禁止 | 禁止 |
| 等待审批或用户补充 | 禁止 | 禁止 |
| 历史只读或已归档 | 禁止 | 禁止 |

后续如要支持“从下一轮切换”，必须增加明确的生效消息边界、Runtime Snapshot 和时间线切换事件，不得只更新一个当前专家 ID。

“空草稿、未发送首条消息”的代码判定固定为：会话中不存在 `role=user` 或 `role=assistant` 的消息。`defaultInitPrompt` 等输入框预填内容只存在于前端草稿，不参与判定；专家启用卡片来自绑定表和 Host 时间线，也不参与消息计数。

## 6. 数据模型方案

### 6.1 保留基础助手绑定

`conversations.agent_id` 保持现有职责，但语义收窄为“基础助手 ID”。新建会话必须引用 `assistant/primary/chat_selector` 组合的 Agent。

### 6.2 新增专家绑定表

建议新增 `conversation_expert_bindings`：

```text
id                    TEXT PRIMARY KEY
conversation_id       TEXT NOT NULL
expert_id             TEXT NOT NULL
state                 TEXT NOT NULL  -- active | replaced | removed
activation_source     TEXT NOT NULL  -- expert_center | draft | migration
expert_version        TEXT
package_hash          TEXT
display_snapshot_json TEXT NOT NULL
package_snapshot_json TEXT NOT NULL
activated_at          TEXT NOT NULL
deactivated_at        TEXT
```

约束：

- 同一会话最多一条 `state=active` 的绑定。
- `expert_id` 必须引用 `agent_kind=expert` 的记录。
- `display_snapshot_json` 只保存历史卡片所需的名称、头像、描述和分类，不保存密钥或完整 Prompt。
- `package_snapshot_json` 保存绑定时的静态专家执行包；`package_hash` 对该快照计算。后续专家定义发生修改时，既有会话继续使用绑定版本，新绑定才使用新版本。
- 每次 Run 只在静态专家快照上重新叠加当前 Host 授权、会话知识绑定和允许启用的 Skills，不从最新专家定义覆盖 Persona、Manifest 或资源声明。
- 完整运行时能力包继续进入每次 Run 的 Request Snapshot；展示快照和执行快照职责分离。
- 更换时关闭旧绑定并新增绑定，不覆盖历史行。
- 删除专家记录前必须处理历史绑定；历史展示优先使用快照，不因专家删除而消失。

### 6.3 前端类型

建议增加：

```ts
type AgentKind = 'assistant' | 'expert' | 'worker'
type AgentInvocationMode = 'primary' | 'inline' | 'child'
type AgentVisibility = 'chat_selector' | 'expert_center' | 'hidden'

type ConversationExpertBinding = {
  id: string
  conversationId: string
  expertId: string
  state: 'active' | 'replaced' | 'removed'
  expertVersion?: string
  packageHash?: string
  displaySnapshot: ExpertDisplaySnapshot
  packageSnapshot: ExpertPackageSnapshot
  activatedAt: string
  deactivatedAt?: string
}
```

会话加载结果应直接返回当前绑定和历史绑定，避免前端通过 Agent 列表反推。

## 7. Runtime 与权限组合

### 7.1 Prompt 分层

推荐顺序：

```text
Fox/Runtime 基础契约
  -> 基础助手 System Prompt
  -> 专家 Persona Overlay
  -> 专家 Skills/资源上下文
  -> 项目、知识库和动态低权限上下文
  -> 用户消息
```

不采用 WorkBuddy 式“专家人格完全替换基础 Persona”。基础助手、Host 权限、安全边界和 Runtime Contract 必须保留；专家只能在明确边界内增加专业身份与方法。

Prompt 组合必须按当前模型上下文窗口执行预算：Host/Runtime 基础契约不可被专家截断；基础助手、专家 Persona、Skills 和动态上下文分别记录长度，并按低权限动态上下文、专家附加上下文、助手附加上下文的顺序收缩。默认诊断只记录 Hash、字符数和 Token 估算，不输出完整 Prompt。

### 7.2 能力与权限

- 专家 Manifest 声明的是所需能力，不是最终授权。
- 有效工具范围必须是 Host Capability、基础助手约束和专家 Allowlist 的交集。
- Skills 可以组合加载，但不能通过 Skill 正文扩大工具权限。
- MCP 必须经过现有配置、凭据和 Host 审批流程。
- 知识库只有在用户可访问且会话已绑定时才能提供给专家。
- 工具与 MCP 交集在每次 Run 开始时重新计算；会话中途改变的配置从下一次 Run 起体现在工具目录中，Host 的实时 Preflight 和审批仍可立即拒绝当前 Run 的调用。
- Request Snapshot 必须同时记录基础助手 ID、专家绑定 ID、专家版本、Package Hash、Assistant/Expert 声明工具、最终有效工具，以及被排除工具和原因。
- 专家胶囊主体保持简洁；最近一次 Run 的 `有效/声明` 工具数量和“无工具但可纯文本回答”状态放入胶囊下拉详情。

### 7.3 错误与降级

- 新绑定专家离线、缺失或分类无效时拒绝绑定，并返回稳定错误码和可执行提示。
- 既有绑定的展示优先使用 `display_snapshot_json`；运行优先使用经过 Hash 校验的 `package_snapshot_json`，不依赖专家当前定义仍然存在。
- 执行快照缺失、损坏或 Hash 不一致时禁止静默切换到最新专家，Run 失败并提示重新选择专家。
- 权限交集为空不是运行错误；Runtime 保留纯文本回答能力，并在 UI 中显示当前无可用工具。

### 7.4 性能边界

- Run 准备阶段按 Assistant/Expert ID 定点读取，不全量加载 Agent 列表。
- 活动绑定必须命中 `conversation_id + state=active` 索引；测试使用大样本验证查询计划，不使用脆弱的严格毫秒断言。
- Request Snapshot 记录 Prompt 规模和工具规模，便于定位专家叠加带来的首 Token 延迟。

### 7.5 Runtime 协议建议

现有 `agentId/systemPrompt` 保留基础助手语义；`expertPackage` 改为可选的独立专家能力包，并增加绑定元数据：

```json
{
  "agentId": "fox-general",
  "expertBinding": {
    "bindingId": "...",
    "expertId": "fox-reviewer",
    "version": "...",
    "packageHash": "..."
  },
  "expertPackage": {}
}
```

Runtime 不根据专家名称自行选择工具或工作流。没有绑定时 `expertBinding` 与 `expertPackage` 都为空。

## 8. 兼容与迁移策略

### 8.1 内置 Agent 分类

| 现有 ID | 新分类 |
| --- | --- |
| `fox-general` | `assistant/primary/chat_selector` |
| `fox-debugger` | `expert/inline/expert_center` |
| `fox-frontend` | `expert/inline/expert_center` |
| `fox-reviewer` | `expert/inline/expert_center` |
| `fox-security` | `expert/inline/expert_center` |
| `fox-architect` | `expert/inline/expert_center` |

### 8.2 远程 Agent 分类

- `is_subagent=true` 映射为 `worker/child/hidden`。
- 明确标记为默认或允许进入聊天选择器的远程 Agent 映射为 `assistant/primary/chat_selector`。
- 其他顶层远程专业 Agent 默认进入 `expert/inline/expert_center`，避免再次污染聊天菜单。
- 同步失败或服务离线只改变 `available`，不能丢失本地分类和历史绑定。

### 8.3 历史会话

- 使用 `fox-general` 的历史会话保持不变。
- 使用五个内置专家作为 `conversation.agent_id` 的历史会话，在迁移时改为 `fox-general` 基础助手，并生成 `activation_source=migration` 的专家绑定。
- “远程 Runtime 历史会话”明确指 `conversation.agent_id` 仍指向 `runtime_type=yuxi` Agent、且没有新专家绑定的既有会话；它们继续按旧链路读取和恢复，避免改变远程线程身份。
- 新会话只允许使用新模型。只有远程 Expert inline 执行、远程线程恢复和历史迁移全部具备等价语义并通过迁移测试后，才移除兼容分支；不按固定日期或版本号强制删除。

## 10. 实施顺序

### P0：分类与菜单收口

- 增加 Agent 分类字段和迁移。
- 将内置专家从聊天下拉菜单移到专家中心。
- 映射远程 Sub-agent 为隐藏 Worker。
- 不改变 Runtime 行为，先解决菜单混乱。

### P1：会话专家绑定与交互

- 增加 `conversation_expert_bindings`。
- 专家中心召唤改为绑定到默认助手会话。

## 11. 测试与验收

### 11.1 自动化测试

- Agent 分类组合校验和迁移幂等。
- `list_agents` 按使用场景过滤，不误返回 Expert 或 Worker。
- 同一会话只能存在一个活动专家绑定。
- 专家启用、更换、移除和会话删除事务一致。
- Runtime Prompt 顺序稳定，专家不能覆盖 Host 约束。
- 有效工具范围满足交集规则，专家不能扩大权限。
- Request Snapshot 包含基础助手和专家绑定事实。
- 绑定后修改专家定义不会改变既有会话的静态执行包，Package Hash 校验失败会阻止运行。
- Prompt 超长时按预算收缩且保留 Host/Runtime 契约，并记录长度诊断。
- Request Snapshot 分别记录声明、有效和被排除工具；空工具交集仍可纯文本回答。
- 远程专家离线、快照损坏和绑定锁定返回稳定错误码。
- 大量 Agent 和历史绑定下，Assistant/Expert 定点查询与活动绑定查询继续命中索引。
- 远程 Sub-agent 不进入聊天下拉菜单。

### 11.2 前端验收

- 聊天下拉菜单只显示助手。
- 专家中心点击“召唤专家”后返回聊天页并显示时间线卡片。
- 专家胶囊位于聊天框底部、“执行前询问”右侧。
- 胶囊不挤占右侧助手、语音和发送按钮。
- 窄窗口、长专家名、暗色主题和高对比主题显示正常。
- 刷新与应用重启后，胶囊和历史卡片都能恢复。
- 运行、审批和用户补充期间不能更换或移除专家。
- 知识库服务离线时，远程专家显示不可用但历史绑定不丢失。

### 11.3 负向验收

- 未选择专家的普通对话 Prompt、工具和 UI 不发生变化。
- 专家卡片和胶囊内容不进入用户消息或模型上下文。
- 删除专家后历史会话仍能显示专家快照。
- 历史远程会话仍能加载和恢复。
- 专家 Manifest 请求的工具不在 Host 授权范围时必须被拒绝。

## 14. 已确认决策

- 聊天助手下拉菜单只展示 Assistant。
- Expert 从专家中心选择，不进入聊天助手下拉菜单。
- Worker 始终隐藏，只供内部调度。
- `conversation.agent_id` 保留基础助手语义。
- 第一阶段每个会话最多激活一个 Expert。
- 专家胶囊位于聊天框底部、“执行前询问”右侧。
- 专家启用卡片进入对话时间线，但不进入模型消息。
- 已有消息的会话默认新建对话使用新专家。
- 专家不能扩大 Host 权限。
- 专家团队必须等待 A5 Child Run，不使用单上下文角色扮演替代。
