# 基础 Agent 核心能力对比

> 状态：维护中<br>
> 适用版本：Fox `0.1.x`<br>
> 维护范围：Fox、Maka、Kun、DeepSeek-Reasonix 与 OpenAI Codex 的基础 Agent 能力<br>
> 最后更新：2026-08-26

本文不比较谁接了更多模型、插件、知识库和外部服务，而是把一个 Agent 最基础的九项能力拆开来看：循环、状态、工具、验证、Prompt、安全、规划、记忆和多 Agent。每一项都先用大白话解释，再说明 Fox、Maka、Kun、DeepSeek-Reasonix 和 Codex 分别做得好的地方。

更偏源码、具体 Prompt 原文和文件位置的对比，见[Fox 与主流 Agent 能力及 Prompt 对比](Agent能力与Prompt对比.md)。

## 先建立一个最简单的认识

可以把 Agent 想成一个被派去独立办事的人：

| Agent 组成 | 大白话比喻 | 缺少以后会怎样 |
| --- | --- | --- |
| 模型 | 脑子 | 理解不了问题，也做不出判断 |
| Prompt | 岗位说明书和做事规矩 | 有脑子，但不知道职责、原则和边界 |
| 工具 | 手、脚、电脑和电话 | 会想、会说，但不能真正改变外部世界 |
| 循环 | 做一步、看结果、再做下一步的工作节奏 | 只能尝试一次，遇到问题就停 |
| 状态 | 手里的任务单和工作笔记 | 做着做着忘记目标、进度和失败原因 |
| 验证 | 完工后的检查和验收 | 做完就自认为成功，实际结果可能不可用 |
| 权限 | 门禁卡、预算和审批制度 | 要么什么都做不了，要么可能越权乱做 |
| 规划 | 开工前的步骤、依赖和分工 | 复杂任务容易顺序混乱、漏步骤 |
| 记忆 | 个人经验和公司档案 | 每次都从零开始，或者重复犯错 |
| 多 Agent | 带领一个团队协作 | 可以扩大规模，但管理不好会把错误也放大 |

因此，Agent 不是“一个很长的 Prompt”，也不是“模型能调用工具”这么简单。一个真正能办事的 Agent，至少需要形成下面这个闭环：

```text
理解目标
   ↓
查看当前状态
   ↓
选择并调用工具
   ↓
读取真实结果
   ↓
检查结果是否合格
   ├── 不合格：分析原因、调整、重试
   └── 合格：继续下一步或结束
```

## 重要性排序

假设五个项目使用水平接近的底层模型，我对基础 Agent 能力的排序如下：

| 排名 | 能力 | 为什么排在这里 |
| ---: | --- | --- |
| 1 | 闭环执行 | 决定它究竟是“一次性回答器”，还是能持续把事情办完的 Agent |
| 2 | 任务状态 | 决定它能不能一直记得目标、进度、结果和剩余工作 |
| 3 | 可靠工具 | 决定它能不能真正读、写、运行和查询，而不只是提出建议 |
| 4 | 验证与纠错 | 决定“做过了”能不能变成“真的做好了” |
| 5 | Prompt 与行为策略 | 决定它遵循什么原则、怎样使用工具、什么时候停止 |
| 6 | 权限与安全 | 决定它能否在真实环境中被放心地授权执行 |
| 7 | 任务拆解与计划 | 决定复杂任务能否按正确顺序推进并处理依赖 |
| 8 | 上下文与记忆 | 决定长任务能否续跑、跨任务能否积累经验 |
| 9 | 多 Agent 与扩展生态 | 决定能力能否并行放大，但必须建立在前八项可靠的基础上 |

这个排序不是说 Prompt 或记忆不重要，而是强调依赖关系：没有循环，再好的 Prompt 也只能指导一次回答；没有真实工具和验证，再聪明的计划也可能停留在口头上；单 Agent 闭环不可靠时，多 Agent 通常只会更快地产生更多不可靠结果。

## 1. 闭环执行能力

### 大白话解释

闭环就是：Agent 做完一步后，必须看这一步实际发生了什么，再决定下一步。

例如让 Agent 修复一个程序错误。真正的闭环不是“读代码后给一段修改建议”，而是：

1. 读取报错和相关代码。
2. 找到最可能的原因。
3. 修改文件。
4. 运行测试。
5. 如果测试失败，读取新错误并继续修改。
6. 测试通过后，检查是否误伤其他功能。
7. 确认目标完成，再向用户交付。

闭环最怕两个问题：一是工具一调用就认为成功，二是没有明确停止条件，导致 Agent 提前结束或无意义地反复执行。

### 五个 Agent 的优点

| Agent | 做得好的地方 | 大白话理解 |
| --- | --- | --- |
| Fox | Run/Event、工具返回、审批、恢复和工作对象连成完整过程 | Fox 不只关心“说了什么”，还关心“事情进行到哪一步、留下了什么证据、是否已经验收” |
| Maka | 事件溯源式 Runtime 和耐久 TaskRun | 像给整个办事过程装了行车记录仪；中途出错或重启后，能根据记录继续 |
| Kun | Graph Lead 监督节点执行、审查、修复和集成 | 像一个项目负责人，不只是把活分下去，还会追问每个人有没有做好，并把结果合起来 |
| Reasonix | Executor/Planner 双模式，循环较短、结构轻 | 像一名轻装上阵的执行者，少开会、少留复杂表格，适合快速完成明确任务 |
| Codex | 编码循环成熟，强调持续执行到问题真正解决 | 像经验丰富的工程师：查看代码、修改、运行测试、读错误、继续修，直到可以交付 |

### 各自最突出的地方

- **Fox** 的优势是闭环里有治理对象。它不是简单地多跑几轮，而是能把 Goal、Task、Evidence、Review Finding 和 Acceptance 串起来。
- **Maka** 的优势是循环耐久。重点是“运行很久、中间断过，也能够知道之前发生了什么”。
- **Kun** 的优势是监督循环。它特别重视子任务完成后的 Review 和 Repair。
- **Reasonix** 的优势是轻。基础循环没有太多额外负担，适合终端里的直接任务。
- **Codex** 的优势是编码执行纪律成熟。对真实代码库的查看、修改、验证和继续推进处理得很系统。

如果只看“最基础的执行循环”，Codex 更像成熟的编码执行者，Maka 更像耐久 Runtime，Kun 更像任务总监，Fox 更像带验收制度的工作系统，Reasonix 则像轻量而直接的个人执行助手。

## 2. 任务状态管理

### 大白话解释

状态就是 Agent 在工作过程中需要持续记住的“当前事实”：

- 用户最终想得到什么。
- 当前做到哪一步。
- 哪些步骤成功了。
- 哪些步骤失败了，为什么失败。
- 调用了哪些工具，工具真实返回了什么。
- 哪些事情正在等审批或外部条件。
- 剩余工作是什么。

状态不等于聊天记录。聊天记录像会议录音，内容很多，但很难快速知道任务现在到底是什么情况；结构化状态更像项目看板，一眼能看到待办、进行中、已完成和阻塞。

### 五个 Agent 的优点

| Agent | 状态保存方式的特点 | 大白话理解 |
| --- | --- | --- |
| Fox | Goal、Task、Plan Revision、Evidence、Finding、Acceptance、Run/Event 分开保存 | 不只保存聊天，而是保存一整套任务台账、质检单和验收单 |
| Maka | TaskRun、Task Ledger、事件历史和会话上下文分层 | 工作日志很细，而且把“长期任务台账”和“当前对话内容”分开 |
| Kun | Graph 节点保存任务依赖、负责人、进度和结果 | 像项目管理软件里的任务图，适合看多个子任务怎样汇总成最终结果 |
| Reasonix | 会话与配置状态较轻，尽量减少复杂持久对象 | 像个人待办本，信息少、启动快，适合不需要重治理的任务 |
| Codex | Thread、Turn、Goal、Plan、Compaction 和恢复状态完整 | 像持续工作的开发任务：对话很长也能压缩，之后继续接着做 |

### 怎么理解它们的差别

假设任务是“调研三个竞品、修改两处代码、运行测试、写一份报告”：

- Fox 会更关心每项工作对应哪个 Task、产生了什么 Evidence、谁做了 Review、最终是否 Acceptance。
- Maka 会更关心整个 TaskRun 经历了哪些事件，断开后怎样恢复，Prompt 或执行策略变化后结果有什么不同。
- Kun 会把调研、代码、测试和报告拆成图节点，标出依赖，让 Lead 监督节点完成并修复不合格结果。
- Reasonix 会尽量用较少的状态完成任务，不主动建立很重的业务对象。
- Codex 会保持编码任务的当前计划、工具结果和会话摘要，长时间工作后仍能继续。

这一项 Fox 的优势最明显：它把状态做成了产品事实，而不是只留在模型上下文中。Maka 的耐久事件记录和 Kun 的图状态，则分别值得 Fox 在恢复能力和并行执行上学习。

## 3. 可靠的工具调用

### 大白话解释

工具就是 Agent 真正干活的手。常见基础工具只有几类：

- 读文件和搜索内容。
- 写文件和修改代码。
- 执行命令和测试。
- 查询数据库、网页或服务。
- 请求审批或调用其他 Agent。

工具不是越多越好。五个稳定、反馈清楚的工具，通常比五十个名字相似、权限模糊、结果不统一的工具更有用。

可靠工具至少要满足：输入格式明确、权限范围明确、结果真实返回、失败原因可理解、重复执行后果可控、Agent 不能把“准备调用”说成“已经调用”。

### 五个 Agent 的优点

| Agent | 工具体系的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | 工具经过 Host 权限边界；支持项目文件、命令、MCP、OpenAPI、Hooks、知识库和通用工具 | 工具都要走前台登记和门禁，方便统一控制、审计和诊断 |
| Maka | Runtime 对工具事件记录细，Headless 场景便于自动运行和分析失败 | 不只知道工具失败，还能把工具失败纳入实验和回放 |
| Kun | 根据本轮真实可用工具动态生成偏好；不同工作台有不同工具组合 | Agent 不会只背一份固定工具说明，而是看自己当前手上有什么再决定怎样做 |
| Reasonix | MCP 可组合 Tools、Prompts、Resources，扩展 Sidecar 较轻 | 像插上一个小模块就增加一组能力，不需要把宿主改得很重 |
| Codex | 文件、Shell、Patch、搜索、MCP 和协作工具与 Sandbox/Approval 深度结合 | 编码工具成熟，而且模型清楚哪些能直接用、哪些要先申请 |

### 真正应该关注什么

评估工具能力时，不要只数工具数量，应问：

1. Agent 是否知道这个工具当前真的存在？
2. 调用后是否获得机器返回，而不是自己猜结果？
3. 工具失败后是否能读懂原因并换方案？
4. 写文件和执行命令是否限制在授权范围？
5. 工具输出是否被当作不可信数据，避免其中的文字反过来控制 Agent？
6. 工具调用是否能进入日志、证据和验收？

Fox 的长处是治理统一，Codex 的长处是编码工具成熟，Kun 的长处是按场景动态匹配工具，Maka 的长处是工具事件可实验、可回放，Reasonix 的长处是轻量组合。

## 4. 验证与纠错能力

### 大白话解释

验证就是 Agent 做完以后不能只说“好了”，而要拿出能证明结果正确的信号。

例如：

- 修改代码后运行对应测试。
- 写完网页后执行构建并检查页面。
- 更新数据库后查询目标记录。
- 生成文件后确认文件存在、格式正确、内容完整。
- 调研事实后核对原始来源和时间。

纠错则是验证失败后的下一步：定位失败原因、决定是修代码、换工具、缩小范围、回滚，还是向用户说明真正的阻塞条件。

### 五个 Agent 的优点

| Agent | 验证与纠错的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | Evidence、Reviewer、Finding 和 Acceptance 都有持久对象；失败可恢复、重试和诊断 | 不接受一句“我检查过了”，要求有证据、有问题单、有最终验收 |
| Maka | Headless Eval、任务回放、工具失败摘要和 Prompt 对照实验 | 不只检查一项任务，还能批量比较“换 Prompt 后整体变好还是变坏” |
| Kun | Graph Lead Review/Patch/Repair 工具链，审查结果结构化 | 子 Agent 交作业后，Lead 会质检；不合格可以创建修复动作 |
| Reasonix | 内置 Review/Test Skills，强调只读检查和聚焦结果 | 临时请一个专门检查的人进来，不让它顺手改乱其他地方 |
| Codex | 强调根因修复、按风险验证、测试失败后继续推进 | 不满足于让报错消失，更重视是否真正解决根因且没有引入回归 |

### 谁在哪种验证上更强

- **单次编码任务的验证纪律**：Codex 很成熟。
- **结构化证据和业务验收**：Fox 最有特点。
- **多节点审查与自动修复**：Kun 最值得参考。
- **批量 Prompt/策略回归评测**：Maka 最完整。
- **轻量、按需调用专门审查者**：Reasonix 很干净。

Fox 下一步最适合把这几类验证合在一起：继续保留 Evidence/Acceptance，同时引入 Kun 的节点 Review/Repair，以及 Maka 的跨任务回归评测。

## 5. Prompt 与行为策略

### 大白话解释

Prompt 是给 Agent 的岗位说明书和工作规章，主要回答：

- 你是谁，负责什么。
- 什么指令优先，什么内容只可以当资料。
- 什么时候调用工具，什么时候询问用户。
- 怎样处理错误和不可信内容。
- 什么算完成，什么时候停止。
- 最终结果应该怎样交付。

Prompt 很重要，但它不能凭空创造系统没有的能力。Prompt 写了“必须验证”，运行时却没有测试工具，Agent仍然无法验证；Prompt 写了“不要越权”，工具层却允许访问所有目录，也不能只靠模型自觉保证安全。

### 五个 Agent 的优点

| Agent | Prompt 的突出优点 | 大白话理解 |
| --- | --- | --- |
| Fox | 稳定指令与动态上下文分层，有权威度、预算、截断和 Hash；强调工具真实性与不可信输入 | 像把公司制度、岗位说明、当前项目和本轮任务分开放，不让它们混成一团 |
| Maka | Prompt A/B、候选循环、回放、优化和固定版本控制 | 像产品做实验：不是凭感觉改一句，而是拿同一批题测试新旧版本谁更好 |
| Kun | Graph、Review、Design、SDD 等场景都有专用 Prompt | 像给项目经理、审查员、设计师分别发不同操作手册，而不是所有人共用一份说明 |
| Reasonix | 基础 Prompt 短，目录指令和 Skills 按需加载，缓存友好 | 平时只背最重要的规章，需要做审查或测试时再翻对应手册 |
| Codex | Base、Permissions、Personality、Goal、Mode、Plugins、Apps、World State 等模块化组装 | 每类信息都有独立卡片，权限变化只换权限卡，不需要重写整本说明书 |

### 五种不同的优秀思路

1. **Fox：分层和治理。** 重点是不同内容具有不同权威度，确认记忆是事实，不应冒充高优先级指令。
2. **Maka：可实验。** 重点是 Prompt 改动必须有任务集、对照组和数据结果。
3. **Kun：按职业写专用手册。** 重点是 Graph Lead、Reviewer 和 Designer 的任务语言不同。
4. **Reasonix：保持短小。** 重点是稳定内容尽量不变，高变化方法论按需加载。
5. **Codex：类型化拆分。** 重点是权限、人格、目标、环境和协作模式各自独立。

对 Fox 而言，最佳组合不是选其中一个，而是：保留 Fox 的权威度和真实性规则，学习 Maka 的实验体系、Kun 的专用角色契约、Reasonix 的按需加载、Codex 的类型化片段。

## 6. 权限与安全边界

### 大白话解释

Agent 的安全不是“提醒它小心一点”，而是系统真正限制它能做什么。

例如一个 Agent 负责修改某个项目，它可以获得该项目的读写权限，但不应该因此自动获得整个硬盘、所有网络服务和全部凭据。子 Agent 也不能因为被委派，就获得比父 Agent 更大的权限。

安全边界通常包括：目录范围、读写范围、命令执行、网络访问、凭据使用、预算、超时、审批、日志和取消能力。

### 五个 Agent 的优点

| Agent | 安全方面的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | Host 收口系统权限、授权项目根、审批策略、Keyring、审计和子 Agent 权限交集 | 模型只是提出申请，门禁由系统掌握；派给下属的门禁卡不会比自己更高级 |
| Maka | 个性化和环境信息明确标为低优先级、不授予权限；隔离执行思路清晰 | 用户偏好和环境说明只是资料，不能拿一句文本当通行证 |
| Kun | Graph Lead/节点有授权检查、写入 Scope 继承和专用边界工具 | 项目负责人能监督任务，但只能在节点被批准的范围里操作 |
| Reasonix | Instruction Import、路径、Git 根和符号链接边界处理细 | 即使规则文件通过链接绕路，也不能偷偷读到项目外面 |
| Codex | Sandbox Mode、Approval Policy、命令权限和子 Agent 权限继承系统化 | Agent 清楚自己在沙箱里能做什么；越界操作必须走明确审批 |

### 为什么这一项不能只靠 Prompt

Prompt 属于“要求”，Host/Sandbox 属于“强制执行”。两者都要有：

- 只有 Prompt：像墙上写着“闲人免进”，但门没有锁。
- 只有 Sandbox：门锁得很好，但办事的人不知道为什么进不去，也不知道如何申请。
- Prompt 加 Host/Sandbox：既有清楚规章，也有真正门禁，还能在需要时走审批。

Fox 在这一项基础较好。未来增加并行 Child Run 或自动 Worktree 时，仍应坚持权限交集、预算和审计，而不是为了更自主而放松边界。

## 7. 任务拆解与计划

### 大白话解释

计划能力不是让 Agent 每次都输出一份很长的计划，而是让它判断：

- 这个任务是否需要拆分。
- 哪些步骤有先后依赖。
- 哪些步骤可以同时做。
- 每一步预期产物是什么。
- 怎样判断每一步完成。
- 哪一步失败会影响后续工作。

简单任务不需要复杂计划。例如改一个错别字，直接改和检查就够了。复杂任务才需要显式计划，否则规划本身会变成额外开销。

### 五个 Agent 的优点

| Agent | 规划方面的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | 有只读 Planner、Plan Revision、Task、Goal 和 Acceptance | 计划员只负责把事情想清楚，执行者负责动手；计划变化还能留下版本 |
| Maka | Graph Mode、Task Ledger 和耐久记录配合 | 计划不是一次性文字，而是可以随着执行持续更新的工作图和台账 |
| Kun | Graph Lead 对建图、派发、依赖、监督、修复和交付全部负责 | 最像真正的项目经理，尤其擅长把复杂任务变成团队任务图 |
| Reasonix | Planner/Executor 分离，Skills 能提供临时方法论 | 需要规划时切到规划者，需要执行时回到执行者，保持整体轻量 |
| Codex | Plan、Goal continuation 和执行状态结合，强调计划与实际进度同步 | 不把计划写完就扔掉，而是边做边更新，直到目标真实完成 |

### 当前最值得 Fox 学习的地方

Fox 已有 Planner 和结构化工作对象，但 Planner 输出目前更像顺序步骤。Kun 的 Graph Lead 更进一步：明确依赖、并行关系、节点接受标准和失败后的 Repair。Maka 则证明计划图应当与耐久事件记录结合。

因此 Fox 的合理演进不是“让 Planner 写得更长”，而是让它输出可以被 Host 执行和验证的任务图：

```text
节点 A：调研
  产物：对比表
  验收：每项结论有源码依据

节点 B：实现功能
  依赖：A
  产物：代码修改
  验收：相关测试通过

节点 C：更新文档
  可与 B 后半段并行
  验收：链接有效、与实现一致

节点 D：总审查
  依赖：B、C
  不通过时：创建 Repair 节点
```

## 8. 上下文压缩与记忆

### 大白话解释

上下文是 Agent 当前放在脑子里的信息，记忆是准备以后再次使用的信息。

两者容易被混淆：

- 当前任务的目标、刚才的工具结果属于任务上下文。
- 用户长期偏好、项目约定、已经确认的事实可以进入长期记忆。
- 网页里偶然看到的一句话、模型自己的猜测，不应该直接变成长期记忆。

上下文越长不一定越好。把所有历史都塞进去，会增加成本，也会让重要规则被淹没。优秀系统需要保留关键状态、压缩低价值历史，并知道每条信息来自哪里、可信度如何。

### 五个 Agent 的优点

| Agent | 上下文与记忆的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | 长期记忆有 candidate/confirmed/conflict、作用域、召回和审计 | 新信息先进入待确认区，确认后才成为正式档案；冲突也不会悄悄覆盖旧事实 |
| Maka | Memory、Session Environment、Task Ledger 和 Goal 分层注入 | 长期资料、当前环境和任务进度各放各的位置，不把所有东西混进聊天历史 |
| Kun | Context Block 带 kind 和 authority，工作台状态与任务图结合 | 每张信息卡都标明“这是什么、权威度多高”，模型更容易正确使用 |
| Reasonix | 短稳定前缀、目录规则解析、Skills 按需加载 | 不把所有手册背在身上，走到某个目录或遇到某类任务才加载需要的内容 |
| Codex | Compaction、Resume、Goal 和多种 Context Fragment | 对话太长时整理成续办摘要，同时保留目标和关键运行状态 |

### 谁最值得学习

- **长期事实治理**：Fox 自己已经是强项，应坚持。
- **动态信息与稳定前缀分离**：Maka 和 Reasonix 值得学习。
- **上下文类型和权威度**：Kun 与 Codex 值得学习。
- **长会话压缩和恢复**：Codex 的工程化程度较高。

Fox 的理想形态是：继续用受治理记忆保存长期事实，同时把权限、人格、专家、项目规则、插件能力、目标、环境和本轮状态拆成独立上下文片段；长会话压缩后也能追溯原始 Evidence，而不是只相信摘要。

## 9. 多 Agent 与扩展生态

### 大白话解释

多 Agent 就像从一个人工作变成带一个团队。它能带来并行、专业分工和相互审查，但也会新增很多管理问题：

- 谁负责最终结果。
- 子任务怎样拆分和排序。
- 多个人同时改文件是否冲突。
- 子 Agent 的权限和预算是多少。
- 子 Agent 说“完成了”以后谁来检查。
- 中途失败、取消或重启后怎样恢复。

因此多 Agent 不是基础 Agent 的替代品，而是放大器。好的单 Agent 会被放大，混乱的单 Agent 也会被放大。

### 五个 Agent 的优点

| Agent | 多 Agent 的优点 | 大白话理解 |
| --- | --- | --- |
| Fox | Child Run 有独立记录、预算、权限交集、并发限制、取消传播和结果聚合 | 下属有自己的工单和额度，领导能取消任务，也知道每个人真实返回了什么 |
| Maka | 动态 Graph 子节点、耐久结果记录和隔离 Worktree 思路 | 团队任务即使跑很久也有记录；不同人改代码时尽量分开工位 |
| Kun | Graph Lead、Supervision、Review、Patch、Repair 和 Scope 继承 | 五个项目里最像完整项目团队：负责人派工、盯进度、质检和返工 |
| Reasonix | Explore/Review/Test 等隔离子 Agent Skills | 不建立很重的团队，只在需要时叫一个专门顾问来做聚焦工作 |
| Codex | Spawn/Fork、角色配置、Awaiter、协作模式和父权限继承 | 通用团队工具成熟，既能派探索者和执行者，也能安排专门等待外部结果的角色 |

### 怎么选择这些思路

- 需要**强治理和可审计委派**：Fox 的 Child Run 基础好。
- 需要**长时间运行和隔离修改**：Maka 的耐久图与 Worktree 思路有价值。
- 需要**复杂任务的监督、审查和返工**：Kun 的 Graph Lead 最值得学习。
- 需要**简单、低成本的临时专家**：Reasonix 的 Skill 子 Agent 很合适。
- 需要**通用编码协作和多种角色**：Codex 的 Fork/Role/Awaiter 更成熟。

Fox 下一步应优先补 Graph Lead 和并行 DAG，而不是先增加更多子 Agent 数量。真正的目标不是“同时叫来十个人”，而是让两三个子 Agent 的工作可以被验收、恢复、修复和安全集成。

## 横向总结：每个 Agent 最像什么

| Agent | 最像的现实角色 | 为什么 |
| --- | --- | --- |
| Fox | 有制度、有审计、有验收的企业工作系统 | 每项任务都有过程、证据、审查、验收和权限边界 |
| Maka | 带实验室和行车记录仪的 Agent Runtime | 擅长长时间运行、恢复、回放和比较不同 Prompt/策略 |
| Kun | 能带专业团队的全场景项目经理 | 能建任务图、派发、监督、审查、返工，并覆盖设计、研究、写作和编码 |
| Reasonix | 轻量、按需带工具箱的个人技术助手 | 基础 Prompt 短、扩展可组合、需要时再加载专门方法 |
| Codex | 经验成熟、懂安全流程的高级软件工程师 | 对代码库操作、权限、验证、续跑和多角色协作都很成熟 |

## 如果只选每个项目的一项长处

1. **Fox：工作治理。** 它最清楚“任务是什么、证据是什么、谁审查、怎样才算验收”。
2. **Maka：Prompt 和 Runtime 实验。** 它最擅长证明某次 Prompt 改动到底有没有让 Agent 变好。
3. **Kun：Graph Lead。** 它最擅长管理复杂多节点任务，并对失败结果进行审查和返工。
4. **Reasonix：轻量与缓存意识。** 它最擅长把基础 Prompt 保持短小，需要什么再加载什么。
5. **Codex：通用编码执行系统。** 它在真实代码库里的循环、工具、权限、验证和续跑最均衡。

## Fox 应该形成的组合

Fox 不需要变成另一个 Maka、Kun、Reasonix 或 Codex。更合理的组合是：

具体的统一架构、分阶段实施和防复杂化门槛，见[Fox Agent 核心能力优化方案](../07-路线图/Agent核心能力优化方案.md)。

  Goal / Task / Evidence / Review / Acceptance
  记忆治理 / 专家版本 / 工作流 / 数字同事
                     │

最终应当形成的产品特点是：

- 像 Codex 一样能持续执行和验证。
- 像 Maka 一样能用数据证明 Prompt 与策略的提升。
- 像 Kun 一样能管理复杂任务图和专家团队。
- 像 Reasonix 一样保持 Prompt 与运行负担克制。
- 同时保留 Fox 自己最难替代的证据、验收、记忆和专家治理。

## 用十个问题快速判断一个 Agent 是否可靠

以后再研究其他 Agent 时，可以直接问下面十个问题：

1. 它做一步后，会不会读取真实结果再决定下一步？
2. 它能不能清楚说明当前目标、进度、剩余工作和阻塞原因？
3. 它是否只使用当前真实存在的工具？
4. 工具没有返回成功时，它会不会仍然声称已经完成？
5. 它用什么证据证明结果正确？
6. 验证失败后，它会修复、换方案，还是直接把错误扔给用户？
7. Prompt、外部资料、用户偏好和工具输出之间有没有清楚的信任层级？
8. 目录、命令、网络、凭据和子 Agent 权限是否由系统强制限制？
9. 长任务中断后，能不能根据结构化状态恢复，而不是完全依赖聊天历史？
10. 多 Agent 场景中，谁对最终结果负责，谁负责审查和返工？

如果前六个问题答不好，即使它支持很多模型、几十种插件和漂亮界面，也很难称为可靠 Agent。后四个问题决定它能否从个人演示走向长期、真实和高风险的工作环境。
