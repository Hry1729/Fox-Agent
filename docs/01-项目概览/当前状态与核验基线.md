### 「已推送」的核实方式

判断「已推送」不能只看本地 `origin/*` 引用：那只是本地缓存，离线时可能过期。本轮先做了一次离线核验，随后补齐了联网核验。

**离线阶段（较弱）**：本地 `origin/main` 与 HEAD 相同，只能说明本地远程跟踪引用一致。当时 `FETCH_HEAD` 时间为 Fox `2026-09-22 12:37`、Yuxi `2026-09-08 09:26`，可作为引用新鲜度的上限。

**联网阶段（较强，已执行）**：直接查询远端引用，得到

```powershell
git -C D:\python\projects\Fox\Fox  ls-remote origin refs/heads/main
git -C D:\python\projects\Fox\Yuxi ls-remote origin refs/heads/main
```

结果：Fox 远端 `main` = `0346a5c90988b6752dfb9de391a76ed18b5368eb`（与本地 HEAD 相同）；Yuxi 远端 `main` = `ffe289df12751e33fd0cb86b88865bc81bf98233`（与本地 HEAD 相同）。即两侧在核验时刻**均已推送，且无未推送提交**。

**注意 HEAD 会随文档提交前进**：承载本页的提交是 `0346a5c`（仅 docs，无产品代码）。因此本页 §1 表格中的 HEAD 是**核验时刻**的值，不是永久值。任何时刻重新判断是否已推送，都应以 `git rev-parse HEAD` 与 `git ls-remote origin refs/heads/main` 现查现比，不要照抄本页数字。

## 2. 结论成熟度与证据分级

### 2.1 成熟度词汇（不可互相代替）

文档中使用下列词汇时必须指代其字面含义：

| 词汇 | 含义 | 反例（不能这样写） |
| --- | --- | --- |
| 已实现 | 当前 HEAD 源码里存在该行为，且能从代码路径读出 | 只有设计文档或方案 |
| 已提交 | 该改动存在于某个 Git 提交中 | 只在某人工作区未提交 |
| 已推送 | 该提交存在于远端仓库 | 仅本地 `origin/*` 引用一致（见 §1） |
| 已发布 | 存在对外可获取的发布物（安装包/Release/标签），且能指出其版本与哈希 | 本地 `target/` 里存在 exe |
| 已验收 | 存在与**该发布物哈希**对应的验收记录，覆盖声明范围内的场景 | 单元测试通过；旧版本录屏 |

「测试通过」不等于「已验收」；「已提交」不等于「已推送」；「已推送」不等于「已发布」。四者必须分开记录。

### 2.2 证据分级

结论需要标注证据达到哪一层。层级从低到高：

1. **源码实现** —— 直接读取当前 HEAD 的源码或配置。
2. **定向测试** —— 针对该行为的自动化测试（Bun / `node --test` / `cargo test` / pytest）。
3. **GUI 手工验收** —— 在真实桌面界面操作并留痕。
4. **真实云模型验收** —— 使用真实供应商模型凭据完成的端到端任务。
5. **安装包验收** —— 在干净或隔离环境安装带哈希的安装包后验收。
6. **跨平台/生产验收** —— 非 Windows 平台或真实企业环境验收。

低层级证据**不能**推出高层级结论。例：定向测试通过不能写成「GUI 已验收」；本机安装包能装上不能写成「跨平台已验收」。

### 2.3 关于「没有某能力」的判断范围

写「Fox 没有 X」时，必须同时写清检索范围，否则该结论无效。本页与各主题文档采用如下写法：

## 4. 执行权威的层次（最易混淆，务必分清）

Fox 里「默认用什么执行」有多个**互不相同**的层次，不能合并成一句话：

```text
1) Agent.runtime_type: "pi" | "yuxi"
   → 决定走 RuntimeHost（本地 Sidecar）还是 YuxiRuntimeHost（远程）

2) ExecutionAuthority（每个 Run 冻结在 run_control_bindings）
   select() 优先级：已冻结绑定 > FOX_KERNEL_MODE 环境变量 > 编译期 feature
   - 普通构建（无 kernel-default feature）且无环境变量 → 新 Run = Legacy
   - tauri:build:kernel-preview 打开 kernel-default → 新 Run = Authoritative
   - 已冻结的 Run 永远不因环境变量或回滚改变 authority

3) engine_id（仅 Kernel/Authoritative 路径）: pi | codex | deepseek_harness
   由 FOX_KERNEL_ENGINE 指定，缺省 pi

4) kernel_mode: legacy | authoritative（shadow 只写 shadow 表）

5) Execution Profile: legacy | durable_v2_shadow | durable_v2 |
   graph_readonly_preview | graph_reviewer_v1
```

源码依据：

- 优先级实现：`apps/desktop/src-tauri/src/runtime_host/kernel_authority.rs::select`（冻结值优先，其次 `FOX_KERNEL_MODE`，否则按 `cfg!(feature = "kernel-default")` 取 Legacy/Authoritative；非法值报错而非回退）。
- 编译期开关：`apps/desktop/src-tauri/Cargo.toml` 的 `kernel-default = []`（默认 features 不含它）。
- 预览包：`apps/desktop/src-tauri/tauri.kernel-preview.conf.json` 的 `build.features: ["kernel-default"]`，由根 `package.json` 的 `tauri:build:kernel-preview` 调用。
- 引擎解析：`apps/desktop/src-tauri/src/kernel_model_config.rs`（`FOX_KERNEL_ENGINE` 取 pi / codex / deepseek_harness）。

**因此：**

- 「默认 Legacy」描述的是**普通构建**的默认；这不与「Kernel Preview 包默认 Authoritative」矛盾，两者是不同构建产物。
- Pi **不是**第三种权威模式；它是 engine 名 + Sidecar 运行时。
- 历史文档中「默认启用新 Kernel」的表述指的是 Preview 包，不适用于日常 `cargo` / `pnpm tauri build` 产物。
