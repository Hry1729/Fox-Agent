# 专家智能体对比与演进建议

> 状态：已归档；E1-E4 已完成，本文仅保留竞品研究与演进依据
> 适用版本：Fox `0.1.x` 及后续版本
> 维护范围：专家 Persona、能力包、工作流、子智能体团队与数字同事
> 最后更新：2026-08-24

## 核心结论

“专家”不是单一技术。市场产品至少混合使用了五个层级：

1. **Persona 覆盖**：名称、头像和专家提示词改变模型身份与回答方式。
2. **能力包**：Persona 同时绑定 Skills、Tools、MCP、知识和 Hooks。
3. **工作流专家**：用状态机、阶段、Gate 和结构化产物约束执行过程。
4. **专家团队**：Lead 与多个成员拥有独立上下文，通过子 Run 和消息协作。
5. **数字同事**：在专家能力上增加持久配置、记忆、定时任务、仓库和 IM 渠道。

WorkBuddy 的专家属于能力包，并可升级为真实专家团队和数字同事；PinVou 的 Persona 卡本身主要是提示词覆盖，但产品另有 Skills、MCP、知识库、记忆和工作流；Fox 已采纳“基础助手 + 会话专家绑定”的组合：专家从专家中心召唤，以时间线卡片和 Composer 胶囊呈现，Runtime 注入独立 Persona Overlay，同时保留更严格的 Host 权限与 Goal/Task/Evidence。Fox 已完成 E1 可安装专家包、E2 持久化工作流专家、E3 串行 Supervisor 专家团队和 E4 持久数字同事首版。

## 三者能力对比

| 维度 | WorkBuddy | PinVou | Fox 当前 |
| --- | --- | --- | --- |
| 专家基础单元 | 可下载 Plugin Bundle，包含 `agents/*.md` Persona | `PersonaCard`，核心是元数据和 Markdown body | `AgentRecord` 明确分为 Assistant/Expert/Worker；Expert 通过会话绑定叠加到基础 Assistant |
| Prompt 注入 | Agent Markdown 作为身份覆盖，首条初始化 Prompt 分开处理 | 首轮注入完整 body，后续每轮注入短 identity anchor | Agent System Prompt + Runtime Contract + Model Rules + 动态低权限上下文 |
| Skills | Bundle 可带 `skills/`，frontmatter 可预加载 | 产品有 Skills，但 Persona Schema 不直接绑定 | Agent Resources 支持 Skills；启用 Skill 正文进入稳定 Prompt，清单进入 `expertPackage` |
| Tools/MCP | Bundle 可带 Commands、Connectors/MCP、Hooks；成员工具可设作用域 | Persona 通常继承会话工具；`conversational_only` 可清空工具；MCP 独立存在 | Agent Resources 支持 Tools/MCP；真正授权由 Host Capability 和审批决定 |
| 知识与记忆 | 数字同事可绑定知识库和记忆 | 产品有知识库与记忆，和 Persona 分层组合 | 会话/远程 Agent 可绑定知识；本地长期 Memory 已由 A2 治理 |
| 工作流 | Persona 指令、Hooks 和 Agent Team 任务共同约束 | 独立 Workflow 有角色、状态、路由、Gate、重试和输出 | `.foxexpert` v2 可携带持久 Workflow；Stage 映射现有 Goal/Task/Evidence |
| 子智能体 | `Agent` 工具提供独立上下文 Sub-agent | 未在 Persona 卡本身提供团队原语 | A5 已提供 Host-owned、有限并发 Child Run |
| 专家团队 | `TeamCreate` + 命名成员 + `SendMessage` + 共享任务 | Persona 不是团队；工作流角色不等同于独立 Agent Team | E3 v1 已实现真实 Child Run Member、串行分派、Scope/预算/取消/聚合；mailbox 与共享领取后续引入 |
| 权限边界 | Agent mode、工具作用域、Hooks 和宿主权限组合 | Persona 多数继承会话工具，卡本身权限表达较弱 | Host 收口文件、命令、MCP 和审批，权限事实不由 Prompt 决定 |
| 安装与市场 | 专家市场、Bundle 下载、版本/Hash、导入导出和安全扫描 | 内置/用户 Persona 卡池 | 已有本地专家中心与用户专家编辑；无独立包格式、签名升级和市场 |
| 持久化同事 | 模型、仓库、知识、记忆、自动化和 IM 绑定 | 有独立的记忆、工作流等产品能力 | E4 v1 已有冻结 Expert Instance、项目/知识、配额、Interval Schedule 与签名 Channel；专用 IM Adapter 后续增强 |

## WorkBuddy：不是纯提示词

WorkBuddy 的单 Agent 专家确实以 Persona Markdown 为身份核心，但安装单元是 Plugin Bundle，可以同时包含：

- `agents/*.md`：身份、方法和编排指令；
- `skills/`：可预加载的领域技能；
- `commands/`：专家可调用的命令；
- `connectors/`：外部连接器或 MCP；
- Hooks：在工具、会话和子智能体生命周期执行策略。

团队专家不是在一个 Prompt 里模拟多个角色。Lead 会调用真实的 `TeamCreate`、`Agent` 和 `SendMessage`：成员具有独立上下文，可使用限定工具，并通过 mailbox 和共享任务协作。因此其“专家团队”同时依赖 Persona 指令和运行时编排原语，只有提示词而没有这些工具时无法获得相同语义。

WorkBuddy 的数字同事再向上增加持久模型、代码仓库、知识库、记忆、自动化和 IM 绑定。这已经是长期运行实体，不应与一次会话中的专家 Persona 混为一谈。

## PinVou：Persona 为提示词层，能力在产品其他层

PinVou 的 `PersonaCard` 主要包含 ID、部门、名称、描述、图标、颜色、Markdown body、来源和 `conversational_only`。装备后：

1. 首轮把完整 Persona body 注入用户消息前；
2. 后续 turn 只注入简短身份锚点；
3. 普通 Persona 继承当前 Session 的工具；
4. `conversational_only` Persona 清空工具。

Persona Schema 没有直接绑定 Skill、工具 Allowlist、MCP 或 Workflow。因此“卡片本身”主要是 Prompt Overlay。

但 PinVou 产品不是只有提示词。它另有 Skills、MCP、知识库、记忆和 Workflow。Workflow 能定义角色文件、状态机、阶段路由、Gate、重试/停止和角色输出。准确说法是：PinVou 用 Persona 管身份，用其他子系统提供执行能力；二者可以在同一会话中组合，但还不是 WorkBuddy 那种一个包同时声明 Persona、能力和团队的专家分发单元。

## Fox 当前优势与差距

### 已有优势

- Agent 与 Runtime/Model 解耦，同一对话产品可以接 Pi 或远程 Runtime。
- Agent Resources 已表达 Tools、Knowledge、MCP 和 Skills，不止是 System Prompt；本地 Pi Run 已接收完整 `expertPackage`。
- 专家能力包会写入 Request Snapshot，可诊断每次运行实际获得的身份、资源与启用 Skills。
- 文件、命令、MCP 和审批由 Host 授权；Prompt 或 Skill 不能自行扩大权限。
- Goal、Task、Evidence 和 Work Event 是 Host-owned 事实，刷新和重启后可恢复。
- Model Profile、Prompt Hash、Request Snapshot 和离线 Eval 为跨模型适配提供了可观测基础。

### 原始差距的当前状态

| 原优先级 | 原始差距 | 当前状态 |
| --- | --- | --- |
| P0 | 本地 Agent/专家创建与编辑体验 | 已完成 |
| P0 | 版本化专家包 Manifest | E1 已完成 |
| P0 | 每专家严格 Tool/MCP Allowlist 与权限预览 | E1 与 Host Scope 已完成 |
| P1 | 可复用工作流专家 | E2 v1 已完成 |
| P1 | Child Run/Sub-agent | A5 已完成 |
| P1 | Lead/Member 团队与通信协议 | E3 串行 Supervisor v1 已完成；mailbox/并行仍延期 |
| P2 | 专家目录、导入导出、版本和安全扫描 | 本地目录、导入导出、版本/Hash 已完成；远程市场、发布者签名与信任分级仍未实现 |
| P2 | 数字同事实体、调度和 IM | E4 v1 已完成持久实体、Interval Schedule 与签名 Channel；专用 IM Adapter 仍未实现 |

## 推荐演进

E0 和会话集成已落地：Fox 通用助手是基础 Assistant；调试、前端体验、代码审查、安全审查和架构规划是可绑定 Expert；用户可创建本地 Expert，远程 Sub-agent 映射为隐藏 Worker。它们复用 Pi Runtime 与 Host 权限，不是 Child Agent，也不等同于可安装专家包。

### Fox 已采纳落点

- Assistant 仅进入聊天助手下拉菜单，Expert 仅进入专家中心，Worker 不进入普通选择界面。
- `conversations.agent_id` 保留基础助手语义；专家使用独立、可恢复、带快照的会话绑定。
- 专家启用卡片进入时间线但不进入模型消息；当前专家胶囊位于“执行前询问”右侧。
- Runtime 同时记录 `assistantPackage`、`expertBinding`、`expertPackage`，工具和 MCP 权限取交集。
- 单会话仅支持一个 active Expert；已有消息后更换专家会创建新草稿，不做上下文内热切换。

### E0：Persona 专家

- 提供本地专家创建、编辑、复制和删除。
- 保存名称、图标、分类、说明、System Prompt 和开场建议。
- 复用现有 Agent 与 Runtime，不增加任何权限。
- UI 必须明确“身份提示”不能授予工具、项目或网络能力。

### E1：专家能力包（已完成）

Fox 已采用可直接审计的 `.foxexpert` JSON 和版本化 Manifest：

```yaml
schemaVersion: 1
id: fox.docs-reviewer
version: 0.1.0
agent:
  systemPrompt: ./prompts/system.md
resources:
  skills: [docs-review]
  tools: [read, grep]
  mcps: []
  knowledgeReferences: []
permissions:
  project: read_only
workflow: null
```

安装已校验严格 Schema、路径逃逸、逐文件/整包 Hash、Fox 兼容范围和 Skill/Tool/MCP/知识存在性；桌面端在确认前展示权限与缺失资源。版本历史不可变，升级不改写既有会话快照，同版本不同 Hash 拒绝，历史版本可显式回滚。Manifest 只声明所需能力，最终授权仍由 Host 与用户决定。

### E2：工作流专家（已完成）

`.foxexpert` Schema v2 已可绑定 Workflow v1，声明阶段、输入/输出 JSON Schema、Gate、有限重试、停止和验收条件。Workflow Run/Stage/Gate 由 SQLite v30 持久化，Stage 映射现有 Goal/Task/Evidence；模型负责执行，Host 负责状态转换、用户确认、输出 Schema、权限和证据校验。重启恢复、Gate、失败重试和单事实源均有自动化覆盖。

### E3：专家团队（已完成首版）

- 依赖路线图 A5 的 Child Run，而不是先用 Prompt 模拟团队。
- Lead 与 Member 使用独立 Context、独立 Run 和可审计 Tool Scope。
- 首版只支持串行分派和结果回传；稳定后再引入并行、mailbox 和共享任务领取。
- 取消、超时、成本、深度和并发必须由 Host 限制并传播到子 Run。

### E4：数字同事（已完成首版）

- 已增加持久 Expert Instance、冻结能力包、项目/知识绑定、Interval Schedule、运行配额和签名 Channel。
- Schedule 已提供幂等、非重叠、coalescing、catch-up/misfire 与离线恢复。
- Channel 已提供精确身份、HMAC-SHA256、时间窗、频控、Keyring 密钥、撤销和完整审计；专用 IM Adapter 和公网 Listener 不属于首版。

## 不建议直接照搬的部分

- 不把专家权限写进 Prompt 后直接信任模型遵守。
- 不把 Persona、Workflow 和 Agent Team 都叫“专家”，数据库中应保留明确类型。
- 不在 A5 Child Run 之前用单上下文角色扮演宣称“多智能体团队”。
- 不让专家包直接执行安装脚本或任意 Hook；首版 Hooks 应是受限声明式事件。
- 不让市场安全服务不可用时默认放行高风险包。
- 不让模型自行宣称 Goal/Task 完成；仍以 Host 状态和 Evidence 为准。

## 验收建议

| 阶段 | 最小验收 |
| --- | --- |
| E0 | Persona 新建/编辑/删除；普通对话不误切专家；无权限扩大 |
| E1 | 包安装、版本升级、Hash、路径逃逸、缺失 Skill/Tool 和权限预览测试 |
| E2 | 工作流暂停/恢复/Gate/失败/重启；Goal/Task/Evidence 只有一个事实源 |
| E3 | 父子 Run 关联、独立上下文、工具隔离、取消传播、成本上限和结果回传 |
| E4 | 定时触发幂等、外部身份校验、离线恢复、配额、审计和撤销访问 |

真实模型质量验收按[Agent 能力测试基准](../../05-开发指南/Agent能力测试基准.md)中的在线 Smoke 和外部评测方案执行。
