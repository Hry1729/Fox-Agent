# 知识库后端扩展实施清单

> 状态：已归档；仅用于追溯知识库服务 `0.7.0` 扩展过程。

Updated: 2026-07-25

This checklist is the implementation index for Fox-specific backend extensions. The compatibility baseline is Yuxi `v0.7.0`; upstream upgrades are intentionally out of scope.

## Current Status

- Phase 1 implementation is complete in the local Yuxi `v0.7.0` worktree.
- Automated coverage passes for HEAD, bounded full streaming, exact Range reads, revision precedence, stale revisions, object races, missing objects, filename safety, and authorization short-circuiting.
- The live Docker service exposes both HEAD and GET and returns `401` before object resolution when unauthenticated.
- One authenticated live file still needs to pass the Fox contract verifier before Phase 1 is declared deployment-accepted.
- Phases 2-4 remain intentionally unadvertised; original-file HEAD does not return preview capability headers yet.

## Guardrails

- Keep every change additive and versioned. Do not rename or remove existing Yuxi API fields.
- Reuse Yuxi authentication, knowledge-base authorization, PostgreSQL metadata, Redis/ARQ, and MinIO clients.
- Keep MinIO originals as the source of truth. Never expose object paths or storage credentials to Fox.
- Recheck user, knowledge-base, and file access on every metadata, byte-range, job-status, and preview-content request.
- Do not advertise a capability until its complete API contract is operational.
- Avoid schema changes in the original-file gateway. Preview Job schema changes belong to their own migration.

## Phase 1: Original File Gateway

Routes:

```text
HEAD /api/workspace/knowledge/download?kb_id=...&file_id=...&variant=original
GET  /api/workspace/knowledge/download?kb_id=...&file_id=...&variant=original
```

Required implementation:

- Resolve the file through the existing KnowledgeBase manager so a `file_id` cannot be paired with another `kb_id`.
- Support metadata-only HEAD without loading object bytes.
- Stream full GET responses from MinIO with bounded chunks.
- Support exactly one explicit byte range: `bytes=start-end`.
- Return exact `206`, `Content-Length`, `Content-Range`, and `Accept-Ranges: bytes` headers.
- Return `416` with `Content-Range: bytes */{size}` for malformed, multiple, open-ended, suffix, inverted, or out-of-bounds ranges.
- Treat `If-Range` as a strict Fox revision precondition. Return `412` if it differs from the current source revision; never fall back to a full `200` response.
- Generate `X-Source-Revision` in this order: MinIO version ID, persisted SHA-256, compatibility hash of opaque ETag + size + last-modified.
- Treat ETags as opaque. Never infer MD5 semantics from multipart or ordinary ETags.
- Return sanitized `Content-Disposition`, `X-File-Name`, MIME, ETag, last-modified, and optional version ID.
- Preserve the existing parsed-download behavior for compatibility.

Acceptance gates:

- Unit tests cover Range parsing and source revision generation.
- Route tests cover HEAD, full GET, first/middle/final/one-byte ranges, stale `If-Range`, invalid ranges, unauthorized access, and mismatched knowledge/file IDs.
- The Fox contract verifier passes against the rebuilt local Docker service.
- Large original files are never materialized as one Python `bytes` value by the route.

## Phase 2: Preview Job Control Plane

Routes:

```text
GET  /api/workspace/knowledge/preview/status
POST /api/workspace/knowledge/preview
HEAD /api/workspace/knowledge/preview/content
GET  /api/workspace/knowledge/preview/content
```

Required implementation:

- Add persisted, idempotent Preview Jobs keyed by security domain, knowledge base, file, source revision, preview profile, and renderer version.
- Reuse ARQ/Redis for dispatch and duplicate-job convergence.
- Model `pending`, `ready`, `failed`, `unsupported`, and `stale` explicitly.
- Store derived PDFs in a private preview bucket or prefix.
- Keep `X-Source-Revision` and `X-Preview-Revision` distinct.
- Apply the Phase 1 exact-Range and strict `If-Range` semantics to derived PDF reads.
- Add bounded retry, terminal failure caching, audit metadata, and stale-artifact cleanup.

Capability gate:

Do not add `X-Preview-Api-Version: 1` to original-file HEAD until all four routes above, authorization, persistence, Range reads, and worker dispatch are functional.

## Phase 3: Isolated Layout Conversion Worker

Delivery order:

1. PPTX/ODP to PDF vertical slice.
2. DOCX to PDF.
3. XLSX/XLS/ODS to PDF.

Isolation requirements:

- Use one-shot rootless containers or an equivalent strong sandbox, not a host `soffice --headless` process as the security boundary.
- Disable network, macros, external links, OLE activation, and automatic content execution.
- Use read-only input, read-only root filesystem, isolated tmpfs output/profile, no Docker socket, and no host credentials.
- Drop capabilities, enable no-new-privileges and seccomp/AppArmor, and cap PID, CPU, memory, output size, pages, and wall-clock time.
- Accept only controlled object identifiers and fixed profiles, never arbitrary paths or command arguments.

## Phase 4: Operations And Contract Stability

- Add preview cache capacity/TTL cleanup and metrics without logging document content.
- Record user, knowledge base, file, operation, result, bytes, duration, source revision, and renderer version.
- Run the Fox verifier in CI against a disposable Yuxi stack.
- Maintain contract fixtures for authorization, events, exact byte semantics, error codes, and capability headers.
- Document deployment additions and rollback steps before enabling the preview capability in production.

## Live Verification Inputs

Only the final Docker-backed verification needs user-provided runtime data:

```text
FOX_KNOWLEDGE_TOKEN
kb_id
file_id for an original document
PPTX/ODP file_id for Phase 3
```

Fox verifier command:

```powershell
$env:FOX_KNOWLEDGE_TOKEN = '<token>'
pnpm.cmd knowledge:verify-preview -- --base-url http://127.0.0.1:5050 --kb-id <id> --file-id <id>
```
