# Fox 开发文档

> 状态：维护中<br>
> 适用版本：Fox `0.1.x`<br>
> 最后更新：2026-09-22

本目录面向参与 Fox 产品、设计、前端、桌面后端、Agent Runtime、测试和发布工作的工程师。文档描述当前代码事实、稳定设计边界和已经确认的演进方向，不把历史方案直接当成当前实现。

## 先读这一页

**[当前状态与核验基线](01-项目概览/当前状态与核验基线.md)** —— 仓库基线（分支/HEAD/工作区）、结论成熟度口径（已实现 / 已提交 / 已推送 / 已发布 / 已验收）、证据分级、每个主题的唯一维护点、以及待验证清单。

其余文档只写各主题的技术正文。当「某结论现在算不算数」有疑问时，以该页为准，不要从各主题文档的历史段落里推断。

## 文档分区

| 目录 | 内容 | 更新时机 |
| --- | --- | --- |
| `01-项目概览` | 产品定位、能力矩阵、系统全景、仓库结构和术语 | 产品边界或仓库结构变化时 |
| `02-架构` | Tauri、Runtime、数据、集成、扩展和安全架构 | 稳定架构边界变化时 |
| `03-产品与前端` | 前端架构、页面、组件、交互和体验规范 | 产品交互或设计规范变化时 |
| `04-技术参考` | Schema、协议、Command、配置和状态枚举 | 接口或代码契约变化时 |
| `05-开发指南` | 环境、流程、编码、测试、调试和扩展方式 | 工具链或开发流程变化时 |
| `06-运维指南` | 构建、发布、诊断、恢复和性能 | 发布与运行方式变化时 |
| `07-路线图` | 已确认的能力路线和限制 | Milestone 或优先级变化时 |
| `架构决策` | 重要且难以逆转的技术决策 | 决策被接受或替代时 |
| `评审` | 面向评审/汇报的材料与一次性集成证据（含契约清单与验证报告） | 新增评审批次时；历史批次只追加状态说明 |
| `归档` | 已被新文档吸收的历史方案与状态记录 | 完成迁移审查后 |

`评审` 与 `07-路线图/实施记录` 属于**证据与历史**，不是当前事实来源：其中的结论按当时基线成立，当前状态以[当前状态与核验基线](01-项目概览/当前状态与核验基线.md)为准。

## 事实来源优先级

文档与实现不一致时，按以下顺序核实：

1. 当前分支的代码、数据库迁移和自动化测试。
2. 版本化协议、配置文件和生成清单。
3. [当前状态与核验基线](01-项目概览/当前状态与核验基线.md) 与其中的主题维护点。
4. 本目录中的常青架构与技术参考文档。
5. GitHub Issues、Milestones 和已接受的架构决策。
6. `评审`、`实施记录` 与 `归档` 中的历史计划、研究和实施状态（仅代表当时基线）。

发现偏差时，不应只修正文档或只修代码。先确认预期行为，再让实现、测试和文档恢复一致。

## 维护规则

- 文件名使用中文；保留行业通用缩写，如 API、MCP、Runtime、SQLite。
- 对外统一使用“知识库服务”，只有解释代码路径或兼容字段时使用 `Yuxi` 实现名称。
- 路线图描述未来，架构文档描述当前稳定边界，技术参考必须贴近代码事实。
- 「已实现 / 已提交 / 已推送 / 已发布 / 已验收」是五个不同结论，不能互相代替；口径与证据分级见[当前状态与核验基线](01-项目概览/当前状态与核验基线.md)。
- 同一事实只写一次：先确认它属于哪个主题的主要维护文档，其他位置用相对链接引用，不复制正文。
- 写「没有某能力」时必须同时写明检索范围，单次搜索不足以支撑全仓库否定结论。
- 每项公共接口变更必须同步更新相关参考文档和测试。
- 不在文档中记录真实 API Key、Token、Cookie、内部地址或用户数据。
- 历史文档只有在内容被完整吸收并完成链接检查后才能移入归档或删除。

具体写作约定见 [文档编写规范](文档编写规范.md)。
