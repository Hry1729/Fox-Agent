# 开发工作流

> 状态：当前<br>
> 适用版本：Fox 0.1.0<br>
> 维护范围：Issue、分支、实现、评审与交付<br>
> 最后更新：2026-07-29

## 目标与范围

本文定义 Fox 日常开发的推荐闭环。GitHub Issue 是需求和验收事实来源，SQLite、Runtime 协议、前端展示及文档必须在同一变更中保持一致。

仓库当前未配置可见的正式 CI 工作流，因此工程师不能把“本地能运行”替代为完整回归，也不能假设推送后会自动执行检查。

## 开始任务

1. 阅读 Issue 的目标、范围、非目标、依赖与验收标准。
2. 查看关联的架构文档和现有实现，确认数据所有权与模块边界。
3. 将任务拆成能够独立验证的步骤；存在数据迁移或公共协议时优先冻结契约。
4. 检查工作区现有改动，避免覆盖他人工作。
5. 建立与 Issue 对应的分支。Codex 协作分支默认使用 `codex/` 前缀；团队可在仓库规则固化后调整。

示例：

```powershell
git switch -c codex/a0-01-work-model
git status --short
```

## 实施顺序

跨层功能推荐遵循以下顺序：

```mermaid
flowchart LR
  Contract["状态与契约"] --> Data["SQLite 与 Repository"]
  Data --> Host["Rust Host / Commands"]
  Host --> Runtime["Runtime 协议与工具"]
  Runtime --> UI["前端状态与界面"]
  UI --> Verify["自动化与人工验收"]
  Verify --> Docs["文档与 Issue 更新"]
```

小范围变更不必机械经过所有层，但必须确认没有遗漏受影响的契约。

## 代码边界

| 变更类型 | 首要目录 | 必须联查 |
| --- | --- | --- |
| UI 与交互 | `apps/desktop/src/` | Tauri Command 类型、恢复态、空态与错误态 |
| Tauri Command | `apps/desktop/src-tauri/src/commands/` | 前端 client、数据库 Repository、错误码 |
| 数据库 | `database/migrations.rs`、`repositories.rs` | 备份恢复、旧数据升级、状态约束 |
| Runtime | `services/agent-runtime/src/` | Rust 协议镜像、Capability Manifest、契约测试 |
| Knowledge 接口 | `yuxi/`、知识库前端模块 | 服务契约脚本、缓存、取消和版本标识 |
| Skills/MCP | `skills.rs`、`mcp.rs` | 凭证边界、审批策略、Runtime 工具目录 |

## 数据库变更规则

- 迁移只能追加，不能重排或改写已发布迁移。
- 迁移编号使用 `migrations.rs` 中下一个可用版本；当前实现已应用到版本 13。
- 所有迁移在事务中执行，并写入 `schema_migrations`。
- 旧数据库升级、重复执行和数据完整性必须有测试。
- 回滚策略以“恢复迁移前备份”为主，不承诺旧程序能直接读取新 Schema。
- 新路径字段必须考虑备份恢复后的路径重定位。

## 前后端契约规则

- Tauri Command 请求与响应统一使用 `camelCase` 序列化。
- 前端只能通过 `features/conversations/api/desktop-client.ts` 等适配层调用 Command，不在展示组件中散落 `invoke`。
- 运行事件需要同时支持实时流与 SQLite 恢复；刷新后结果必须一致。
- 新事件要有稳定的类型名、顺序号和幂等规则，未知事件不得导致前端崩溃。
- 修改 JSONL Runtime 协议时，同时更新 JS、Rust、Capability Manifest 和契约测试。

## 提交前验证

根据风险选择测试，公共协议或跨模块变更执行完整矩阵：

```powershell
bun test ./apps/desktop/tests
pnpm.cmd runtime:test
pnpm.cmd knowledge:verify-preview:test
cargo fmt --manifest-path apps/desktop/src-tauri/Cargo.toml -- --check
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml
pnpm.cmd --dir apps/desktop build
git diff --check
```

修改 Runtime 构建、Tauri 资源或发布配置时追加：

```powershell
pnpm.cmd runtime:build
pnpm.cmd runtime:smoke
pnpm.cmd tauri:build
```

## 提交与评审

提交应按可审查的行为单元组织，避免混入生成文件、缓存、测试数据库或本地参考项目。

```powershell
git diff --stat
git diff --check
git status --short
git commit -m "feat: add recoverable work task state"
```

评审说明至少包含：

- 解决了什么问题，以及明确没有做什么。
- 关键数据流、状态转换或安全边界。
- 自动验证命令及结果。
- 人工验证步骤与截图需求。
- 数据迁移、兼容性、性能和已知限制。

## Issue 收尾

只有满足验收标准后才关闭 Issue。更新内容包括：

1. 实际实现与原方案的差异。
2. 测试和人工验收结果。
3. 新增或变更的配置、数据库版本、协议版本。
4. 未解决风险和后续 Issue 链接。
5. 对应常青文档的更新位置。

## 常见失败模式

- 只验证实时事件，没有验证刷新和重启恢复。
- 只改 JS Runtime，忘记更新 Rust 协议验证。
- 将 API Key、Token 或 MCP 环境变量写入 SQLite/日志。
- 修改旧迁移而不是追加新迁移。
- 用提高 Vite Chunk 告警阈值掩盖体积增长。
- 删除旧设计文档前，没有把仍有效的信息整理进新文档。
- 在共享工作区撤销或覆盖非本人改动。

## 完成定义

- Issue 验收项逐项通过。
- 代码、测试、数据库和协议文档同步。
- 普通路径、失败路径、取消与恢复路径均被考虑。
- 没有提交密钥、构建产物、缓存或本机数据。
- 相关构建和测试已执行；未执行项及原因已明确记录。
