# 开发工作流

> 状态：生效<br>
> 适用版本：Fox 0.1.x<br>
> 维护范围：Issue、分支、实现、验证、复测与交付<br>
> 最后更新：2026-10-28（单 Pi 分支同步；本轮未复跑产品测试）

## 目标与范围

本文定义 Fox 日常开发的闭环。GitHub Issue 是需求和验收的事实来源；SQLite、Pi 引擎协议、Host 路由、前端展示和文档必须在同一变更里保持一致。

## 开始任务

1. 读 Issue 的目标、范围、非目标、依赖和验收标准。
2. 读相关架构文档和现有实现，确认数据归属和模块边界。先区分默认 Authoritative 与显式 Legacy；历史外部驱动已退休，这决定了改哪里，见 [Agent 运行时架构](../02-架构/Agent运行时架构.md)。
3. 拆成能独立验证的步骤；涉及迁移或公共协议时先冻结契约。
4. 检查工作区现有改动，不要覆盖别人的工作。多人或多个 agent 并行时，各自用独立的 `git worktree`。

## 分支与提交

- 仓库目前只有 `main` 一个长期分支。之前的特性分支（如 `feat/four-agent-phase0-1`）已合入。
- 代码改动推到 `main` 或经 PR 合入都会触发 Windows CI；PR 也会触发。
- 只改文档的提交在提交信息末尾加 `[skip ci]`。
- 不要 force push `main`。
- 提交按可审查的行为单元组织，不要混入生成文件、缓存、测试数据库或本地参考项目。

```powershell
git diff --stat
git diff --check
git status --short
```

## 实施顺序

跨层功能推荐按下面的顺序做：

```mermaid
flowchart LR
  Contract["状态与契约"] --> Data["SQLite 与 Repository"]
  Data --> Kernel["Kernel 决策 / 引擎协议"]
  Kernel --> Host["Rust Host / Commands"]
  Host --> Runtime["Pi Runtime worker"]
  Runtime --> UI["前端状态与界面"]
  UI --> Verify["自动化测试与人工复测"]
  Verify --> Docs["文档与 Issue 更新"]
```

小范围变更不必经过每一层，但要确认没有漏掉受影响的契约。

## 数据库变更规则

- 迁移只能追加，不能重排或改写已发布的迁移。编号用 `migrations.rs` 里下一个可用版本；当前版本见[数据架构](../02-架构/数据架构.md)。
- 迁移在事务里执行并写入 `schema_migrations`；迁移后做外键检查。
- 迁移前会自动备份数据库。回滚以“恢复迁移前备份”为准，不承诺旧程序能读新 Schema。
- 旧库升级、重复执行和数据完整性必须有测试。
- 新路径字段要考虑备份恢复后的路径重定位。

## 前后端契约规则

- Tauri Command 的请求和响应统一用 `camelCase` 序列化。
- 前端只通过 `features/conversations/api/desktop-client.ts` 等适配层调用 Command，不在展示组件里直接 `invoke`。
- 运行事件要同时支持实时流和 SQLite 恢复，刷新后结果必须一致。
- 新事件要有稳定的类型名、顺序号和幂等规则；未知事件不能让前端崩溃。
- 改引擎协议时同时更新 Rust、生成的 JS、Capability Manifest 和契约测试。
- Host 的稳定错误码改动要同步前端镜像。

## 文档同步门槛

改动驱动准入、执行模式、Schema、恢复边界或设置入口时，同一变更应同步 README、CHANGELOG、`docs/README.md`、相关架构与参考页，以及 `default-knowledge/fox-guide` 内置帮助。历史报告保留正文，只追加适用时点说明。

单 Pi 分支的阶段状态统一见[单 Pi 主线状态](../01-项目概览/单Pi主线状态.md)。阶段一、SDK 测试、Legacy 映射、默认桌面恢复和业务验收分别记录。阶段二与 C gap 未完成，不因文档同步或部分测试通过改成完成。

## 提交前验证

按风险选择，命令和 CI job 的对应关系见[测试指南](测试指南.md)。常用组合：

```powershell
bun test ./apps/desktop/tests
pnpm.cmd build
pnpm.cmd runtime:test
cargo test -p fox-agent-kernel -p fox-engine-protocol
pnpm.cmd protocol:check
cargo test -p fox-agent-backend --features acp
pwsh ./scripts/test-desktop-rust.ps1 -Mode Suite
git diff --check
```

改 Runtime 构建、Tauri 资源或发布配置时追加：

```powershell
pnpm.cmd runtime:build
pnpm.cmd runtime:smoke
pnpm.cmd tauri:build:windows
```

## 推送后：CI 与定向复核

1. 推送后看 Windows CI 结果，每个 job 的失败测试名会写在 job 摘要里。
2. 只需要复核某处修复时，手动运行定向模式：`targeted=true`，`rust_test_filter` 填相关测试名。定向模式跳过前端、ACP 后端和协议检查，不能代替完整 CI。用法见[测试指南 · 定向模式](测试指南.md#定向模式targeted)。
3. 自动化覆盖不到的部分（Pi 原生会话、沙箱、安装包、界面）单独记录候选 SHA、执行模式、模型、命令和结果。单 Pi 记录放在 `apps/desktop/tests/acceptance/single-pi-20261027/`；旧 `sandbox.md` 批次保留历史。
4. Windows 人工复测必须从普通目录（Medium 完整性）运行 exe，见[调试指南](调试指南.md#windows-人工测试必须以-medium-完整性运行)。

## 评审说明

至少包含：

- 解决了什么问题，明确没有做什么。
- 关键数据流、状态转换或安全边界。
- 自动化命令和结果（含 CI run 编号）。
- 人工复测步骤（或 `sandbox.md` 的章节号）。
- 数据迁移、兼容性、性能和已知限制。

## Issue 收尾

满足验收标准后才关闭 Issue。更新内容：

1. 实际实现与原方案的差异。
2. 测试和人工复测结果。
3. 新增或变更的配置、数据库版本、协议版本。
4. 未解决的风险和后续 Issue 链接。
5. 对应常青文档的更新位置。路线图和已知限制见 [Kernel 改造进度](../07-路线图/Kernel-改造进度.md)、[已知限制](../07-路线图/已知限制.md)。

## 常见失败模式

- 只验证实时事件，没有验证刷新和重启恢复。
- 只改 JS 或只改 Rust，协议生成物没更新，`protocol:check` 失败。
- 改了外部后端错误码，前端镜像没同步。
- 把 API Key、Token 或 MCP 环境变量写进 SQLite 或日志。
- 修改旧迁移而不是追加新迁移。
- 从 Low 完整性目录运行 exe，把“拒绝访问”误判成回归。
- 只跑定向 CI 就认为全量通过。
- 删除旧文档前，没有把仍有效的信息整理进常青文档。
- 在共享工作区撤销或覆盖别人的改动。

## 完成定义

- Issue 验收项逐项通过。
- 代码、测试、数据库、协议和文档同步。
- 普通、失败、取消和恢复路径都考虑过。
- 没有提交密钥、构建产物、缓存或本机数据。
- 相关构建和测试已执行；没执行的项和原因写清楚。
