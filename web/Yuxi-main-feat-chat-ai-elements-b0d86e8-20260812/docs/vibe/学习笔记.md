## 第 2 站：后端启动与路由装配

### `backend/server/main.py` — 后端启动入口
**一句话定位**：后端的"总装车间"。创建 FastAPI 应用 → 挂路由和中间件 → 启动服务。本身没有业务逻辑，业务都在它挂载的东西里。

**6 个代码块**：
1. Windows 修补：换事件循环策略 + 修 sys.path（仅本地裸跑 Windows 生效，Docker 是 Linux 跳过）
2. 导入 + 常量：限流/CORS 的配置值
3. 登录记录器（内存字典 + 异步锁）+ CORS 配置函数
4. **创建 app + 挂路由（核心）**：`FastAPI(lifespan=...)` + `include_router(router, prefix="/api")`
5. 登录限流中间件（滑动窗口）+ 挂日志/限流中间件
6. `__main__`：uvicorn 启动按钮（本地裸跑用，Docker 里不用手动跑）

**🧠 关键设计**：
- **Windows 事件循环那段必须放最前面**：psycopg（异步 PG 驱动）跟 Windows 默认事件循环不兼容，得在 asyncio 被使用前换策略，晚了就来不及。
- **限流 = 滑动窗口算法**：deque 存登录时间戳，超 60s 的从头弹掉；窗口内满 10 次返回 429；**登录成功后清空该 IP 记录**（人性化）。
- **lifespan**：FastAPI 生命周期钩子（启动连库 / 关时清理），逻辑在 `server/utils/lifespan.py`。

**⚠️ 坑 / 易错**：
- **中间件执行顺序是反的**：Starlette 里"后添加的先执行"（洋葱模型）。添加顺序 ≠ 执行顺序。
- **CORS 的 `*` 和 credentials 不能同时开**：浏览器规范硬性要求，代码主动避开。
- **业务逻辑不在 main.py**：找接口 → `server/routers`；找启动初始化 → `server/utils/lifespan.py`。
- Docker 开发时别手动跑 `__main__`，docker-compose 已经帮你跑了。

### `backend/server/routers/` — HTTP 路由层（所有接口入口）
**一句话定位**：后端所有 HTTP 接口（`/api/...`）的家。18 个路由文件按业务领域拆分，在 `__init__.py` 里集中注册。路由层只管"接请求、调服务、返响应"，业务逻辑不在这（在 `yuxi/services/`）。

**18 个路由分三组**：
- 🟢 基础系统（必加载）：`system`、`auth`、`agent`、`chat`
- 🟡 管理工作台（必加载）：`dashboard`、`auth_dept`、`system_task`、`mcp`、`model_provider`、`skill`、`tool`、`user`、`filesystem`、`workspace`、`mention`
- 🔴 重依赖（LITE 模式跳过）：`knowledge`、`knowledge_eval`、`graph`

**🧠 关键设计**：
- **集中注册**：`__init__.py` 把所有子路由 include 到一个总 `router`，再由 main.py 加 `/api` 前缀。一眼看完所有接口，新增只改这一处。
- **LITE_MODE 延迟导入**：知识库/图谱/评估的 `import` 写在 `if not _LITE_MODE:` 块**内部**（不是文件顶部）——LITE 模式下连模块和重依赖库（Milvus/Neo4j）都不加载，不只是不注册路由。这才是真正省掉依赖的关键。
- **双 skills 路由**：`skill_router` 模块导出 `skills`（`/api/system/skills/*`，管理员）和 `user_skills`（`/api/skills/*`，普通用户）两个对象，同一份数据分权限视角。

**⚠️ 坑 / 易错**：
- 找接口实现三步：`__init__.py` 注释定文件 → `xxx_router.py` 找 URL 函数 → 真正业务在 `yuxi/services/`。
- 路由层必须"薄"，别写业务逻辑（架构不变量）。
- `_LITE_MODE` 判断用 `.lower()` + 接受 `true/1`，容错配置大小写。

### `backend/server/utils/lifespan.py` — 应用生命周期（启动/关闭清单）
**一句话定位**：FastAPI 的"开机/关机清单"。启动时连库、建表、塞内置数据、初始化各管理器；关闭时按序释放资源。就是 `main.py` 里 `FastAPI(lifespan=lifespan)` 传进去的那个。

**🧠 核心机制：`@asynccontextmanager` + `yield` 分两半**
- `yield` 前 = 启动逻辑；`yield` 处 = 运行期间；`yield` 后 = 关闭逻辑。
- 替代旧的 `@app.on_event("startup")`，启动/关闭共享同一上下文。

**启动初始化清单**（每项独立 try/except）：
- 数据库：`pg_manager.initialize` + 建表 + ensure schema
- 内置数据：MCP 服务器、Skills、4 种默认智能体、模型供应商、模型缓存
- 知识库（LITE_MODE 跳过）
- 基础设施：Redis 预热、配置同步线程、沙盒 provider
- LangGraph checkpoint 表（独立连接池 `langgraph_pool`）
- tasker 启动 + 打印 banner

**🧠 关键设计**：
- **每项独立 try/except + 只记日志不中断**：容错启动，非核心组件挂了不拖垮全局。但数据库失败也只记日志 → 后续依赖 session 的会连锁失败。核心依赖应"loud failure"，非核心才静默降级。
- **LITE_MODE 跳过知识库**：判断跟 routers 完全一致，同一开关多处边界统一。
- **LangGraph checkpoint 用独立连接池** `langgraph_pool`，跟业务库隔开互不拖累。

**⚠️ 坑 / 易错**：
- 关闭顺序是反依赖序：tasker → sandbox → queue → pg_manager（数据库最后关，别人清理还要用它）。
- `config.start_runtime_sync()` 是后台**线程**（同步轮询 Redis），不是 asyncio 任务。
- 部分 `import` 写在 try 块内（延迟导入，减启动加载/避循环依赖）。

### `backend/server/routers/auth_router.py` — 认证与用户管理路由（一个路由文件长啥样的范例）
**一句话定位**：所有 `/api/auth/*` 接口的家。登录、用户 CRUD、CLI 登录、OIDC 单点登录。1032 行，目录里的大文件。

**URL 拼接链**（呼应 main.py 限流）：
`@auth.post("/token")` + `APIRouter(prefix="/auth")` + `main.py include_router(prefix="/api")` → `/api/auth/token`。就是 main.py 里限流的那个端点。

**分块**：建路由器(45) → Pydantic 模型(48-179) → 登录`/token`(199-291) → CLI 设备码登录(299-342) → 首次运行+初始化管理员(346-425) → 用户信息`/me`/`/profile`(434-505) → 用户管理 CRUD(514-921) → 头像(925-947) → 模拟登录(951-1002) → OIDC(1010-1031)。

**🧠 关键设计**：
- **`/token` 登录叠了多层安全**：双标识登录(uid/phone)、防用户名枚举(不存在返回通用错误)、登录锁定(423+X-Lock-Remaining)、失败计数、成功重置。
- **两层限流防御**：main.py 限 IP 维度(60s/10次)，这里限账户维度(失败N次锁)。两层叠加才安全。
- **`Depends()` 是 FastAPI 核心**：自动调函数填参数；`get_admin_user` 等 handler 内部带权限校验，所以"加 Depends = 加权限校验"。
- **三档权限 Depends**：`get_required_user`(登录即可) / `get_admin_user`(管理员) / `get_superadmin_user`(超管)。换 Depends 即换权限。
- **Pydantic 模型**：数据模板，自动校验+生成文档，`response_model` 过滤返回值。
- **软删除**：`is_deleted=1` + 清空敏感字段，查询要带 `is_deleted==0` 过滤。
- **部门隔离**：`_ensure_user_in_current_department`，普通管理员只能管本部门。
- **OIDC 路由是"薄路由"典范**：每个函数体一行 `return await xxx_handler(...)`，逻辑全在 service。

**⚠️ 坑 / 易错**：
- `/token` 和用户 CRUD 的业务逻辑(密码校验/锁定/权限)写在路由里，没下沉 service——能跑但路由偏胖。新增接口参考 OIDC 那组，逻辑放 `yuxi/services/`。
- 删除用户是软删除，查用户记得过滤 `is_deleted==0`，否则会查到"已注销用户-xxx"。
- 模拟登录(`/impersonate`)是危险操作，有日志警告，仅超管可用。

### `backend/server/utils/` — Web 层通用工具箱
**一句话定位**：只服务 Web 层（HTTP 认证/日志/生命周期）的通用工具，不放业务逻辑。跟业务包 `yuxi/utils` 是两套，别混。

**5 个文件**：`lifespan.py`(生命周期,已学) / `auth_middleware.py`(⭐认证权限真身) / `access_log_middleware.py`(访问日志中间件) / `common_utils.py`(setup_logging) / `__init__.py`。

**🧠 关键设计（auth_middleware）**：
- **权限是嵌套责任链**：`get_superadmin_user` → `get_required_user` → `get_current_user` → `get_db`。每层在前一层上加一道检查，Depends 自动串链。写一个 Depends = 跑完整条链 = 加到对应权限档。
- **Depends 可链式依赖**（A 依赖 B，B 依赖 C）——FastAPI 设计精髓。换 Depends 即换权限档。
- **双认证**（get_current_user）：token 以 `yxkey_` 开头走 API Key，否则走 JWT。浏览器用 JWT，程序/CLI 用 API Key。
- **API Key 设计**：存 sha256 哈希不明文；支持"绑定用户"和"绑定部门"（部门 key 找该部门管理员身份代执行）两种。
- `get_required_user` 要求"登录 + 有部门"，是 admin/superadmin 的前置。

**⚠️ 坑 / 易错**：
- `_extract_client_ip` 在 main.py 和 access_log_middleware 里重复（小瑕疵，第三处用到再抽公共）。
- `access_logger` 用 `propagate=False` 防日志重复；`setup_logging` 清掉 `uvicorn.access` handler（自己用 access_logger 记访问日志）。

## 第 3 站：Agent Run 异步执行链路

### `backend/server/worker_main.py` — Worker 进程入口（壳文件）
**一句话定位**：16 行的"壳文件"，自己不干活，只做 Windows 环境修补 + 指向真正的 worker 设置（`yuxi.services.run_worker.WorkerSettings`）。

**3 块**：① Windows 事件循环修补（跟 main.py 一模一样）② `from yuxi.services.run_worker import WorkerSettings` ③ `__all__`。

**🧠 关键认知（比代码重要）**：
- **worker 是独立进程**：docker-compose 里 `worker-dev` 跟 `api-dev` 是两个独立容器/进程。main.py 的环境修补/初始化对它不生效，这里得自己再做一遍。
- **为什么要有 worker**：智能体跑一次对话可能几十秒~几分钟（调大模型/检索/多轮思考），不能让 HTTP 请求挂着。流程：API 把任务丢 Redis 队列→立刻返回→worker 取任务慢慢跑→进度写回 Redis→前端 SSE/轮询拿进度。
- **ARQ**：Python 异步任务队列库（基于 Redis），轻量版 Celery，原生 asyncio。`WorkerSettings` 是其配置类。
- **壳文件模式**：入口只做"环境准备 + 转发"，真正配置在 `run_worker.py`，入口干净可复用。

**⚠️ 坑 / 易错**：
- 真正的 worker 逻辑不在这，在 `yuxi/services/run_worker.py`。
- Windows 修补跟 main.py 重复（连注释都没改），因为两进程各自独立修补。

### `yuxi/services/run_worker.py` — Worker 端：怎么接活、怎么干活
**一句话定位**：worker 真正干活的逻辑。取任务、执行智能体、进度写回 Redis、处理取消和重试。`WorkerSettings` 是 ARQ 配置，`process_agent_run` 是核心任务函数。

**分块**：两异常类(Retryable/NonRetryable) / `RunContext`(取消监听) / `ChunkedEventWriter`(事件批量缓冲) / 辅助函数 / `_consume_stream_with_cancel`(消费流+监听取消) / ⭐`process_agent_run`(核心) / `_worker_startup-shutdown` / `WorkerSettings`。

**🧠 关键设计**：
- **`WorkerSettings`**：`functions=[process_agent_run]`(worker 只处理这一个任务)、`max_tries=2`、`job_timeout=3600`(1h)、`on_startup/shutdown`、`redis_settings`。API 入队时任务名必须对上 `process_agent_run`。
- **`process_agent_run` 流程**：取run(已终结则跳过)→解析payload→加载用户→标记running→建RunContext+Writer→发metadata→消费流(按finished/error/interrupted/ask_user分支收尾)→异常处理(取消/可重试/不可重试)→finally清理。
- **取消=协作式**：API 往 Redis 写信号 → RunContext 后台每 0.2s 轮询 → `_consume_stream_with_cancel` 用 `asyncio.wait` 同时盯"下一个chunk"和"取消信号"，谁先到处理谁。能在 chunk 间优雅中断+flush，不是强杀。
- **重试分错误类型**：可重试(网络/DB断/超时/RetryableRunError) vs 不可重试(NonRetryableRunError业务错误)。`_is_last_try` 判断是否最后一次，是则 failed，否则 raise 让 ARQ 重新入队。
- **`ChunkedEventWriter`**：流式 token 攒到 100ms/512字符 再批量写 Redis，tool_call 立即刷。

**⚠️ 坑 / 易错**：
- `_worker_startup` 里 worker 自己初始化(连库/建表/ensure MCP/skills/配置同步)，比 API lifespan 精简——印证 worker 独立进程要自己起家。
- 任务名 `process_agent_run` 是 API 入队和 worker 处理的"对接暗号"，两端必须一致。

### `yuxi/services/agent_run_service.py` — API 端：怎么派活、怎么看进度
**一句话定位**：API 端服务，负责创建 run、入队、SSE 推进度、取消。路由调它，它调 repositories + ARQ 队列。跟 run_worker.py 是"派活/接活"两端。

**分块**：SSE常量(心跳15s/最长30min/轮询1s) / `_compact_*`(事件压缩省流量) / ⭐`create_agent_run`(创建+幂等) / ⭐`enqueue_agent_run`(入队派活) / 查结果系列 / `request_cancel_agent_run`(取消发送端) / ⭐`stream_agent_run_events`(SSE流)。

**🧠 关键设计**：
- **`enqueue_agent_run`（派活现场，2行）**：`queue.enqueue_job("process_agent_run", run_id, _job_id=f"run:{run_id}")`。任务名对上 worker 的 functions；`_job_id` 防重复入队。
- **`create_agent_run` 幂等**：`request_id` 相同不重复创建（防重复提交）；resume 沿用原模型；非法模型直接 422 不静默回退（呼应"不掩盖缺陷"）；IntegrityError 兜底再查一次。
- **`stream_agent_run_events`（SSE，轮询 Redis 模式）**：循环拉 Redis 事件→SSE 推前端；遇 end 结束；run 终结补 end；每 15s 发心跳防超时；最长 30min；每秒轮询。
- **`request_cancel_agent_run`（取消发送端）**：DB 标记 cancel_requested + Redis 发信号。worker 的 RunContext 轮询到后优雅中断。支持 cascade_children 级联取消子 run。

**⚠️ 坑 / 易错**：
- `_compact_*` 是 verbose=False 时压缩事件去冗余，省 SSE 流量，非核心逻辑。
- SSE 心跳 `: heartbeat` 是注释行，保持连接活着，防代理/浏览器断开。

**🔗 第 3 站核心图：两文件通过 Redis 三条通道串联（最该记的）**
```
[API: agent_run_service]          [Redis 三通道]          [Worker: run_worker]
create_agent_run → 建 run 到 PG
enqueue_agent_run ─────────────→ ①ARQ任务队列 ─────────→ process_agent_run 取任务
                                                          ↓ stream_agent_chat 跑
stream_agent_run_events ← 轮询 ← ②事件流 ←──────────── append_run_event 写进度
request_cancel_agent_run ───────→ ③取消信号 ───────────→ RunContext 轮询中断
```
- ① 任务队列：API 入队 / Worker 出队（对接暗号=任务名 `process_agent_run`）
- ② 事件流：Worker 写进度 / API 轮询推前端（带 seq，断线可续）
- ③ 取消信号：API 发 / Worker 协作式中断

**核心认知**：API 与 Worker 是两独立进程，不直接调函数，靠 Redis"传纸条"解耦。API 立刻返回，Worker 慢跑，进度流回前端，断线能续。= 长耗时任务异步化标准解法。理解这张图 = 第3站通80%。

### `backend/package/yuxi/` — 后端业务包（整个后端的主体）
**一句话定位**：后端所有业务逻辑的家。跟 `server/`（Web 适配层）分工：server 管 HTTP 收发，yuxi 管业务。路由调 yuxi.services，service 协调各领域模块。

**`__init__.py` 设计**：
- `load_dotenv(".env")` 导入即加载环境变量。
- `executor = ThreadPoolExecutor()` 包级全局线程池。
- ⭐ **模块级 `__getattr__` 惰性加载（PEP 562）**：`from yuxi import knowledge_base` 时才 import 重的 `yuxi.knowledge`。

**🔑 项目一致模式：重依赖按需加载（第3次见）**：routers 的 LITE_MODE 块内 import、lifespan 的 try 内 import、yuxi 的 `__getattr__` 惰性加载——都是"别启动时全加载"。

**8 个子目录（按依赖方向从上到下）**：
- `config/` — 应用配置、内置模型信息
- `services/` ⭐ — 用例层，业务流程编排，路由调它
- `agents/` — LangGraph 智能体（基类/内置/中间件/工具/后端），第3站核心
- `knowledge/` — 知识库+图谱（分块/解析/Milvus/Neo4j），第5站
- `models/` — chat/embedding/rerank 模型适配
- `repositories/` — DB 查询边界，路由不绕过它
- `storage/` — 连接池(postgres)/对象存储(minio)
- `utils/` — 业务通用工具（跟 server/utils 不同）

**🧠 依赖方向（架构不变量）**：
`server(路由,薄) → services(用例) → repositories/agents/knowledge/models(领域) → storage(基础设施)`。单向向下。改代码先想"这行该放哪层"。

**⚠️ 坑 / 易错**：
- `yuxi/main.py` 是占位文件（"Hello from yuxi!"），无实际逻辑，忽略。
- `yuxi/utils`（业务通用）≠ `server/utils`（Web 层通用），别混。
