## Capability JSON root cause

The sampler was correct. The earlier 7 requests genuinely lacked the capability section.

Before the fix, actual HTTP for the real PiNative path:

- system prompt `1875` chars;
- no `Host runtime availability for this frozen manifest/profile:`;
- no `<fox_context>`;
- the content was the Pi SDK default prompt, not the Fox composed prompt.

The same Run's `run.request_snapshot.promptDiagnostics` already had `host_runtime_availability` (1304 rendered chars) and a composed prompt around `29980` chars. The facts were composed but never delivered.

Exact defect: `composeFoxPrompt` returned `prompt`, hashes and diagnostics but omitted `stablePrefix` and `dynamicTail`. `pi-runtime.mjs` passed those fields to `createFoxPlanningExtension`; both were `undefined`, so the extension set an empty `customPrompt` and no `fox_context` section. Pi therefore used its default system prompt.

Fix `2ccd2a97` returns both halves. No identity validation was removed, no Host permission was relaxed, no tool was opened, and no duplicate capability registry was added.

The test `98c9c59a` (later fatal-fixture fix `87635ecc`) starts the **real `pi-runtime.mjs`**, runs the **real SDK extension**, points it at a local HTTP SSE endpoint, and inspects the serialized request body. It asserts the heading, `<fox_context_block>`, the exact manifest/profile identity and `run_command` in the provider tool list. This is the persistent protection for the full delivery chain; the earlier field-only assertion remains as a fast unit check.
